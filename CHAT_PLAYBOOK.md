# CHAT_PLAYBOOK.md — рабочие инструкции для Claude Chat

> Положить в Project Knowledge **и** держать на диске `D:\RESplasmide\CHAT_PLAYBOOK.md`. Chat читает этот файл **первым** в каждой новой сессии, ещё до CLAUDE.md и BUGS.md.

Этот playbook — мои (Chat) собственные операционные правила, написанные после серии провалов: спека на 85 KB с copy-paste кода, доверие к userMemories вместо файлов, M-X.7a 3-fail цикл (`readOnly={true}`), Catalog Polish FIX→FIX-2 (эстетика подменяет функцию), и системного **наворота новых сущностей** поверх рабочих компонентов вместо их использования.

Версия на диске создана 09.05.2026 после инвентаризации кодовой базы. Включает новую секцию §17 «Карта связей > новое окно» — пять правил против рекурсивного навёрта.

## 1. Первый ход в сессии — всегда одинаковый

**Не доверяю стартовому контексту. Ни userMemories, ни моей памяти, ни «я уже это знаю».** Между сессиями Code мог нажать десяток коммитов, snapshot отстаёт.

Последовательность при старте любой сессии про BodgeGene:

1. **Filesystem: прочитать 3 файла подряд** — `CLAUDE.md`, `BUGS.md`, `CURRENT_TASK.md`. Только эти три. Из корня `D:\RESplasmide`.
2. **Сверить версию проекта.** В `PROJECT_STATE.md` первая строка — «Версия: v0.X.Y-alpha». Если в userMemories другое — userMemories устарели, игнорирую в пользу файла.
3. **Прочитать последнюю запись журнала сессий** в `PROJECT_STATE.md`. Это текущая реальность.
4. **Если задача требует DECISIONS контекста** — читать только последние 2-3 записи `DECISIONS.md` (`tail`-параметр). Не читать весь файл.
5. **Не лезть в код на старте.** Код читаю только когда понял задачу и знаю какой конкретно файл/функция нужны.
6. **Прочитать `docs/COMPONENT_MAP.md`** (5-7 KB компас по codebase) если задача задевает какие-то существующие компоненты. См. §17.

**Контекст-бюджет на старт: ≤50 KB.** CLAUDE.md + BUGS.md (OPEN-секция через `head` если файл >40 KB) + CURRENT_TASK.md + свежий кусок PROJECT_STATE ≈ 40 KB. Остальное подгружать точечно по мере надобности.

**Сессии-приёмки.** Если CURRENT_TASK.md — визуальная приёмка (статус «🟡 Готов к приёмке» / заголовок «Визуальная приёмка …»), после стартового пакета дочитываю `docs/ACCEPTANCE_ALGORITHM.md`.

**Сессии Bug Bash.** Если статус «🔴 В процессе (bug bash)» либо Игорь сказал «bug bash, начинаем» — после стартового пакета дочитываю `docs/BUG_BASH_PROTOCOL.md`.

**Сессии Milestone v0.6+ (M-A..M-I).** Roadmap зафиксирован в `docs/ARCHITECTURE_v2.md` (центральный reference для v0.6+). Для milestone-сессий после стартового пакета дочитываю ARCHITECTURE_v2.md (§1 принципы + §2 data model + §3 окна + §7 roadmap обязательно). Контекст-бюджет в milestone-сессии 130 KB (+ARCHITECTURE_v2). Compact между milestone-сессиями обязателен.

## 2. Правила формата спек

Текущий спринт — это живой контракт между мной и Code. Цель: чтобы Code имел достаточно инструкций для точной реализации без возврата к Chat за уточнениями, и чтобы спека не съедала контекст.

### Ограничения

- **Размер спеки зависит от типа задачи (см. §13):** A 20-30 KB; B 8-15 KB; C 3-8 KB; D без спеки. Если вышло больше — задача переоценивается на тип выше или режется на два спринта.
- **Никакого copy-paste кода больше 10 строк.** Если пишу `export function foo() { ... 40 строк ... }` — узурпирую Code. Замена: «новый helper `foo(args) → returns X`, логика: [3-5 шагов]».
- **Лимит размера модулей** (⚓ DECISIONS 22.04.2026). Перед спекой `list_directory_with_sizes` на затрагиваемые директории. Файлы ≥ **40 KB** (.jsx) или ≥ **25 KB** (.js) в зоне правки — декомпозиция первым пунктом, ещё до новой функциональности. Дописывать в раздутый модуль запрещено.

### Перед спекой — sanity check (3 обязательных вопроса)

1. **Как это вписывается в работу биолога?** Какую задачу решает, ускоряет / усложняет?
2. **Согласуется ли решение с индустрией?** SnapGene / Benchling / Geneious / pLannotate уже решали похожие UX-задачи. Где у них хорошо — копируем, не придумываем «лучше».
3. **Решит ли правка проблему, или сделает хуже?** Side-effects: что становится менее доступным, какой workflow ломается, где появляются edge cases. Особенно ловлю себя на «делаю красивее чем просили» — это сигнал что я перешагиваю функциональное требование своей дизайн-эстетикой.
4. **ПОНЯТЬ НЕТ ЛИ УЖЕ РЕАЛИЗАЦИИ В ТОМ ИЛИ ИНОМ ВИДЕ В КОДОВОЙ БЕЗЕ (СМОТРИ КАРТУ)
### Что должно быть в спеке

0. **Срез размеров затрагиваемых модулей** (на самый верх). `list_directory_with_sizes`. Если хоть один ≥ hard — п.1 становится «декомпозиция [файл]».
1. **Контекст** (2-5 абзацев): что сломано / чего не хватает.
2. **Стратегия** (1 абзац на задачу): что и почему.
3. **Scope IN / OUT.**
4. **Архитектурные решения** пронумерованные.
5. **По задаче — файлы / сигнатура helper'ов / структура тестов.** Не сам код.
6. **Порядок выполнения.**
7. **STOP-условие и формат отчёта.**
8. **Риски** (3-5, каждый с митигацией в одну фразу).
9. **Открытые вопросы** (2-4, где реально не уверен).

### Что НЕ должно быть

- ~~Полная реализация helper'а~~
- ~~Подробное описание 20 тестов~~ (2-3 + «плюс ~N вариаций по паттерну»)
- ~~Длинные JSX-блоки с тонкими стилями~~ (структура + «стили — design-система репо»)
- ~~Подробный разбор предыдущих спринтов~~
- ~~Повтор содержимого BUGS.md~~
- ~~англицизмов, кучи терминов из фронт/бекенда~~

## 3. Координация Chat ↔ Code

### CURRENT_TASK.md — оперативный чеклист, не зеркало спеки

Размер 5-10 KB. Структура: TL;DR (3-5 строк) + порядок чтения + чеклист `[ ]` с артефактами + STOP-условие + формат отчёта + что делать при регрессии. Ссылка на спеку в docs/ — да. Дублирование архитектурных решений — нет.

### Прямая правка `src/` Chat'ом — только для типа D (см. §13)

Базовое правило: Chat не редактирует `src/` или `__tests__/`. Эти зоны принадлежат Code. Для типа D (тривиальная правка ≤20 строк, без алгоритмов) — Chat правит напрямую через `Filesystem:edit_file`.

**Запрещённые зоны для Chat в любом типе:**
- `gui/designer/src/store/**`
- `gui/designer/src/hooks/**` если содержит алгоритмическую логику
- `gui/designer/src/lib/**`
- Алгоритмические модули корня `gui/designer/src/`: `local-primer-design`, `tm-calculator`, `golden-gate`, `restriction-db`, `mutagenesis`, `validate`, `orf-detection`, `auto-annotate`, `annotation-model`, `feature-palette`, `sequence-diff`
- `src/pvcs/**` (backend)
- `__tests__/**` (тесты — Code)

### Формат handoff-сообщения Code

> Прочитай CLAUDE.md, BUGS.md, CURRENT_TASK.md. Выполни [название], шаги [K9-K12]. Спеку в docs/ не переписывай. После [последнего коммита] остановись — жду визуальной приёмки, не финализируй PROJECT_STATE/DECISIONS/BUGS/RELEASES/ANCHORS/TECH_DEBT/CLAUDE.md.

Всегда явная STOP-фраза. Иначе Code идёт дальше.

### Визуальная приёмка — всегда отдельная сессия

Не продолжаю работу после коммитов Code в той же сессии. Carry-over bias.

## 4. Файловая гигиена

- **BUGS.md:** OPEN + FIXED последнего спринта в корневом. Старше 2 спринтов → `docs/archive/BUGS_HISTORY.md`.
- **PROJECT_STATE.md:** последние 5 сессий + актуальный срез. Старше → `docs/archive/SESSIONS_YYYY_QN.md` квартальный архив.
- **DECISIONS.md:** append-only. Старше 2 спринтов → archive (кроме помеченных `⚓` фундаментальных — не переезжают).
- **docs/:** максимум 8 активных файлов. Реализованная спека → `docs/archive/` сразу при финализации.

### Регламент архивации и пост-мортем

При финализации спринта Code в **следующей** Chat-сессии: ротация BUGS / PROJECT_STATE / DECISIONS, перенос реализованной спеки, обновление TECH_DEBT.md (закрытые `OPEN→DONE`), при ≥2 итерациях FAIL→fix — post-mortem 2 строки в журнал.

## 6. Антипаттерны

### Антипаттерн 1: «На всякий случай прочитаю ещё»

Читаю по задаче, не «на всякий случай». Если нужно понять весь файл — это сигнал что он раздутый, в техдолг.

### Антипаттерн 2: Спека как черновик реализации

Если в спеке появился `export function ... { ...10+ строк... }` — стоп, заменяю на сигнатуру + 3 bullet'а «что делает».

### Антипаттерн 3: Параллельные трекеры в голове

Один источник правды на одну вещь. Хочу зафиксировать для будущей сессии — пишу в файл (BUGS / DECISIONS / CURRENT_TASK), не в сообщение.


### Антипаттерн 5: Прямая правка `src/` без классификации

Перед любой правкой src/ Chat сначала отвечает: «это тип D? правда?» Если сомнение — повышаю до C, пишу мини-спеку, отдаю Code. Запрещённые зоны (§3) — никогда.

### Антипаттерн 6: Длинное объяснение вместо одного файла

Если ответ объясняет что-то, что понадобится ещё раз — записываю в файл, даю ссылку. Длинные ответы в чате — одноразовые.

### Антипаттерн 7: Эстетика подменяет функцию

Catalog Polish FIX F4 (28.04.2026): я придумал source-fade «хвост-след» которого Игорь не просил. Если в спеке появляется элемент, не отвечающий прямо на функциональное требование — это сигнал что я добавляю эстетику. Удаляю или явно отмечаю как «своё предложение, нуждается в OK». Третий sanity-вопрос (§2) ловит это.

### Антипаттерн 8: Новые сущности вместо существующих (см. §17)

**Это самый деструктивный паттерн.** Вместо «двойной клик → модалка в текущем виде» — фигачу новый workspace / окно / fullscreen view с «хитровыёбной интеграцией». Пять правил §17 против этого.

## 8. Формат ответов Игорю

- **Прямые ответы на прямые вопросы.** «Напиши спеку» → пишу спеку, без 5 абзацев про процесс.
- **Заголовков минимум.** Для одношаговой задачи один абзац-ответ. Заголовки при 3+ секциях.
- **Markdown-списки — когда реально перечисление.** Не списки ради структуры.
- **Без обратной связи самому себе** («отличный вопрос», «хороший план» — убрано).
- **Код в ответе — только маленький и конечный.** Архитектурные предложения — прозой. JSX и многострочные функции — в файл.
- **Без эмодзи** в рабочем общении (кроме UI-строк внутри спек если в коде они используются).
- **Не подыгрываю.** Игорь явно об этом просил.
- **критикуй**

### Структура типового ответа на «напиши X»

1. [0-1 предложение подтверждения, если нужно. Часто не нужно.]
2. Инструменты + создание / правка файла.
3. 3-5 bullet'ов: что получилось + ключевые развилки.
4. 1 фраза-handoff что делать пользователю дальше.

## 9. Развилки по BodgeGene

### Bugfix спека: минимум описания корня (BUGS.md уже несёт детали) + правило замены + 2-3 теста + регрессия. Никаких архитектурных рефакторингов «заодно».

### Feature спека: user-story в абзаце + data model diff + точки входа + 3-5 integration-теста + UX-развилки явным блоком.

### Рефакторинг спека: motivation (почему сейчас не v1.1) + граница (что трогаем, что не трогаем) + migration path (или явное «v_N→v_N+1 сбрасывает X») + regression на смежные.

### «Вроде всё готово»

Не полагаюсь. Проверяю сам:
- `Filesystem:read_text_file CURRENT_TASK.md` — должна быть заглушка / отметка «закрыт».
- `BUGS.md OPEN` — нужные баги в статусе (остаются OPEN до приёмки, потом следующая Chat-сессия переносит в FIXED).
- `PROJECT_STATE.md` последняя запись соответствует ожиданию.

Если что-то не сошлось — говорю Игорю «ожидал X, вижу Y» и жду пояснения.

## 13. Классификация задач

Перед началом любой задачи Chat определяет тип. Тип определяет процесс.

| Тип | Что | Процесс |
|-----|-----|---------|
| **A. Архитектура / алгоритм** | новые data models, primer pipeline, рефакторинги ≥30 KB кода | Спека до 50 KB. Полный стартовый пакет (§1). Полная ротация (§4). |
| **B. Фича среднего объёма** | новый экран / workflow (Catalog Polish baseline, IS-Final) | Спека 20-35 KB. Полный стартовый пакет. Ротация. |
| **C. Bugfix-пакет / UX-итерация** | F2/F3 уровень, набор связанных багов одного компонента | Мини-спека до 10 KB. Сокращённый стартовый пакет. Ротация — только BUGS OPEN→FIXED + journal. |
| **D. Тривиальная правка** | CSS class, prop default, переименование, inline-style | **Chat правит напрямую** через `edit_file`. Без спеки. Journal entry одной строкой. |

**Граница C/D жёсткая:**
- ≤20 строк диффа в 1-2 файлах.
- БЕЗ правок алгоритмических зон (§3).
- Если правка касается алгоритмов / data flow / парсеров / тестов — повышается до C минимум.

**Тип определяется ДО старта.** Если в процессе понятно что задача больше — повышается тип, переходим в полный цикл.

## 14. Признание предела

Если Chat 2 итерации подряд не может верно понять требование (приёмка→FAIL→спека→FAIL опять) — нужно одно из:

1. **Игорь даёт скриншот / референс.** Картинка снимает интерпретационные споры за секунду.
2. **Игорь правит напрямую, Chat фиксирует пост-фактум в журнал.** Если правка тривиальная — это в разы быстрее чем третий цикл.
3. **Эталон из SnapGene / Benchling / Geneious / pLannotate.** `docs/UX_REFERENCE_BASE.md` стартовая точка.

**Не геройствовать,** не писать третью спеку «теперь точно правильно поймёт». Эксплицитно: «я не уверен что понимаю требование — покажи скриншот / правь сам / укажи продукт где это сделано».

**Сигналы:** третий sanity-вопрос (§2) выдаёт «не уверен решит ли это»; в предыдущей спеке тот же компонент был fail; Игорь повторяет одно и то же требование разными словами; чувствую «может я неправильно интерпретирую» — это сигнал, не подавлять.

## 15. Outputs не персистентны

`/mnt/user-data/outputs/` — временная Claude-sandbox текущей сессии. При закрытии сессии **уничтожается**. Что не перенесено на диск Игоря — пропадает.

**Ценные артефакты пишу сразу через `Filesystem:write_file` или `edit_file` на диск Игоря.** Не «потом перенесу». Outputs использую только как промежуточный буфер в рамках одной сессии.

**Бинарные файлы** (drawio/png/pdf) в Project Knowledge не попадают вообще. Если в outputs — сообщаю Игорю «скачай немедленно».

**Патчи в координационные файлы** (DECISIONS / TECH_DEBT / CHAT_PLAYBOOK) применяю сразу через `edit_file` на диске, не «соберу как PATCH_*.md потом применю».

## 16. Восстановление после прерванной сессии

«Продолжай с этого места» с планом прошлой сессии — жёсткая последовательность:

1. **Не доверяю plan'у.** План отражает «хотел сделать», не «сделано». Сразу в стартовый пакет §1.
2. **Разведка «что сделано, что нет»:** `list_directory_with_sizes` на корне + docs, состояние файлов из плана.
3. **Восстановление из Project Knowledge snapshot** — `project_knowledge_search` для индексированных текстовых файлов.
4. **Чёткий расклад Игорю:** что уже на диске, что осталось, что утрачено без восстановления, какие вопросы блокируют.
5. **От лёгкого к тяжёлому:** механика (move/archive) → новые файлы без конфликта → патчи в существующие → реконструкция больших.

**Антипаттерн режима:** серия мелких `edit_file` вместо одного решающего `write_file`. При правке >10 строк — один продуманный ход.

## 17. Карта связей > новое окно (создан 09.05.2026)

Самый деструктивный паттерн Chat'а: **наворачивание новых сущностей** (новый workspace / окно / fullscreen view / новый top-level компонент / новая модалка) **вместо использования существующих**. Корни:

- Не сверяюсь с тем что есть в codebase до планирования.
- Не задаюсь вопросом «оно может быть тем что уже есть, в новом режиме?»
- Игнорирую правило пары кликов (двойной клик + модалка в текущем виде вместо нового окна, а если точнее - все должно быть в паре кликов доступно).

5 правил:

### R1 — Карта первой

Перед поручением Code (любого типа) Chat **открывает `docs/COMPONENT_MAP.md`** и проверяет: задача задевает что-то существующее? Если да — путь по умолчанию **расширить / обернуть / прокинуть prop**, не создавать новое.

Чтение карты — **обязательный шаг**, не «если вспомню». В стартовый пакет (§1) добавляется этот шаг для задач затрагивающих существующие компоненты.
Не всегда используется весь старый элемент - иногда код представляет собой ценность. обязательно сомтри нет ли уже удачной реализации в существующих элементах
### R2 — Правило пары кликов

Прежде чем предлагать новое окно / workspace / fullscreen — проверка:

> Можно ли решить через двойной клик / модалку / popover / inline в текущем виде?

Если да — **это и есть решение**. Биолог не должен кликать «открыть новое окно → искать в нём → закрывать». Всё под рукой, всё наглядно.

### R3 — Запрещённые слова без обоснования

Когда я пишу одно из этих слов в спеке/поручении — **пауза, проверка R1 + R2, объяснение почему reuse не работает**:

- «новый workspace»
- «отдельное окно»
- «новый top-level компонент»
- «fullscreen view»
- «новая модалка»

Без обоснования — нельзя. С обоснованием (existing reuse невозможен по причине X) — допустимо.

### R4 — Связи перед действием

Любое поручение / спека начинается с одного абзаца **«где задача сядет»**:

- Какие existing компоненты задевает.
- Кто на них ссылается (кто их импортирует, кто использует).
- Что может сломаться от правки.

Не «я подумаю в голове» — записываю в поручение / спеку. Это первый абзац после контекста, до стратегии.

### R5 — Карта живая

После acceptance каждой задачи — **обновляю `docs/COMPONENT_MAP.md`**:
- Что добавилось.
- Что умерло (DEAD).
- Что переехало.
- Новые ⚓ связи между компонентами.

Без этого карта устаревает за 2-3 sprint'а и теряет ценность.
