# AGENTS.md — BodgeGene

BodgeGene — local-first редактор плазмид и конструктор генетических сборок. Рабочий каталог: `D:\RESplasmide`.

## Восстановление контекста

Всегда читать в таком порядке:

1. `AGENTS.md` — постоянные правила.
2. `CURRENT_TASK.md` — текущий scope и чеклист.
3. `PROJECT_STATE.md` — короткий актуальный snapshot.

Дополнительно только по задаче:

- дефект → `BUGS.md`;
- архитектурное решение → `DECISIONS.md` + `docs/ARCHITECTURE.md`;
- планирование → `docs/BACKLOG.md`;
- UI → `docs/DESIGN_SYSTEM.md`;
- конкретная подсистема → `docs/COMPONENT_MAP.md` и подходящий skill.

Не читать архивы и старые отчёты «на всякий случай». Источник истины по поведению: **код → тесты → нормативная спецификация → текущие документы**.

## Роли и поток работы

- Пользователь — владелец продукта и биологической семантики: утверждает scope,
  компромиссы и финальную приёмку.
- Planner — единственный операционный центр решений внутри утверждённого пользователем
  scope: формулирует пакет, выбирает режим работы, принимает или отклоняет frozen
  candidates, консолидирует review, назначает Integration owner и запускает финальный
  gate. Обычно Planner не пишет product code.
- По умолчанию пакет пишет один Implementation coder. Для крупного или
  высокорискового пакета Planner может назначить максимум двух coder только в одном из
  трёх режимов:
  - **implementation + independent proof** — один coder пишет production, второй только
    oracle/tests/mutations/benchmark в отдельном manifest; до первого freeze они не
    читают изменения друг друга; это default двухкодерного режима для high-risk пакета;
  - **seam split** — заранее замороженный интерфейс, отдельные worktree и
    непересекающиеся manifests; это режим пропускной способности, а не усиления proof;
  - **independent alternatives** — только когда сам контракт недоопределён: до кода
    Planner фиксирует конкурирующие гипотезы и критерий выбора; два frozen proposal не
    смешиваются автоматически.
- Два coder никогда не пишут в один writable checkout и никогда одновременно не
  редактируют один файл. Такой режим начинается только от чистой зафиксированной базы
  или явно подготовленного воспроизводимого snapshot; если dirty worktree нельзя точно
  воспроизвести в обеих изоляциях, остаётся один writer.
- Experimental Agent Teams и самопорождение вложенных writers не являются режимом
  реализации. Двух writer запускают только как два отдельных foreground-процесса
  `claude --worktree <unique-name> --agent <profile>`; каждый до edit подтверждает, что
  его `HEAD` равен принятому base SHA. Два writer-профиля нельзя запускать из одной
  неизолированной Claude-сессии. Coder не делегирует product edits дальше.
- Integration owner — ровно один из coder, назначенный Planner. После первого freeze
  второй coder становится read-only. Planner выбирает frozen inputs и выдаёт Integration
  owner новый **integration manifest**: явное объединение принятых component/proof файлов
  и отдельно названных integration-файлов. Только после этой передачи Integration owner
  собирает canonical candidate и выполняет correction; исходные manifests не расширяются
  молча. Planner не редактирует параллельно те же product-файлы.
- Reviewer работает read-only по замороженному candidate и не становится автором.
  Низкорисковому policy/mechanical пакету достаточно одного; обычному изменению
  поведения — до двух; для биологии, потери данных, trust boundary, concurrency,
  state-ownership или cross-layer пакета допустимы до трёх независимых линз. Reviewer
  видит контракт и candidate, но до своего вывода не читает отчёты других reviewers.
  Review — не голосование: Planner проверяет каждую находку и принимает одно решение.
  При консолидации Planner сопоставляет объединённый `unverified surface` reviewers со
  всем manifest: каждый участок получает evidence, явно принятый residual risk или blocker.
- На handoff каждый writer замораживает свой proposal/component/proof и передаёт base
  SHA, точный manifest и проверяемый digest содержимого/patch; Integration owner затем
  передаёт единый integrated candidate. Commit SHA допустим только если пользователь уже
  разрешил commit. Пересказ и «живой diff, который ещё меняется» не являются передачей.
- Предпочитать крупный вертикальный пакет с одним контрактом микрошагам по одной строке.
  Но один пакет не должен смешивать независимые продуктовые цели.
- Передача кодеру содержит base SHA, writer mode и роль, цель, инварианты, IN/OUT,
  owned manifest/worktree, имя Integration owner, наблюдаемые критерии и гейт; внутри
  этих границ coder сам выбирает реализацию и не докладывает после каждого файла.
- Норма цикла: один integrated handoff → один параллельный read-only review → один
  консолидированный correction pass → финальная проверка только названных исправлений и
  gate. Если та же неисправность пережила correction либо обнаружилась новая корневая
  причина, работа останавливается и перепланируется; второй test-only correction и третий
  круг «докажите ещё» запрещены.

## Обязательные правила

### 1. Тест сначала и соразмерная проверка

Для изменения поведения:

1. тест воспроизводит требование или дефект и падает по целевой причине;
2. минимальная реализация делает его зелёным;
3. focused tests выполняются во время реализации;
4. related tests — один раз на candidate, от принятого base SHA или явного списка;
5. Planner запускает полный test/build/browser gate один раз после принятого
   candidate или correction pass; coder и reviewers не дублируют этот прогон.

Тесты — доказательство изменения, а не самостоятельный продукт. Перед каждым запуском
назвать диагностический вопрос и то, как PASS и FAIL изменят следующее действие. Повтор
того же запуска на неизменном relevant code/test/fixture/instrumentation/environment не
добавляет evidence и запрещён, кроме одного контролируемого retry по flake-протоколу.
Новый запуск информативен только после изменения реализации, наблюдаемого контракта,
диагностической фикстуры/мутации или явно проверяемой гипотезы об окружении.

Как только RED локализовал дефект и ответственный контракт, следующим действием должна
быть реализация либо явный blocker, а не более широкий тестовый круг. Если два
последовательных Planner↔coder цикла состояли только из review/rerun без изменения
кандидата или новой фальсифицируемой причины, обязательны STOP и перепланирование до
третьего цикла.

Если новый тест сразу зелёный, сначала доказать, что поведение уже существует либо
что тест декоративен. Mutation-gate обязателен только для явно названного
высокорискового инварианта, а не для каждой строки. Comment-only, docs-only и
permission-only изменения не требуют искусственного RED или полного test run.

Полный протокол классификации flake живёт только в `tdd-enforce`. Нагрузочный прогон не
повторять до случайной зелени: неверное присутствующее значение остаётся реальным
contract failure, а resource-ветка допускает только один диагностический repeat и один
повтор исходного gate. Для focused/related/full всегда фиксировать число файлов и тестов;
нулевой related-набор product-кандидата — FAIL/непроверено.

Удаление доказанного dead code допускается без искусственного RED-теста, но требует доказательства отсутствия production-consumers и полного регрессионного прогона.

### 2. Один scope и один трекер

- Текущая работа существует только в `CURRENT_TASK.md`.
- Баги существуют только в `BUGS.md`.
- Незавершённые улучшения и техдолг существуют только в `docs/BACKLOG.md`.
- Не создавать `*_TODO`, `*_REPORT`, `MASTER_*`, временные спеки и параллельные журналы.
- Не исправлять соседний дефект «заодно»; записать его и продолжить текущий scope.
- Побочная находка: подтверждённый дефект → `BUGS.md`, улучшение/долг →
  `docs/BACKLOG.md`. Planner записывает её в ближайшей точке синхронизации — acceptance,
  blocker или rejection пакета, — чтобы она не осталась только в чате. Не создавать
  скрытый TODO и не заводить второй tracker.

### 3. Сохранять пользовательские изменения

Worktree может быть грязным. Перед правкой уже изменённого файла сначала отделить
существующий diff от своего будущего изменения. Не использовать `git reset --hard`,
`git checkout --`, широкие `git add .`, `clean`, stash или массовое переформатирование
без явного запроса. Никогда не восстанавливать целый файл из HEAD или другого snapshot,
чтобы отменить локальный edit: сначала прочитать текущий diff и откатить только свои
hunks точным обратным patch. Перед удалением проверить абсолютный путь, ссылки и
Git-статус.

Stage/commit делать только после явного разрешения и по точному manifest/pathspec.
Если package-hunks и чужие hunks находятся в одном файле, file-level pathspec недостаточен:
до stage либо получить явное включение всего файла, либо подготовить и проверить точный
hunk-level patch для index. Перед checkpoint сверить staged diff с manifest/digest,
убедиться, что исключённые hunks остались вне index, и отдельно перечислить исключения.
Перед двухкодерным запуском и checkpoint сверить `git worktree list`; принятая работа
не должна оставаться только во вторичном worktree. Worktree не удалять автоматически:
clean/integrated — только после разрешения, dirty/untracked — STOP и отчёт.

### 4. Честная проверка

В отчёте разделять:

- доказано тестами;
- доказано build;
- проверено в браузере;
- не проверено или только выведено косвенно.

Не объявлять широкий результат по узкому тесту. Флейк фиксировать по имени файла и повторному изолированному прогону.

В отчёте отдельно называть: тесты, build, браузер, benchmark и выводы по косвенным
данным. Benchmark обязан измерять реальный production-path, прогревать измеряемый
worker, чередовать варианты и сохранять контроль шума; экстраполяцию не выдавать за
замер. Любое число benchmark/telemetry/counter/RSS/cancellation/digest становится
evidence только после негативного контроля инструмента по правилам `tdd-enforce`.

### 5. Размер файлов

- `.jsx`: soft 30 KiB, hard 40 KiB.
- `.js`: soft 20 KiB, hard 25 KiB.
- словари/локали/данные не лимитируются.

Hard-превышение не требует механической декомпозиции стабильного файла. Декомпозиция обязательна, если файл уже в Active backlog, быстро растёт или изменение одной функции ломает несвязанную область. Размеры и новые нарушители указывать в финальном отчёте.

### 6. Документы не являются журналами

- `PROJECT_STATE.md` — один текущий snapshot.
- `DECISIONS.md` — только действующие решения.
- `CHANGELOG.md` — короткие релизные итоги.
- Реализованные планы удаляются; история остаётся в Git/checkpoint.
- В корне `docs/` — не более 8 канонических Markdown-файлов.
- `CURRENT_TASK.md` — не более 200 строк; при росте его сжимают до текущего состояния,
  а реальные дефекты/долг переносят только в `BUGS.md`/`docs/BACKLOG.md`, без архива.
- Implementation coder не ведёт журнал в `CURRENT_TASK.md`: он возвращает компактный
  candidate handoff. Planner обновляет trackers после приёмки; подтверждённые
  находки при blocker/rejection фиксирует в тот же момент, не дожидаясь acceptance.

## Биологические инварианты

### Аннотации

- Единственная модель: `annotations[]`.
- Уровни: `region`, `detail`, `point`.
- Не создавать параллельные `domains[]`, `features2[]` или локальные несовместимые схемы.
- Перед правкой парсеров/редакторов читать skill `annotation-contract`.

### Сборка

- `Part` — библиотечная сущность; `Fragment/Piece` — её использование в сборке; `Junction` — химия соединения.
- Мутация исходника создаёт вариант, а не переписывает родителя молча.
- Праймеры сохраняются и версионируются; изменение canvas не очищает их автоматически.
- Биологически невозможная операция не маскируется удобным UI.
- Перед правкой assembly/primer/enzyme-логики читать `bio-invariants` и `assembly-methods-ref`.

### Ферменты

- `GG_ENZYMES` (`golden-gate.js`) — только Type IIS / Golden Gate.
- `RE_ENZYMES` (`restriction-db.js`) — классические рестриктазы / RE-клонирование.
- Каталоги, методы и результаты не смешивать.

### Поиск и вычисления

- Явный биологический фильтр работает fail-closed: ошибка провайдера не равна «совпадений нет».
- Частичный результат явно помечается и не выбирается как подтверждённый.
- Идентичность сущности kind-qualified (`kind:id`).
- Тяжёлые вычисления идут вне UI-потока с отменой, stale-drop и ограничением параллелизма.

## Производительность: слабый компьютер — базовая платформа

Эталон: Windows 10/11, 2 физических ядра / 4 потока, 8 GB RAM, интегрированная графика.

- Базовые функции не зависят от интернета или GPU.
- Нельзя молча снижать биологическую точность ради скорости.
- UI p95 реакции/отмены: <100 ms; обычный long task: <50 ms.
- Частичный metadata-search: <100 ms.
- Точный поиск по 1 Mb DNA после готовности индекса: <1 s.
- Библиотека 10 Mb: цель <250 MB RAM, stress ceiling <500 MB.
- Сначала профилирование, индексы, кэш, инкрементальный пересчёт и компактные typed arrays; Rust/WASM — только для измеренного hot kernel с ≥2× end-to-end выигрышем, ≤1.25× памяти, JS fallback и differential-тестами.

## Архитектурная карта

```text
gui/designer/
  src/App.jsx             root wiring; состояние — в store
  src/store/              Zustand slices
  src/components/         React workspaces и UI
  src/lib/                алгоритмы, адаптеры, форматы, поиск
  src/workers/            тяжёлые вычисления
  src/__tests__/          Vitest integration/contract tests
gui/api/server.py         FastAPI/SnapGene bridge
src/pvcs/                 Python CLI и библиотека
tests/                    pytest
docs/                     архитектура, дизайн, гайды, активные specs
```

Полная актуальная схема — `docs/ARCHITECTURE.md`; точки входа — `docs/COMPONENT_MAP.md`.

## Кодовые правила

- Не добавлять локальный `useState` в `App.jsx`; состояние приложения — в store или доменном hook/controller.
- Не добавлять ручной `useMemo`/`useCallback` без измеренной причины; проект использует React Compiler.
- UI-строки — через i18n; цвета/spacing/shadows/icons — через design tokens и `Icon`.
- Не использовать `outline:none` без равноценного focus-visible состояния.
- Портал не изолирует React events: модал над SequenceView обязан блокировать родительские hotkeys.
- Не писать скрытые TODO в коде.
- Для поиска файлов сначала `rg` / `rg --files`.
- На Windows объединять проверки в минимум процессов, не опрашивать WMI/CIM и не
  запускать несколько тяжёлых прогонов одновременно. Для Vitest по умолчанию
  `--maxWorkers=4`, если конкретный тест не требует одного worker.

## Graphify

Не использовать Graphify автоматически для обычного ревью, точечной навигации или ответа по текущему коду. Запускать его только по явному запросу пользователя либо когда без графового анализа действительно нельзя надёжно установить сложные межмодульные связи. Если граф давно не обновлялся или не соответствует текущему HEAD/dirty worktree, не обновлять его самовольно и не опираться на него — читать живой код и актуальные документы.

`.graphify/` — локальный воспроизводимый индекс, не источник истины. Перед использованием
проверить, что `branch.json` и граф соответствуют текущим branch/HEAD; флаг
`stale:false` сам по себе недостаточен. Для точечного вопроса предпочитать живой код;
если Graphify уже разрешён, использовать `query`, а для изменённых файлов —
`review-delta`. Перестраивать граф только после отдельного явного разрешения.
Runtime/cache-файлы Graphify не коммитить.
