# ACCEPTANCE_ALGORITHM.md — алгоритм визуальной приёмки спринта

> Процедурный документ. Не спека и не техдолг — под лимит «8 активных файлов в `docs/`» не попадает.
> Источник: `CHAT_PLAYBOOK_CORE.md` §1 + `CHAT_PLAYBOOK_APPENDIX.md` §7. Здесь развёрнута пошаговая процедура, в playbook'е — только ссылка сюда.
> Читать Chat'у в каждой сессии-приёмке, сразу после стартового пакета (`CLAUDE.md` / `BUGS.md` / `CURRENT_TASK.md` / `PROJECT_STATE.md` snapshot / `DECISIONS.md` sprint-level).

---

## 0. Pre-check — до первого скриншота

1. Прочитать: `CLAUDE.md`, `BUGS.md` (секция OPEN), `CURRENT_TASK.md`, `PROJECT_STATE.md` snapshot, `DECISIONS.md` sprint-level, активную спеку текущего спринта в `docs/`. Если спринт — первый патч версии (M-X.0 → M-X.1+) или обращается к предыдущему версионному блоку — дочитать соответствующий блок `RELEASES.md`.
2. Извлечь из спеки явный acceptance-чеклист — визуальные утверждения, которые должны быть истинны после спринта. Держать в рабочем буфере 5–15 пунктов.
3. Найти отчёт Code в конце `CURRENT_TASK.md`: коммит-хэши, счётчики тестов (Vitest + pytest), build status, блок «отклонения от спеки». Отчёта нет — стоп, прошу Игоря донести отчёт перед приёмкой.
4. Зафиксировать, какой блок приёмки идёт сейчас (Блок 1 / 2 / …). Проверяем только пункты чеклиста, относящиеся к нему. Остальное — не в этой сессии.

Если контекст-use после шагов 1–3 уже ≥40% — прошу compact до первого скриншота.

---

## 1. Цикл по каждому скриншоту

Три шага в одном ответе, без перескока:

**a. Что вижу.** Одно предложение-описание ровно того, что на картинке. Без интерпретаций. Цель — поймать себя, если додумываю несуществующие элементы.

**b. Что должно быть.** Выписываю из acceptance-чеклиста только те пункты, которые этим скриншотом проверяются.

**c. Вердикт по каждому пункту:** PASS / FAIL / UNSURE.

- **PASS** — критерий явно выполнен на картинке.
- **FAIL** — критерий явно нарушен.
- **UNSURE** — на картинке не видно (ракурс, скролл, состояние). Запрашиваю конкретный дополнительный скриншот: «покажи FragmentEditor с открытой панелью Y после клика на Z». Не компенсирую чтением кода — это смешает приёмку с код-ревью.

Если FAIL — сразу в рабочий буфер: `[критерий] — ожидалось X, видно Y, скриншот N`. Без объяснения причины. Объяснение — после всех скриншотов.

---

## 2. После всех скриншотов — решение

Свожу три таблички:

- Визуальные PASS / FAIL / UNSURE по acceptance-критериям.
- Невизуальные пункты (счётчики тестов, build status) — по отчёту Code.
- Отклонения Code от спеки — явно по его блоку «отклонения».

### Ветка PASS

Полная визуальная приёмка прошла И отчёт Code чист И невизуальные пункты OK.

Действия Chat:

1. Новый версионный блок в `RELEASES.md` (с bump версии если milestone) или дополнение текущего (documentation milestone): что принято, коммит-диапазон, тесты, build, закрытые/открытые TD, DEC-блок, post-mortem (при ≥2 итерациях FAIL→fix).
2. Обновить `PROJECT_STATE.md` snapshot: версия в шапке, тесты, раздел «Что работает» (если появился новый функционал), «Что дальше» (актуализация candidate списка).
3. Bump версии в коде: `gui/designer/package.json` + `gui/designer/src/lib/version.js` — если milestone-bump и Code ещё не поднял (Type C handoff Code).
4. Баги из BUGS.md OPEN, которые закрылись этим спринтом — в FIXED с датой и коммитом.
5. Ротация по §4 `CHAT_PLAYBOOK_APPENDIX.md`: старые FIXED → `docs/archive/BUGS_HISTORY.md`; старые sprint-level DEC из `DECISIONS.md` (старше 2 спринтов) → `docs/archive/DECISIONS_YYYY_QN.md`; `RELEASES.md` при достижении 30 KB / 10 версий → `docs/archive/RELEASES_YYYY_QN.md`; реализованная спека → `docs/archive/` со штампом `**Статус:** ✅ РЕАЛИЗОВАНО [дата]`. Якоря в `ANCHORS.md` не переезжают никогда.
6. `CURRENT_TASK.md` — очистить до заглушки («спринт закрыт, следующая задача не определена»).
7. Новые решения из спеки: sprint-level → `DECISIONS.md` (DEC-XX-NN); фундаментальные ⚓ → `ANCHORS.md`.

После этого — compact перед следующей задачей. Не начинаю новый спринт в той же сессии.

### Ветка FAIL

Хотя бы один критерий FAIL либо Code отметил отклонение, которое я не готов принять.

Действия Chat:

1. Никаких правок в `PROJECT_STATE.md` / `RELEASES.md` / `BUGS.md` / `DECISIONS.md` / `ANCHORS.md`. Спринт не закрыт.
2. В `CURRENT_TASK.md` — мини-спека правок: список FAIL-пунктов; для каждого `БЫЛО / СТАЛО` или правило замены; чеклист чего должно стать после фикса; STOP-условие.
3. Handoff Code одной фразой: «Прочитай CURRENT_TASK.md, доделай FAIL-пункты N/M/K, не трогай PROJECT_STATE/BUGS/DECISIONS, после последнего коммита остановись».
4. Следующая сессия — снова визуальная приёмка, с нуля по §0. Не продолжать в текущей.

### Ветка UNSURE

Если после дополнительных скриншотов остаётся хотя бы один UNSURE — относиться к нему как FAIL до прояснения. Лучше лишний круг приёмки, чем тихо пропущенный дефект.

---

## 3. STOP-условия сессии приёмки

Сессия заканчивается в одном из трёх моментов, дальше не иду:

- PASS-ветка выполнена до конца, изменения записаны в файлы. Compact перед следующей задачей.
- FAIL-ветка: мини-спека написана, handoff сформулирован. Не начинаю «заодно» следующий спринт.
- Нарушены предпосылки (нет отчёта Code, нет активной спеки в `docs/`, стартовые файлы не в ожидаемом виде). Говорю Игорю конкретно «ожидал X, вижу Y», прошу донести или поправить — в следующую сессию.

---

## 4. Антипаттерны приёмки

- **Додумывать за скриншот.** Видно — PASS/FAIL; не видно — UNSURE и запрос второго скриншота.
- **Лезть в код, чтобы «подтвердить визуал».** Код-ревью — отдельная активность. В приёмке читаю код только когда FAIL и нужен точный адрес правки для мини-спеки в `CURRENT_TASK.md`.
- **Объединять в одну сессию приёмку Блока 1 и Блока 2.** Каждый блок — свой цикл §1. Финализация — когда все блоки спринта прошли PASS.
- **Финализировать при UNSURE-пунктах** «потому что наверное работает».
- **Делать ротацию архива в FAIL-ветке.** Ротация — только после полного PASS.
