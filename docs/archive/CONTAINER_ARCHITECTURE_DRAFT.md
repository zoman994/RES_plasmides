## TL;DR

Контейнер — виртуальный «операционный стол» для одной молекулы, с накапливаемой историей операций над ней. Канвас становится графом контейнеров и операций между ними; Construct view и Project Flow унифицируются на одной data-модели с авто-выбором layout (линейный / DAG). Существующие сущности `Fragment` и `Junction` схлопываются в Container и в свойство стыка. Совместимость с `.dna` / `.gb` сохраняется — конечная плазмида экспортируется в стандартный формат с метаданными provenance в qualifiers.

## Концепт

### Что такое контейнер

**Контейнер** — единица канваса. Внутри контейнера ровно одна **активная молекула** (linear или circular ДНК). Контейнер несёт:

- Активную молекулу (sequence + annotations).
- Историю операций над содержимым (Plasmid-Git baseSnapshot + commits[] + операционный лог поверх).
- Концы (5′/3′ для linear; отсутствуют для circular) — выходные коннекторы наружу.

«Виртуальный операционный стол», не «пробирка». В реальной пробирке после digest физически живёт смесь продуктов; в контейнере остаётся только тот продукт, с которым продолжается работа. Второй продукт уходит **в лог операции** и **в протокол как очистка**, но не существует как отдельная сущность канваса. Это сознательное упрощение: метафора стабильна на всех операциях.

### Что такое операция

Операция — переход состояния контейнера. Категории:

- **Молекулярные** (мутации, расширяющие Plasmid-Git): substitution, insertion, deletion, codon edit.
- **Структурные** (меняют топологию или концы): linearize via digest, circularize, fragment extraction.
- **Соединительные** (между двумя контейнерами): ligation, Gibson, Golden Gate, KLD, overlap PCR.

Соединительная операция — ребро между двумя (или N) контейнерами в графе. Тип реакции — производное от пары `(endA, endB)` + reaction class. Текущая сущность `Junction` схлопывается в свойство стыка с descriptor'ом совместимости концов.

### Что такое граф

Граф контейнеров и операций между ними. Каждый узел — контейнер; каждое ребро — операция. Может быть линейным (одна сборка одной плазмиды), может быть DAG (несколько сборок, общие backbone'ы, ответвления).

UI делает авто-выбор layout по форме графа: подграф, который укладывается в цепочку → линейный layout (текущий Construct view); подграф с ветвлениями → DAG layout (текущий Project Flow). Биолог не выбирает «я в Construct или во Flow» — работает с графом, layout сам подстраивается. Construct + Flow унифицируются.

## Что не ломается

### Совместимость форматов

`.dna`, `.gb`, `.gbk`, `.fasta` — на входе и выходе. Внутри контейнерная модель, на экспорте — конечная плазмида с **метаданными provenance в qualifiers** (`COMMENT` блок или `/note` поля).

```
COMMENT     BodgeGene provenance:
            origin: pUC19 (catalog)
            ops: digest_EcoRI_BamHI -> linear_backbone
            ops: ligation_with_EGFP_CDS_from_pET28-EGFP
            ops: mutagenesis_Q45R
            generated: 2026-04-27 BodgeGene v0.6.0-alpha
```

`.gb` парсеры конкурентов (SnapGene / Benchling / Geneious / ApE) **игнорируют** незнакомые qualifiers — обычная плазмида в их инструментах. **BodgeGene-парсер** этих файлов восстанавливает граф операций и показывает полный provenance. **Zero-cost interop с upside для BodgeGene-экосистемы.**

### Конкуренты

SnapGene / Benchling / Geneious стартовали как single-molecule editors (SnapGene 2010, библиотеки появились только к 4-й версии в 2017; Gibson вышел 2009, Golden Gate 2008–2011). Multi-fragment assembly у них — extension over single-molecule core. Junction в их моделях такой же костыль, как у нас сейчас.

Контейнерная модель **в которой первичен граф операций над контейнерами, а молекула — содержимое узла графа** — это инверсия. У них молекула первична, граф вторичен. У нас будет наоборот.

Они не могут к этому переехать без переписывания ядра — десять лет проектов миллионов биологов хранится в old-model. **Greenfield-проект может стартовать сразу с правильной модели.** Появление позже даёт structural advantage, а не отставание.

### Migration `.bodgegene` файлов

`.bodgegene` сейчас хранит `fragments[]` + `junctions[]`. Migration:

- Каждый `Fragment` → `Container` с одной молекулой (`baseSnapshot = fragment.sequence`, `commits[] = fragment.commits[]` если был Plasmid-Git, иначе пусто).
- Каждый `Junction` → ребро между контейнерами с `reactionClass` из старого `junction.type`.
- Schema bump v_N → v_N+1, миграция один раз при первой загрузке.

Без потери данных, без интерпретационных решений. Тривиальная.

## Унификация операций «где + что + откуда»

Дополнено 27.04.2026 после уточнения Игорем: «открываем контейнер, ставим курсор на 789-й нуклеотид, говорим — сюда вставить через Gibson фрагмент из контейнера 2».

Контейнерная модель унифицирует **большое семейство текущих UI-задач** в один паттерн `(где: позиция-в-активном-контейнере) + (что: операция и параметры) + (откуда: source-контейнер если применимо)`:

| Текущий wizard / spec | Что унифицируется в контейнерной модели |
|---|---|
| **V7 INSERTION-CLOCK** (открытый High в BUGS.md, дизайн на InsertionClock-компонент с mini-clock + full-modal + draggable cursor + sequence-view ±50 nt) | Не нужен. Курсор в активном контейнере + context-action «Gibson вставка из X» |
| **Restriction Cloning Wizard** (3-step: ферменты → insert → preview) | Курсор не нужен (RE site задаёт позицию). Click 2 RE site → context-action «вырезать и заменить содержимым X» |
| **Mutagenesis Wizard** (KLD / QuikChange / OE) | Курсор → context-action «substitution / insertion / deletion». Уже частично работает через FragmentEditor mode switcher после Sprint 1.7 — переезжает естественно |
| **Tag insertion** (3xFLAG / 6xHis / SignalP) — сейчас отсутствует как workflow | Курсор на N/C terminus CDS → context-action «вставить tag из палитры» |
| **Deletion** диапазона | Курсор от-до → context-action «удалить» |
| **Replace element** в PlasmidUseWizard | Click на region → context-action «заменить содержимым X» |

Всё это становится **одним паттерном UI** с одним и тем же жестом. V7 как отдельный компонент в контейнерной модели не нужен — его место занимает sequence-cursor + context-menu. Один универсальный компонент закрывает 5–10 текущих use-cases.

### Спецификация операции достаточна для auto-protocol

«Позиция курсора + контейнер-источник» — **достаточная спецификация** для генерации primer design + protocol step. Биолог не пишет `forward primer 5′-...-3′` руками — указывает **намерение** («вставить это сюда»), primer design и protocol — производные.

Это переворачивает текущую модель проекта: сейчас primer design — central feature (`local-primer-design.js`, `tm-calculator.js`, OligoManager). В контейнерной модели primer design становится **invisible infrastructure** — рассчитывается автоматически в момент записи операции, биолог видит результат в протоколе, ручной режим как опция (для edge-cases с trickiness).

Это ещё одна редукция концепций: «primer как первоклассная сущность UI» → «primer как auto-derived deliverable операции». ActionBar после расчёта праймеров (sticky панель: протокол, заказ олигов, GenBank, завершить сборку) сохраняется, но кнопка «расчёт праймеров» исчезает — праймеры всегда уже посчитаны как побочный эффект последней операции.

## Открытые вопросы (для kickoff-интервью)

1. **Construct + Flow: полная унификация или один UI с двумя layout-режимами?**
   Решение Игоря 27.04.2026: «скорее унифицируем». Уточнить в kickoff: один URL/route с авто-выбором layout, или два route'а на одной модели? UX-дизайн перехода между линейным и DAG представлением (анимация, или snap, или explicit toggle).

2. **`Part` semantic в библиотеке.**
   Решение черновое: Part = шаблон молекулы (содержимое будущего контейнера). Drag из палитры → создаётся новый Container с этой молекулой внутри + пустой историей. Уточнить: что с ныне существующими 94 parts'ами? Migration тривиальна (Part остаётся Part), но переименования внутренних полей возможны.

3. **Форма экспорта provenance в `.gb` qualifiers.**
   Структурированный формат (свой mini-DSL в `COMMENT` блоке) или JSON-стиль в `/note`? Trade-off: структурированный — машинно-читаемый при ре-импорте, человеко-читаемый в SnapGene/Benchling. JSON — машинно-читаемый идеально, но в чужих парсерах будет шумом.

4. **Уровень детализации операционного лога.**
   Каждая UI-операция → отдельная запись истории, или batch'и (как `applyMutationsBatch` в Plasmid-Git)? Sprint X cycle решил batch для мутаций, но для соединительных операций batch'и могут быть менее уместны (одна digest-операция = один логический шаг).

5. **Что показывает контейнер на канвасе.**
   Mini-map molecule (как сейчас PartBlock с regions)? Имя + длина + bp count + topology icon? Custom иконка по типу содержимого (linear / circular / fragment / mixed)? Это UX-вопрос, решается в prototype-first фазе.

6. **Ребро операции в графе: что именно показывает?**
   Reaction class (badge + цвет)? Концы стыка (sticky XbaI / blunt)? Auto-generated primer summary (если соединительная операция требует PCR)? Уровень информации на ребре — UX trade-off читабельности.

7. **Соединительные операции на >2 контейнерах (multi-fragment Gibson, GG с N фрагментами).**
   Одно ребро hyperedge (несколько узлов одновременно), или цепочка попарных рёбер? Биологически это одна реакция, графически hyperedge нестандарт.

8. **Связь с auto-protocol.**
   Протокол = traversal графа контейнеров с print их операций. Уточнить: traversal в каком порядке (топологическая сортировка от leaves к root? в обратном направлении?). Группировка операций (всё что касается одного контейнера → один шаг протокола, или каждая операция → шаг?).

## Стоимость / риски / горизонт

### Стоимость (с учётом упрощений после уточнений Игоря)

- 2 крупных спринта на data-model + базовый рендер + migration. Не 4–6 как изначально оценивал — обновлено после уточнения «контейнер = одна активная молекула, виртуальный стол».
- Plus 1–2 спринта на полную унификацию Construct + Flow и переезд всех существующих модалок / визардов на контейнерные действия.
- Реалистично 4–6 итераций FAIL-fix через все спринты; pet-проект, не критично.

### Риски

1. **Migration .bodgegene files.** Тривиально по структуре, нетривиально на edge-cases (старые проекты с custom junction'ами). Митигация: schema bump + один раз при первой загрузке + extensive regression-тестирование.
2. **UI переходный период.** Текущие модалки и визарды живут параллельно с контейнерной моделью пока не закроется полный переезд. Митигация: разделить на спринты по типу UI-сущностей; не пытаться всё одновременно.
3. **Concept fatigue для биологов в `userMemories`/документации.** Игорь работает в контейнерной модели, новые сотрудники проекта обучаются на этой модели. Митигация: прокидывание UX_VISION + DECISIONS как обязательного pre-read.
4. **Auto-protocol может разочаровать в первой итерации.** Provenance-граф автоматизирует часть протокола, но не всю (биолог часто корректирует протокол под свои реактивы / instruments). Митигация: позиционировать auto-protocol как draft, не final; биолог редактирует. Это ничего не ломает.

### Что выигрывает проект

- **Data model**, которая радикально чище конкурентов и даёт BodgeGene structural advantage.
- **Auto-protocol** падает естественным побочным эффектом, не требует отдельного крупного спринта.
- **Provenance** становится первоклассным свойством плазмиды, не feature.
- **Novel contribution для статьи Bioinformatics/JOSS:** «format-compatible cloning tool with novel container/graph data model enabling verifiable provenance». Это уже не «ещё один редактор», а **publishable architectural idea**.
- **Унификация Construct + Flow:** меньше UI-кода, меньше тестов, меньше документации.
- **6 методов сборки** становятся единой системой через `(endA, endB) + reactionClass` — меньше ручного выбора method'а биологом, больше автоматической валидации.

### Горизонт

- **Сроки не критичны** (pet-проект, Игорь 27.04.2026).
- **Совместимость с .gb / .dna сохраняется** — экспорт в standard формат продолжает работать; `.bodgegene` migration тривиальна. Это снимает главный риск перехода для коммерческих продуктов.
- **Публикация на контейнерной модели** даёт статье novel architectural contribution, не feature comparison.
