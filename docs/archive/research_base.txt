# RESEARCH_AND_ARCHITECTURE.md

*BodgeGene / PlasmidVCS — исследование жизнеспособности и углубление архитектуры**Project + Container + DAG + first-class Primer-pool**.*
*Дата: 28 апреля 2026. Статус: research draft, готовый к доработке `ARCHITECTURE_PROJECT_MODEL.md` в следующей сессии (N+3).*

---

## 0. TL;DR

**Главная находка.** Архитектурное ядро BodgeGene — DAG операций над контейнерами с PROV-O-совместимой семантикой — **существует у конкурентов только частично и нигде не интегрировано целиком**. Benchling реализует entity-lineage DAG (parent/child + per-construct assembly history), но это закрытая SaaS, провенанс не сериализуется в файл. SnapGene имеет внутренние блоки `history tree` (тип 7) и `history node` (тип 11) в .dna-формате — но они **не декодированы публично, не экспортируются и недоступны через API**. pydna моделирует assembly как NetworkX MultiDiGraph внутри одного шага, но глобальной DAG-истории операций нет. SBOL3 даёт стандартный язык (PROV-O) для всего, что мы хотим описать, но в практике используется узким академическим сообществом и **не читается ни SnapGene, ни Benchling**. Никто не делает lazy-init lineage. Никто не делает hybrid primer pool с явным `origin`-enum.

**Что это значит для позиционирования.** Часть USP, которую формулировал PROJECT_MODEL_KICKOFF — *primer reuse через container lineage* — **частично закрыта Benchling Inventory/Bioregistry** (oligo как first-class registry-entity с back-reference). Продавать это as-is **нечестно**. Нужно переформулировать позиционирование на три действительных зазора: (1) **открытый локальный файл** без облака и vendor lock-in, (2) **commit-lineage / graph-of-operations** в файле как побочный эффект каждой операции (Benchling этого не делает; SnapGene делает в закрытом виде), (3) **structured `origin` enum + hybrid project-local/global pool с frozen lineage при clone-on-import** — это не делает никто.

**Что это значит для архитектуры.** Принять PROV-O как **vocabulary** (`Entity` ≡ MoleculeContainer, `Activity` ≡ AssemblyContainer, `used`/`wasGeneratedBy`/`wasDerivedFrom`/`hadPlan`/`agent`), но **сериализовать как plain JSON** (не RDF). Использовать **Dexie.js** как persistence слой; событийная (event-sourcing) архитектура `commits[]` остаётся, добавляется content-addressable hash (SHA-256 от canonical JSON) для frozen snapshots. `.bdg` — **ZIP-контейнер в стиле RO-Crate** (manifest + per-container .gb + dag.json + renders); GenBank-export для каждой молекулы внутри + структурированный COMMENT-блок `##BodgeGene-Provenance-START##…##END##` с base64-JSON провенансом. Hyperedge для multi-fragment assembly (один Activity-узел с N inputs) — стандарт SBOL/PROV/Benchling/Nextflow, ApE и SnapGene делают так же.

**Что критично НЕ делать.** Не тащить SBOL3 как нативный формат (overhead RDF + никто не читает кроме SynBioHub). Не делать CRDT — single-user, искусственно для биологических операций. Не пытаться декодировать SnapGene history blocks (закрытый формат, ничтожный ROI). Не пытаться merge как в Git — биология не имеет 3-way merge. Не реализовывать Project Flow main-editor как drag-drop graph (для wet-lab пользователей это плохой UX); DAG-canvas — **только для read-only визуализации**, императивные диалоги — для создания операций.

**Roadmap.** v0.6 = Persistence migration на IndexedDB+Dexie + Project/Container/Edge data restructure без UI-изменений (адаптерный слой). v0.7 = Library overlay + Primer-pool с back-references. v0.8 = DAG-canvas (read-only через React Flow + dagre) + унификация Construct/Flow. v1.0 = Bioinformatics Application Note submission (~2500 слов) + JOSS submission параллельно.

## 1. Жизнеспособность подхода

### 1.1 Конкурентный landscape

Разделим на четыре группы и зафиксируем, что именно каждый делает с провенансом, primers и assembly.

**Plasmid editors (single-molecule centric).**

*SnapGene* — закрытый бинарный `.dna`. Reverse-engineering (Edinburgh-Genome-Foundry/SnapGeneReader, Biopython `Bio.SeqIO.SnapGeneIO`, autosnapgene Кале Кундерта) показывает, что в формате присутствуют **отдельные блок-типы 7 ("history tree") и 11 ("history node")** — то есть SnapGene хранит in-file историю, выходящую за рамки undo-stack. Однако **парсеры эти блоки игнорируют**: схема непубличная. Главное практическое следствие: **при экспорте в любой не-`.dna` формат провенанс полностью теряется**. Primers — first-class блок (тип 5), но **per-file**, без cross-file pool. Multi-fragment assembly — атомарный output (.dna плазмида); intermediate fragments видны только внутри opaque history-блока. Issue Biopython #4217 даже фиксирует, что primer-блок и feature-блок дублируются и не reconciled парсером.

*Benchling* — самый продвинутый по data-modeling из коммерческих. Реальная архитектура: Postgres + JSONB для schema-fields (миграция с EAV в 2024, см. их engineering blog), Elasticsearch для поиска, Data Warehouse для аналитики. Ключевые сущности: **DNA Sequence, DNA Oligo (separate from sequence!), AA Sequence, Custom Entity, Schema, Feature Library, Mixture/Plate/Container/Box/Location**. Provenance — три слоя: (a) per-sequence versions (snapshot при modify), (b) per-construct **Assembly History** ("Benchling stores how that construct was assembled" — см. `help.benchling.com/hc/en-us/articles/39922419457165`; есть API-доступ через History panel и Assembly tab), (c) registry-wide **Entity Lineage** через parent-link fields с "Enforce Lineage" rules. Combinatorial Cloning поддерживает до 15 fragments per assembly — Gibson, Golden Gate, Gateway, In-Fusion, Concatenation; output — один новый construct entity + опционально новые primer-entities + amplicons. **Это полноценный DAG entity-lineage**, но (i) provenance lost on .gb/.dna export, (ii) DAG read-only через UI/API, нет file-формата для шаринга, (iii) cloud-only, $$$, vendor lock-in.

*Geneious Prime* — local Java-бэкенд (или SQL-server). Каждый document имеет URN (stable cross-doc reference). **Cloning DAG как концепция отсутствует** ("lineage" в Geneious — phylogenetic, не cloning). Multi-fragment assembly даёт один output document без формальной input-edge структуры. Primers — отдельные documents в folders, reuse через shared folder, **не registry-style**.

*ApE (Wayne Davis)* — open-source Tcl/Tk. По сути GenBank-superset с `COMMENT ApEinfo:` строками и `/ApEinfo_*` qualifier-extensions (опционально strip on save). Provenance частично есть: при Golden Gate Assembly в `COMMENT` пишется список input-файлов как free-text (Davis & Jorgensen 2022, PMC9580900). Это не структурированный граф, а текстовый breadcrumb. **Per-session linear undo, in-file history отсутствует.** Primers — общая tab-delimited Features library, scan-on-view.

*VectorBuilder* — template+catalog подход; не plasmid editor в нашем смысле, а конфигуратор для коммерческого синтеза. Internal data model **не публикуется**. Primers скрыты от пользователя. Final output — `.gb` плазмиды.

**Synthetic biology DSL / data exchange.**

*SBOL3* — RDF-graph based стандарт. Импортирует **W3C PROV-O wholesale** (Section A.1 спецификации). Каждый `Identified` объект — `prov:Entity`; `prov:Activity` для операций; `wasGeneratedBy`, `wasDerivedFrom`, `qualifiedAssociation` (с `Plan`/`Agent`/role) для рёбер. Семантически **это ровно та модель, которую мы строим**. Но реальная adoption узка: SynBioHub, JBEI/ICE (loosely), Cello, iBioSim, SBOL-Designer, j5, BOOST, iGEM Registry — академический DBTL-CAD кластер. Benchling и SnapGene **не читают SBOL** (был GSoC проект 2021 для SnapGene↔SBOL3 моста, что само по себе подтверждает отсутствие нативной поддержки). Mante et al. (2019, *Synthetic Biology* journal) прямо пишут: "We do not believe biologists would be able to create the required custom annotations in SBOL". SynBio2Easy (2022) — целая статья о том, что SBOL-tooling требует bridge-инструмент, чтобы быть usable.

*GenBank/EMBL flat file* — INSDC стандарт. **CONTIG/AGP** описывают sequencing-assembly provenance, но не cloning. Никакого слота для "this plasmid was made by Gibson of these three records using these primers" в стандартных полях. Tools хранят это либо проприетарно (SnapGene blocks 7/11), либо в COMMENT (ApE), либо в облаке (Benchling). NCBI Structured Comments (`##Tag-START##…##END##`) — **blessed extension point**: поддерживается всеми парсерами без поломки, валидаторы пропускают незнакомые префиксы. Это наш канал.

**Open-source инструменты.**

*JBEI ICE* — registry, не editor. Java/Spring, ~38⭐. Иерархия: Folder → Entry (Plasmid/Strain/Part/Seed) → Sequence → SequenceFeature → AnnotationLocation. У Sequence есть `fwdHash`/`revHash` (sha1) для dedup. **DAG операций отсутствует**; есть Audit (event-log) + Experiment (плоская ссылка на external URL). Permission model на Account/Group уровне детализирована — заимствуем как pattern.

*pydna* (~209⭐, BMC Bioinformatics 2015) — **самая важная open-source референция**. Subclass-полиморфизм Dseqrecord: `Amplicon(Dseqrecord)` помнит `forward_primer/reverse_primer/template`, `Contig(Dseqrecord)` помнит `source_fragments`. **Внутри одной Assembly — буквально NetworkX MultiDiGraph**: nodes = overlap-регионы между фрагментами, edges = сами фрагменты (Dseqrecord на edge-атрибуте), sentinel nodes `5'`/`3'` для linear products. `assemble_linear` = поиск всех путей `5→3`, `assemble_circular` = поиск циклов. Env var `pydna_assembly_limit` (10s default) против взрыва enumeration. **Глобальной DAG операций нет** — provenance только локальная (через subclass parent-refs); скрипт сам = provenance. SEGUID v2 для content-addressed hash (включая circular rotation invariance). Заимствуем три вещи: typed-artifact pattern, MultiDiGraph для homology-overlap внутри Assembly-step, SEGUID v2 для canonical IDs.

*TeselaGen openVectorEditor* — React+Redux компонент editor (deprecated; переехал в `tg-oss/packages/ove`). `sequenceData` — flat plain JS object: `{sequence, circular, features[], parts[], primers[], translations[], cutsites[], orfs[]}`. Features имеют `locations[]` для multi-segment join'ов (важная деталь — pre-feature wrap через начало circular plasmid). VersionHistoryView делегирует storage наружу. Used inside JBEI ICE, Labii, и многих других — фактически industry-standard JS plasmid editor. **Заимствуем именно эту JSON shape для UI-слоя** (наш `sequence: { length, topology, ends, regions[], details[], points[] }` — это уже близко).

*DNA Chisel* (Edinburgh Genome Foundry, Bioinformatics 2020). Constraint+objective модель: `DnaOptimizationProblem` с `constraints[]` (must hold) и `objectives[]` (maximize), `MutationSpace`, `Specification` base class (`AvoidPattern`, `EnforceTranslation`, `CodonOptimize`, …). Provenance — только финальный отчёт (`optimize_with_report → report.zip`). Заимствуем Specification-pattern если когда-нибудь добавим design-rules engine; сама модель не нужна для cloning DAG.

*BioCRNpyler* (Caltech, ~80⭐). Хорошая иллюстрация frozen-after-construction артефакта (`ChemicalReactionNetwork` raises AttributeError при попытке `__setattr__`) — pattern для immutable lineage.

*SBOLDesigner, libSBOLj3, pySBOL3* — рефенс-импл SBOL3, mature, активны. Если когда-нибудь делать SBOL3 export — использовать `pySBOL3` как backend в Python-сервисе или libSBOLj3 как embedded JAR.

*eLabFTW* (~1.2k⭐, AGPL3). Experiment ↔ Item via plain bidirectional links + `#title` autocomplete. **Никакого typed operation graph**: сообщество в issues #3073, #4079, #6743 годами просит DAG-функционал. Discussion #4857 — community fairly explicitly строят quasi-DAG в metadata-полях, что подтверждает: **в OS-мире ELN-уровня DAG ни у кого нет**. ELN consortium format (RO-Crate based JSON-LD) для export — заимствовать как референс packaging.

**Lab notebooks / inventory.**

*Labguru* — Items ↔ Experiments через "Samples" с tab "Experiment And Protocols" (back-reference есть, но generic). *Quartzy* — чистый physical inventory (vendor, lot, location, expiration); никакой связи с sequence на уровне data model. *eLabFTW* — см. выше.

**Подходы из соседних доменов.** Git internals (content-addressable storage, blob/tree/commit/tag, refs как симлинки), IPFS Merkle DAG (CID = hash включая хеши детей; multi-parent для дедупликации), event sourcing (snapshots каждые N events; immutable append-only log; projection в read-model), Nextflow lineage (с релиза 25.04 — каждый task = LID `lid://hash` в `.lineage/`, `nextflow lineage list/view/render/diff` команды — **прямой precedent для нашей CAS-based DAG истории**), Apache Airflow UI (DAG/Grid/Gantt/Detail views — урок про multiple views), React Flow / @xyflow/react + dagre для layout.

### 1.2 Где Project + Container + DAG расходится с конкурентами

Сводная таблица фактических зазоров:

**Действительные зазоры (BodgeGene novel value)**:

1. **Один файл `.bdg` с провенансом как side-effect**, а не feature. Все остальные либо теряют его на экспорте (.gb/.dna), либо хранят в облаке.
2. **Lazy-initialized commits** — контейнер до первой меняющей операции не создаёт `commits[]`, только `baseSnapshot`. Это уникально (никто из исследованных не делает).
3. **`origin` enum как часть data model**: `catalog | paste | file | library_clone | primer_synthesis | assembly_product | split_product`. У Benchling — кастомный schema field, требует admin setup. У всех остальных — нет вообще.
4. **Hybrid primer pool** (project-local + global с явным promotion). Никто из конкурентов не моделирует это явно: либо folder-local (Geneious), либо single-namespace registry (Benchling, ICE), либо per-file (SnapGene). Promotion из project-local в global pool с frozen back-reference — наш паттерн.
5. **Изоморфизм data ↔ протокол** как явный design constraint. У SBOL — близко (PROV Plan), но как стандарт-документ. У нас — рантайм-инвариант для каждой операции в коммите.

**Действительные расхождения (не зазоры, а решения, требующие защиты)**:

- BodgeGene не пытается быть workflow runtime — DAG read-only визуализация, операции создаются императивно (диалоги). Конкуренты-workflow-engines (Nextflow/Airflow) исполняют DAG; мы — фиксируем уже выполненный (ручной wet-lab).
- BodgeGene не делает 3-way merge, в отличие от Git. Биология не имеет соответствующей семантики; разрешение конфликтов = explicit user-driven новая операция.
- BodgeGene не делает CRDT. Single-user dominant, биология не sequence-CRDT-friendly (операции семантические, не позиционные).

### 1.3 Прецеденты graph-of-operations в смежных доменах

**W3C PROV (PROV-O / PROV-DM)** — каноническая модель: Entity, Activity, Agent, плюс qualified-формы (Usage, Generation, Association) для метаданных на рёбрах. PROV-O намеренно format-плюралистичен (Turtle, JSON-LD, RDF/XML, PROV-N). **Это ровно наша модель**. Заимствуем терминологию (`used`, `wasGeneratedBy`, `wasDerivedFrom`, `wasAttributedTo`, `hadPlan`, `startedAtTime`/`endedAtTime`); не заимствуем RDF-сериализацию (overhead для plain-JSON .bdg).

**RO-Crate** (researchobject.org/ro-crate, current 1.1, 1.2 from 2024) — packaging спецификация: директория или ZIP с обязательным `ro-crate-metadata.json` в JSON-LD на schema.org + PROV-O. Используется WorkflowHub, многими генетическими консорциумами (GA4GH-aligned). **Наш `.bdg` может буквально быть RO-Crate**: Root Dataset = проект; per-container `.gb` файлы как `File` entities с `wasGeneratedBy`; `Activity` entities в metadata. FAIR-by-construction без изобретения формата.

**SBOL3 + PROV-O** (см. выше) — каноническая модель в synthetic biology, но узкая adoption. Используем как export target v0.2, через pySBOL3.

**CWL Prov** (commonwl.org) — описывает прогон бы pipeline как RO-Crate + PROV. **Pattern**, не format target. CWL описывает compute pipelines (shell commands), не wet-lab протоколы — semantic mismatch.

**BioCompute Objects (IEEE 2791-2020)** — FDA-supported для regulatory HTS submissions. Семь "доменов" (Provenance/Usability/Description/Execution/Parametric/I-O/Extension). Pattern полезен как чек-лист "что должно быть в project file"; vocabulary genomics-flavored, не cloning. Inspiration only.

**Nextflow lineage (с 25.04, 2025)** — каждый task получает content-addressable LID, `.lineage/` directory хранит records (codeChecksum, script, input parent-LIDs, container/conda env, architecture). `nextflow lineage list/view/render/diff` команды. **Прямой precedent для CAS-DAG в локальном файле**. Урок: префикс `lid://` для opaque hash references — рассмотреть `bdg://` URI scheme внутри `.bdg`.

**Git internals** — четыре типа объектов (blob/tree/commit/tag), всё по SHA-256. Tree = (mode, name, hash) → blob/tree. Commit = (root_tree, parents[], author, msg). Refs = текстовые файлы. Заимствуем content-addressable storage и multi-parent commits; **не** заимствуем merge/3-way merge (биология не имеет).

**IPFS Merkle DAG** — CID включает хеши детей; multiple-parent поддерживается; constructable only from leaves (topological order). Заимствуем canonical-JSON serialization перед хешированием (детерминизм критичен).

**Pijul / patch theory** — patches как first-class коммутативные объекты. Применимо для cherry-pick / replay, **но** наши операции некоммутативны (insert/delete сдвигает координаты). Игнорируем.

**Event sourcing** (Fowler / Kurrent / EventStore) — append-only events, projections. Snapshots каждые N events — performance optimization, не архитектурная необходимость. Snapshots должны эволюционировать с aggregate schema (ключевая ошибка). **Plasmid-git это event sourcing** — изоморфизм; добавить `frozen_snapshot` каждые ~20 commits.

**CRDT (Yjs/Automerge)** — для real-time коллаборации. Sequence CRDT работает на character-level — не подходит для семантических операций ДНК. Linear (sync engine) использует server-side total ordering + LWW, не CRDT для бизнес-данных. **Игнорируем для pet-проекта**; если future collab — Linear-style server total order.

### 1.4 Где модель упрощает биологию (честный list)

**Корректные упрощения** (ПРИНИМАЕМ):

1. **Multi-fragment assembly как Hyperedge** (один Activity с N inputs → 1 output). Принимают **все** конкуренты (SnapGene, Benchling до 15 фрагментов, ApE, SBOL3). Биологически это и есть атомарное событие — тубочка, реакция, продукт. Цепочка попарных рёбер была бы fictional intermediate.

2. **Мутагенез / cut-keep / fragment-insert как in-container commits, не отдельные DAG-узлы.** Это семантически правильно: мутагенез не порождает физически новую "молекулу" — это та же молекула с правкой. Совпадает с тем, как биолог думает о protocol.

3. **Один контейнер = один активный продукт.** В практике биолог работает с одной "версией" в момент. Bench-time реальность: в тубочке одна молекула (или популяция, обычно идентичная по design intent).

4. **Triada triggering commit** (sequence/ends/topology change ИЛИ semantically marked) — корректно соответствует биологическому понятию "значимое изменение".

5. **`origin` immutable enum** — отражает реальные источники ДНК в лаборатории (заказ из catalog, paste, file import, copy, oligo synthesis, assembly product, split product).

**Некорректные упрощения** (ОСОЗНАЁМ; документируем; в v1.0 не закрываем, но не скрываем):

1. **Digest реально даёт смесь фрагментов; мы оставляем один продукт.** Биологически restriction digest pUC19 → 2-3 fragments всегда. Мы моделируем через cut-keep (юзер выбирает который оставить). Это упрощение **в сторону design intent vs физической реальности**. Для формального provenance достаточно; для лабораторной симуляции — недостаточно. **Документируем**: split 1→2 операция возможна как explicit Activity с двумя outputs, но в v1.0 не реализуем.

2. **PCR реально может давать non-specific products.** Мы моделируем как deterministic (forward + reverse + template → один Amplicon). pydna делает то же. Принимаем.

3. **Transformation events / клонирование в host strain** — в нашей модели отсутствуют. Plasmid вышел из ligation = готов к использованию. Реальность: есть transformation efficiency, single-colony picking, miniprep, sequencing-verify. **Открытый вопрос для v0.9+**: добавить ли `TransformationContainer` / `StrainContainer`. SBOL3 имеет `Implementation` для физической реализации.

4. **Sequencing-verify** — provenance говорит "это плазмида X версия Y", реальность — sanger-trace или NGS на плазмиде после miniprep. Disagreement между designed sequence и observed возможен. У нас нет `SequencingVerification` как Activity-type. **Документируем как future**; SBOL3 имеет `ExperimentalData` + `Experiment`.

5. **Реальные ошибки** (mutations during PCR, recombination in vivo, contamination) не моделируются. Это design tool, не lab simulator.

6. **Concentration / amount tracking** — мы не отслеживаем "10 ng/μL × 5 μL". Это inventory-domain (Benchling Inventory, Quartzy). Out of scope.

7. **Strain context** — какой штамм трансформируется (toxic for some methylated DNA, etc.). Open question.

8. **Time-ordering между операциями в одной Activity** — Gibson assembly is one event, but the user мог перепутать порядок добавления фрагментов в реакцию. Не отслеживаем (и не нужно).

### 1.5 Что делать с тем, чего нет в модели

**Multi-product reactions** (digest → mixture). v1.0 решение: `cut-keep` commit (один outcome via choice). v0.9+: `split_product` operation type как hyperedge 1→N (один input AssemblyContainer, N output MoleculeContainers, каждый с `origin: split_product`, `splitFromActivityId`). PROV-O это поддерживает (`Activity` с несколькими `wasGeneratedBy`).

**Transformation / strain context** — отдельный `TransformationActivity` с input MoleculeContainer + reference на `Strain` entity, output `Implementation`-style (физический сэмпл). Inspired by SBOL3 `Implementation`. Off-roadmap для v1.0; в v1.5+.

**Sequencing-verify** — `VerificationActivity` с input MoleculeContainer + `SequencingResult` data attachment, output либо `verified=true` annotation, либо `divergence` description. Inspired by SBOL3 `ExperimentalData`. v1.5+.

**Inventory / physical samples** — out of scope; integration target (Quartzy export, eLabFTW import). v1.0 explicitly не делает.

**Failed experiments** — `Activity` с `prov:invalidatedAtTime` или флагом `success: false`. Открытый вопрос: показывать ли failed на DAG canvas (greyed out vs hidden by default).

**Combinatorial / parametric design** — SBOL3 `CombinatorialDerivation`. Out of scope для v1.0.

### 1.6 Lazy git: precedents и ограничения

**Прямые precedents для lazy lineage у нас нет.** Ближайшее:

- **Git partial clone** (с 2.24, `--filter=blob:none`) — не lazy lineage, lazy fetch missing objects. Но идея promisor remote — важная: baseSnapshot доступен, commits лениво.
- **Mercurial narrow clone** — также shallow/partial; не lazy lineage.
- **Pijul lazy clone** — patches загружаются по требованию.
- **Hydra (Nix CI)** — builds graph lazy.
- **Nextflow `.lineage/`** — content-addressable, lazy resolve через `nextflow lineage view`.
- **pydna** — `pydna_cached_funcs` env (download cache), не lazy lineage.

**Наша lazy git семантика — оригинальная:** `MoleculeContainer.commits[]` инициализируется только при первой меняющей операции (триггер: change в sequence/ends/topology ИЛИ semantically marked op). До этого — только `baseSnapshot` + `origin`. Это даёт:

1. Меньший размер для свеже-импортированной плазмиды (которую юзер не редактировал).
2. Меньше шума на DAG canvas (no-op containers — просто нодa без istории).
3. Чистую границу "imported as-is" vs "edited".

**Ограничения и риски**:

- **Концептуальная нагрузка**: пользователь должен понимать, что коммиты появляются "по-волшебству". Решение: UI показывает "Snapshot only" badge на контейнерах без commits.
- **Migration сложность**: при schema-bump для commit-формата нужно мигрировать только контейнеры с `commits[]`, остальные не трогать.
- **Replay determinism**: заметим явно — `baseSnapshot.hash` входит в hash первого коммита, чтобы избежать silent corruption при изменении baseSnapshot.

**Вердикт**: lazy commits — низкорисковое архитектурное решение, не имеющее прямых аналогов, с понятной семантикой и чистой реализацией (булев `hasCommits` / отсутствие field). Принимаем.

**Edge** (DAG): не нужен как отдельный объект. Inputs/outputs выражены через `AssemblyContainer.inputContainerIds[]` + `outputContainerId`. Edge derive'ится:

```js
// Derived (memoized):
//   for each AssemblyContainer A:
//     for each input I in A.inputContainerIds: edge { from: I, to: A, kind: 'input' }
//     if A.outputContainerId: edge { from: A, to: A.outputContainerId, kind: 'output' }
```

Это упрощает invariants (нет duplicate-state edge-объектов) и идиоматично для PROV (`Activity.used` + `Entity.wasGeneratedBy`).

**Commit** (внутри-контейнерные операции):

```js
/**
 * @typedef {Object} Commit
 * @property {string} id              UUIDv7
 * @property {string} parentId?       previous commit hash; null for first
 * @property {string} hash            SHA-256({type, payload, parentHash, baseSnapshotHash})
 * @property {CommitType} type        discriminated union
 * @property {Object}  payload        type-specific
 * @property {string}  createdAt
 * @property {Agent}   author
 * @property {string?} message        free-form
 * @property {Snapshot?} frozenSnapshot   recompute-snapshot every N commits (perf)
 * @property {number}   schemaVer
 * @property {string}   triggeredBy    'sequence-change'|'topology-change'|'ends-change'|'semantic-mark'
 */

// CommitType ::=
//   'substitution' | 'deletion' | 'insertion' | 'pcr_amplify' | 'cut_keep' |
//   'fragment_insert' | 'tag_add' | 'topology_change' | 'annotation_edit' |
//   'explicit_clone' | 'primer_synthesis_init' | 'milestone'
```

**Pure reducer** для каждого commit type, single switch:

```js
function applyCommit(snapshot, commit) {
  switch (commit.type) {
    case 'substitution':    return applySubstitution(snapshot, commit.payload);
    case 'deletion':        return applyDeletion(snapshot, commit.payload);
    case 'insertion':       return applyInsertion(snapshot, commit.payload);
    case 'fragment_insert': return applyFragmentInsert(snapshot, commit.payload);
    case 'cut_keep':        return applyCutKeep(snapshot, commit.payload);
    case 'tag_add':         return applyTagAdd(snapshot, commit.payload);
    case 'topology_change': return applyTopologyChange(snapshot, commit.payload);
    case 'annotation_edit': return applyAnnotationEdit(snapshot, commit.payload);
    case 'milestone':       return snapshot;  // no-op semantically; DAG-marker
    default: throw new UnknownCommitTypeError(commit.type);
  }
}
```

### 2.2 Persistence

**IndexedDB через Dexie.js** (^4.x). Обоснование (см. §1.3 для детальной argumentation):

- Декларативная schema migration model значительно безопаснее manual `upgradeneeded`-callbacks.
- `useLiveQuery` React hook упрощает интеграцию.
- Compound indexes из коробки.
- ~30KB bundle size приемлем.

**Schema v9** (после миграции с v8 = localStorage Zustand):

```js
db.version(9).stores({
  projects:   '++id, name, createdAt, updatedAt',
  containers: '++id, projectId, kind, name, [projectId+kind]',
  commits:    '++id, containerId, parentId, createdAt, [containerId+createdAt]',
  primers:    '++id, projectId, sequence, name, *tags, [projectId+sequence]',
  primerUsage:'++id, primerId, containerId, commitId?, [primerId+containerId]',
  library:    '++id, kind, ownership, *tags, [kind+ownership]',
  blobs:      'id',  // PNG renders, OPFS-style content
  refs:       'name'  // 'project/<id>/main' → containerId; for fast lookups
}).upgrade(async tx => {
  // migration logic from v8 zustand-persist localStorage
  const oldData = JSON.parse(localStorage.getItem('bodgegene-data') || 'null');
  if (oldData) {
    await migrateFromV8(tx, oldData);
    localStorage.removeItem('bodgegene-data');
    localStorage.setItem('bodgegene-migrated-from-v8-at', new Date().toISOString());
  }
});
```

Indexes design:

- `containers [projectId+kind]` — фильтр по проекту + типу (assembly vs molecule)
- `commits [containerId+createdAt]` — chronological replay
- `primers [projectId+sequence]` — dedupe по sequence в проекте
- `primerUsage [primerId+containerId]` — back-reference query "where used"
- `library [kind+ownership]` — overlay lookup для UI

**`.bdg` file format — RO-Crate-compliant ZIP:**

```

├── containers/
│   ├── <id>.json              ← container body (sans rendered blobs)
│   └── <id>.gb                ← GenBank export with provenance COMMENT
├── commits/
│   └── <hash>.json            ← content-addressable
├── primers/
│   └── primers.json           ← compact pool
├── library/
│   └── library.json
├── refs/
│   └── refs.json              ← project/main pointers
├── renders/                   ← optional, PNG/SVG
```

Sizing oracle (для проекта 10 контейнеров + 50 commits + 20 primers):

|---|---|---|

**GenBank export per container** — каждый MoleculeContainer экспортируется как самостоятельный `.gb` файл с двумя расширениями:

   ```

     AUTHORS   Sinelnikov,I.
     TITLE     Direct Submission
     JOURNAL   Exported 2026-04-28 from BodgeGene 0.6.0 https://bodgegene.dev
   ```
   SnapGene-flavored парсеры используют `JOURNAL Exported … from <tool>` как detection-сигнал; никакого риска, что это сломает SnapGene/Benchling/Geneious.

2. **Структурированный COMMENT-блок** с провенансом:
   ```
   COMMENT     ##BodgeGene-Provenance-START##
               schema      :: https://bodgegene.dev/schema/v1
               format      :: base64-json
               payload     :: eyJhY3Rpdml0eUlkIjoi…   (line-folded base64)
               ##BodgeGene-Provenance-END##
   ```
   Структурированные комменты — NCBI-blessed pattern (`https://www.ncbi.nlm.nih.gov/genbank/structuredcomment/`). Все парсеры (BioPython, SnapGene, Benchling, Geneious, ApE) сохраняют их byte-for-byte. Свой prefix (`BodgeGene-Provenance`) гарантирует, что NCBI/GSC валидаторы не путают с MIGS.

3. **Feature-level** через `/note=` qualifier с `key: value;` синтаксисом (SnapGene-compatible) для feature-уровневой attribution: `note="bdg_commit: <hash>; bdg_origin: assembly_product"`.

**Round-trip validation experiment** для статьи: импортируем 50 публичных плазмид (SnapGene library, AddGene, iGEM Registry); проводим `import → BodgeGene → export-gb → re-import` через цикл; metric: **sequence identity = 100%, feature-name match >= 99%, custom-qualifier preservation >= 95%, BodgeGene-aware re-import восстанавливает full DAG**. Этот экспериментальный claim — конкретный для Application Note.

**Chrome File System Access API vs File API** — strategy progressive enhancement:

- **MVP (v0.6)**: `<input type=file>` для open + `Blob → URL.createObjectURL → <a download>` для save. Везде работает, тривиально.
- **v0.7+**: feature-detect `'showOpenFilePicker' in window`; на supported (Chrome/Edge/Opera 86+) — direct file save с persisted handle (handle сохраняется в IndexedDB, `queryPermission()` re-prompts). На остальных (Safari, Firefox stable) — graceful fallback на download.
- Используем `browser-fs-access` (Google) как ponyfill.

**Auto-save**: throttle 2s + debounce 5s для cloud (если когда-нибудь будет); `dirty` флаг в Zustand; `beforeunload` event при `dirty`; `visibilitychange` → forced flush.

**Multi-tab consistency**: BroadcastChannel для cross-tab уведомлений ("commit added in tab A → tab B re-replay"); `navigator.locks.request('bgene-write', {mode:'exclusive'}, ...)` для эксклюзивных DB writes; pattern leader election для autosave (один таб как leader).

### 2.3 Zustand slices

Цель: разделить state по доменам, минимизировать кросс-slice dependencies, чёткая undo policy.

```js
// slices/projectSlice.js
{ currentProjectId, projects: { [id]: Project }, recentProjectIds[], openedHandles: Map<id, FileSystemHandle> }
// CRUD: createProject, openProject, closeProject, switchProject, importBdg, exportBdg

// slices/containerSlice.js — unified для Molecule + Assembly через kind discriminator
{ containers: { [id]: MoleculeContainer | AssemblyContainer } }
// Operations: createContainer, addCommit, replayContainer, derivedCurrentSnapshot

// slices/primerPoolSlice.js
{ primers: { [id]: Primer }, usage: { [primerId]: Set<containerId> } }
// CRUD + dedup-on-paste + back-reference compute + origin tracking

// slices/librarySlice.js — three-level ownership
{ libraryEntries: { [id]: LibraryEntry }, filterOwnership: 'all'|'project-local'|'shared'|'catalog' }
// Per-project view filtered, but storage flat

// slices/canvasSlice.js — DAG layout cache, derived
{ nodePositions: { [id]: {x,y} }, edgeRouting: { [edgeKey]: ... }, viewport: {x,y,zoom}, selectedIds[] }

// slices/uiSlice.js
{ activeView: 'editor'|'flow'|'library', dialogs: { [name]: bool|state }, theme, dirty: bool }

// slices/historySlice.js — undo/redo
{ undoStack: Snapshot[], redoStack: Snapshot[], cursor: number }
```

**Undo policy**:

- `SNAPSHOT_KEYS = ['projectSlice', 'containerSlice', 'primerPoolSlice', 'librarySlice']` — domain state.
- **Excluded** from undo: `canvasSlice` (UI layout — non-undoable as user expectation; only manual reset), `uiSlice` (dialogs/theme), file-system handles (live references).
- При commit на container — push snapshot domain state в `historySlice.undoStack`; clear redoStack.
- Undo = pop undoStack → push current to redoStack → restore.
- Important: undo откатывает **в Zustand**, но **не** удаляет коммиты из IndexedDB (append-only). При undo визуально откатываемся; при следующей операции форкаемся (новый commit с parent = previous, пропуская "отменённый").

Это компромисс между classical undo (эфемерный) и event-sourcing (no real undo, only inverse operation). Для UX — undo в UI; для audit trail — IndexedDB всегда полный.

**Persistence wiring**: `containerSlice`, `commits`, `primerPoolSlice`, `librarySlice` имеют middleware, который persist'ит изменения в Dexie через debounced batch (300ms). `projectSlice` сохраняет current ref + recent list. `canvasSlice` — `localStorage` для quick load (positioning per project). `uiSlice` — sessionStorage / volatile.

### 2.4 Operational semantics

**Replay determinism**.

```js
function replayContainer(container) {
  if (!container.commits || container.commits.length === 0) {
    return container.baseSnapshot;
  }
  // Order by createdAt with id as tie-breaker (UUIDv7 lexicographically sortable)
  const ordered = [...container.commits].sort((a, b) =>
    a.createdAt === b.createdAt ? a.id.localeCompare(b.id) : a.createdAt.localeCompare(b.createdAt)
  );
  // Find latest commit with frozenSnapshot
  let cursor = container.baseSnapshot;
  let startIdx = 0;
  for (let i = ordered.length - 1; i >= 0; i--) {
    if (ordered[i].frozenSnapshot) {
      cursor = ordered[i].frozenSnapshot;
      startIdx = i + 1;
      break;
    }
  }
  for (let i = startIdx; i < ordered.length; i++) {
    cursor = applyCommit(cursor, ordered[i]);
  }
  return cursor;
}
```

**Detrminism invariants**:

- Operations — pure functions: no `Date.now()`, `Math.random()`, no mutation.
- All non-deterministic data captured at commit creation time, stored in `payload`.
- Canonical JSON serialization (sorted keys, no whitespace) перед хешированием — **критично**.
- Hash = `SHA-256({type, payload, parentHash, baseSnapshotHash})`. Включает `baseSnapshotHash` чтобы избежать silent corruption если кто-то поменял baseSnapshot.

**Frozen snapshots каждые 20 коммитов**: после `applyCommit`, если `(commits.length % 20 === 0)`, прикрепляем `frozenSnapshot` к этому commit'у. Trade-off: storage overhead ~5% на средний коммит, replay speedup 20×. Number tunable (open question: измерить, начать с 20).

**Indel coordinate remapping** для annotation-edit и fragment-insert:

```js
function remapAnnotationCoords(snapshot, indel) {
  // indel: {type: 'insert'|'delete'|'substitute', pos, length, oldLength}
  // Generic transform для regions/details/points:
  return {
    ...snapshot,
    regions: snapshot.regions.map(r => remapRange(r, indel)),
    details: snapshot.details.map(d => remapRange(d, indel)),
    points:  snapshot.points.map(p => remapPoint(p, indel))
  };
}
function remapRange(r, indel) {
  const {pos, length, oldLength = 0, type} = indel;
  let {start, end} = r;
  // если сдвиг полностью до start
  if (pos + oldLength <= start) {
    const delta = (length - oldLength);
    return {...r, start: start + delta, end: end + delta};
  }
  // если сдвиг полностью после end → нет изменений
  if (pos >= end) return r;
  // overlap: edge cases — annotation invalidated → flag
  return {...r, _coordWarning: 'overlapping_indel', start, end};
}
```

Tricky cases (deletion polностью охватывающая annotation, insertion в середину) — обобщение `adjustAnnotationCoords` в текущей plasmid-git.js. В spec: **invalid annotation flagged, not deleted** — пользователь сам решает.

**Frozen snapshot sub-region** (для clone-on-import frozen lineage):

```js
/**
 * @typedef {Object} FrozenLineage
 * @property {string} sourceProjectId
 * @property {string} sourceContainerId
 * @property {string} sourceContainerHash    // hash at clone time
 * @property {Snapshot} subRegion?           // optional: only sub-region cloned, not whole molecule
 * @property {Date}   clonedAt
 */
```

При импорте container из другой Library entry — `sourceContainerHash` фиксируется. Любые последующие изменения в источнике **не** распространяются (frozen by design). Inspired by SBOL3 `persistentIdentity + version + identity` pattern.

**Acceptance pattern для AssemblyContainer**:

```
state machine:
  planning ──[validate inputs ok, params set, simulate dry-run]──> ready
  ready    ──[commit: produce output container]──────────────────> committed
  ready    ──[edit inputs/params]────────────────────────────────> planning
  committed ── (immutable; further changes via clone)
```

В reducer:

```js
function reduceAssemblyAction(state, action) {
  switch (action.type) {
    case 'addInput':
      assert(state.state === 'planning' || state.state === 'ready');
      return {...state, inputContainerIds: [...state.inputContainerIds, action.id], state: 'planning'};
    case 'commit':
      assert(state.state === 'ready');
      const product = simulateReaction(state, getInputs());
      // Create new MoleculeContainer with origin: assembly_product
      const productId = createMoleculeContainer({origin: {kind: 'assembly_product', activityId: state.id}, baseSnapshot: product});
      return {...state, state: 'committed', outputContainerId: productId, endedAtTime: new Date().toISOString()};
    // ...
  }
}
```

### 2.5 Migration v0.5 → v0.6 в два шага

**Шаг (a) — data restructure без UI-изменений** (sprint 1a):

1. Ввести IndexedDB+Dexie (sprint 0). Migrate localStorage Zustand persist → IndexedDB через one-shot upgrade в Dexie v9.
2. Преобразовать текущую Сборку (`fragments[] + junctions[]`) в:
   - N MoleculeContainer-ов (по одному на каждый fragment)
   - 1 AssemblyContainer (с reactionClass из текущего method dropdown, inputs = fragments)
   - 1 output MoleculeContainer (если Сборка committed)
3. **Адаптерный слой** в UI: `getCurrentAssemblyForUI()` возвращает legacy-shape `{fragments, junctions}` derive'нный из новой data model. UI рендерит как раньше.
4. **Compat mode**: feature flag `FF_NEW_DATA_MODEL` (default off в alpha). Пользователь работает в legacy UI; данные пишутся в новой модели через адаптер.

Critical: stable fallback — если что-то сломалось при адаптации, можно откатить FF. Адаптер **read-only over new model** (UI не пишет напрямую в legacy shape — все правки идут через новую model и адаптер просто проектирует их обратно).

**Шаг (b) — UI на новые узлы** (sprint 1b, 2, …):

8. Адаптерный слой выводится из use, FF становится default-on, потом удаляется.

**Дата-стабильность**: на каждом этапе schema на disk одна и та же (новая v9). UI-only feature flag.

### 3.2 Pitch для статьи

**Bioinformatics Application Note (target: 2,500 words)**:

Title candidate: **"BodgeGene: a format-compatible plasmid editor with a graph-of-operations data model for verifiable cloning provenance"**

Abstract structure:
- *Motivation*: Modern plasmid editors (SnapGene, Benchling, Geneious) treat cloning history as either lost-on-export (.dna binary, .gb flat file) or platform-locked (cloud SaaS). No open tool produces a single shareable file with both the resulting plasmid and the structured cloning DAG that produced it. SBOL3 + PROV-O provide the standard vocabulary, but adoption is narrow and tooling assumes RDF expertise.
- *Results*: BodgeGene is a browser-based plasmid editor that models the cloning workflow as a directed graph of *Activities* (assemblies, PCRs, digests) over *Containers* (designed molecules), with provenance as a side effect of every operation. Files are open ZIP archives following the RO-Crate specification, containing per-molecule GenBank exports (with NCBI structured comments carrying lineage) and a JSON DAG using PROV-O vocabulary. Round-trip tested on 50 plasmids from SnapGene Library, AddGene and iGEM Registry, with sequence identity 100% and feature-name preservation >99%.
- *Availability*: github.com/<...>/bodgegene, MIT licensed, browser-only, no install.
- *Contact*: ...

Key claims (defensible):
1. **Format-compatible**: every Container exports to GenBank readable by SnapGene/Benchling/Geneious without loss of sequence/features.
2. **Cross-tool provenance**: COMMENT-block JSON survives third-party round-trip; BodgeGene re-imports restore full DAG.
3. **Hybrid primer pool with structured `origin`**: novel combination not present in surveyed tools.
4. **Lazy lineage**: containers without operations carry no overhead — a property not present elsewhere.
5. **PROV-O semantics on disk**: practical adoption of W3C standard vocabulary in a tool aimed at non-RDF-expert biologists.

Avoid claims:
- ❌ "Benchling-killer" (Benchling enterprise covers different ground).
- ❌ "primer reuse novelty" (Benchling did this; we're novel only in `origin`+hybrid+frozen-lineage).
- ❌ "Industrial production-ready" (it's a research tool).

**JOSS submission** (Journal of Open Source Software):

JOSS требует: open-source repo, automated tests (CI green), documentation, paper.md (~250-1000 words), API/SDK consideration. Soft requirements: clear paper.md, Statement of Need, Functionality summary, References. Параллельная подача с Bioinformatics Application Note приемлема (JOSS accepts citing other peer-reviewed). Submit ~v0.9, after stable v0.8 release.

### 3.3 Risk framing (честное)

1. **Concept fatigue trois слоев** — Project / Container / DAG.
   - *Mitigation*: при первом использовании UI показывает только Editor (одна молекула — как SnapGene). Project и DAG раскрываются по мере использования. Tutorial-видео + onboarding tour.
   - *Honest acknowledgment*: для пользователя который "просто хочет cut-paste sequence" наш tool overkill. Это feature, не bug — целевая аудитория — те, кому нужен provenance.

2. **`.bdg` migration при schema bump**.
   - *Mitigation*: per-record `_v` field, lazy upcaster pipeline, automated backup в IndexedDB blob store с тегом `pre-v(N)-backup` перед миграцией, restore-on-failure в Dexie upgrade tx.
   - *Honest acknowledgment*: схема будет эволюционировать, и иногда миграции будут пропускать edge cases. Strategy: stable v1.0 schema → minor patches безопасно; major bumps с big migration test suite.

3. **localStorage limit реален** — 5-10 MB в большинстве браузеров.
   - *Mitigation*: миграция на IndexedDB в sprint 0; localStorage только для UI prefs.
   - *Closing*: после v0.6 не проблема.

4. **Provenance в COMMENT block игнорируется конкурентами** — это feature или bug?
   - *Honest analysis*: **обе стороны**.
     - **Feature**: zero-cost interop. SnapGene открывает наш `.bdg`-export — видит молекулу, не ломается. Это критично для "переслать коллеге".
     - **Bug**: при возврате через SnapGene → BodgeGene без нашей COMMENT (если SnapGene её удалил при операциях) — provenance теряется.
   - *Conclusion*: это "feature with awareness". В UI BodgeGene показывает badge "imported from SnapGene round-trip — DAG может быть partial". Documentation честно отражает.

5. **Pet-проект scaling**. Bus factor = 1.
   - *Mitigation*: clear architecture spec, automated tests, documentation, JOSS paper. Open-source MIT — кто-то может форкнуть.
   - *Acknowledgment*: BodgeGene — research tool, не product. Ожидать enterprise-grade SLA нельзя.

6. **Benchling уже делает primer reuse** (см. §1.4 deep-dive в исследовании).
   - *Resolution*: переформулирование. Не competing on "primer reuse" — competing on "primer reuse в open file format с structured origin и frozen lineage". Целевая аудитория — academia/teaching/personal, не enterprise.

7. **SBOL adoption узкая**.
   - *Mitigation*: SBOL3 export как v0.2 feature behind a flag, не critical path. Делается через pySBOL3 механически.
   - *Acknowledgment*: SBOL может быть useful только для academic synbio/iGEM подмножества.

## 4. Открытые архитектурные вопросы

Эти не закроются текущим исследованием — кандидаты для N+2 / N+3:

1. **Snapshot frequency N**. Default N=20 (snapshot every 20 commits). Adaptive (snapshot when replay > 100ms) — overkill сейчас. Открыто: измерить на реальных проектах в v0.7 и подкорректировать.

2. **Hot/cold split commits[] в IndexedDB**. Для проектов >1000 коммитов может потребоваться. Сейчас — open, измерить.

3. **OPFS migration для blobs**. IndexedDB зрелее, но для очень больших snapshot (>10MB) OPFS быстрее. Open для v1.5.

4. **Future collab story**. CRDT — overkill. Linear-style (server total order + LWW + CRDT только для текстов комментов) — best path, но требует backend. Open до v2.0.

5. **TransformationContainer / StrainContainer**. Биологически нужно для полного provenance, но out of scope для v1.0. SBOL3 `Implementation` — референс. Open для v1.5.

6. **SequencingVerificationActivity**. SBOL3 `ExperimentalData`+`Experiment` референс. Open для v1.5.

7. **Split product (digest → multiple outputs)**. v1.0 = `cut-keep` (one output). v1.5 = explicit `split_product` Activity 1→N. Open data-model: один Activity с outputs[] vs N parallel ChildActivity.

8. **Combinatorial / parametric design**. SBOL3 `CombinatorialDerivation`. Open для v2.0.

9. **Failed experiments на DAG canvas**. Greyed-out vs hidden by default. UX research нужен. Open.

10. **Drag-drop graph editor для main editing**. Текущая позиция: read-only canvas, императивные диалоги для создания операций. Если user feedback скажет "want to drag" — пересмотр. Open.

11. **Dual file format: .bdg (ZIP) vs single-JSON .bdgproject**. ZIP правильный для assets, но overhead для small projects. Open: hybrid? Heuristic-based selection?

12. **Concurrent collaboration через File System Access API + cloud-sync hybrid**. Single file на Dropbox/iCloud Drive — naive sync ломается с .bdg ZIP. Open для v2.0.

13. **Plugin/extension system**. Geneious's Plugin SDK — референс. Open для v2.0.

14. **Versioning внутри primer pool**. Primer sequence is mostly immutable, но если нужно правка — branch/version или delete+create? Open.

15. **Cross-project dependencies**. Если container клонирован из другого проекта (frozen lineage), и тот проект deleted — что делать с back-reference? Open: store snapshot vs broken link.

16. **Legacy projects backward-compat policy**. Сколько версий назад читаем? Один N-1, последние 3, навсегда? Open.

17. **Primer Tm calculation correctness across contexts** (different salt, IDT vs Phusion buffers). Out of scope для data model, но ошибки в Tm подрывают доверие. Open: какой Tm engine использовать (existing JS lib `oligotm`)?

18. **Internationalization / Russian UI**. Author primary language Russian; UI / docs language strategy: English-first для academic adoption, Russian as locale option? Open.

19. **DAG topology edge cases**. Cycles (impossible in cloning?) — guard в reducer. Disconnected components per project (multiple parallel cloning lines) — render strategy. Open.

20. **Authorship attribution в multi-user**. Currently единственный `Agent` per project. Multi-user: per-commit author. PROV-O ready, UI не. Open для v2.0.

Эта research-сессия дала плотную базу для двух следующих документов:

1. **`ARCHITECTURE_PROJECT_MODEL.md` (тип A spec, ~25-30 KB)** — проработанная архитектурная спецификация со всеми discriminated unions, state machines, reducer-функциями, pseudocode для replay/migration/round-trip validation. Готова к записи в N+3 сессии. Все нужные данные — в §2 этого документа.

2. **`POSITIONING.md`** (текст для статьи, README, презентаций) — финальный pitch без маркетингового надувательства. Все нужные claims — в §3.

Главный архитектурный мессидж: **PROV-O (vocabulary) + Event Sourcing (storage) + Content-Addressable Hash (identity) + RO-Crate (packaging) + GenBank+structured-comment (interop)** — это пять колонн, на которых стоит BodgeGene. Каждая колонна имеет реальный precedent в зрелых стандартах/инструментах. Уникальность — в их интеграции в один tool с явным `origin` и hybrid pool.

Главный позиционирующий мессидж: BodgeGene — **honest open research tool**, не Benchling-killer. Цель — сделать то, что не может никто другой сейчас (open file with verifiable provenance), для аудитории, которой это нужно (academic / teaching / personal / small labs). Не борьба за enterprise.
