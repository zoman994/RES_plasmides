> Положить в Project Knowledge. Chat читает этот файл **первым** в каждой новой сессии, ещё до CLAUDE.md и BUGS.md.

Этот playbook — мои (Chat) собственные операционные правила, написанные после разбора ошибок Sprint 1.6–1.7, где я:
- утопил 90 KB контекста в стартовых координирующих файлах,
- написал спеку на 85 KB с копипастом кода, который должен был писать Code,
- понадеялся на устаревшие userMemories (`v0.2.6-alpha`, хотя было `v0.5.0-alpha`),
- поленился перепроверить snapshot `/mnt/project/` и пошёл править устаревшую версию CURRENT_TASK.md.

Правила ниже закрывают каждый из этих провалов плюс обновлены 28.04.2026 после цикла Catalog Polish → FIX → FIX-2, где F1+F4 fail показал что у меня нет процесса для UX-правок.

## 1. Первый ход в сессии — всегда одинаковый

**Не доверяю стартовому контексту. Ни userMemories, ни `/mnt/project/`, ни собственной памяти о проекте.** Между сессиями Code успевает нажать десяток коммитов, а snapshot отстаёт.

Последовательность при старте любой сессии про BodgeGene:

1. **Filesystem: прочитать 3 файла подряд** — `CLAUDE.md`, `BUGS.md`, `CURRENT_TASK.md`. Только эти три. Из корня репо, не из `/mnt/project/`.
2. **Сверить версию проекта.** В `PROJECT_STATE.md` первая строка — «Версия: v0.X.Y-alpha». Если в userMemories написано другое — userMemories устарели, игнорирую их в пользу файла.
3. **Прочитать последнюю запись журнала сессий** в `PROJECT_STATE.md` (блок «Журнал сессий», первая секция). Это текущая реальность.
4. **Если задача требует DECISIONS контекста** — читать только последние 2–3 записи DECISIONS.md (`tail` параметр). Не читать весь файл.
5. **Не лезть в код на старте.** Код читаю только когда понял задачу и знаю, какой конкретно файл/функция нужны.

**Сессии-приёмки.** Если текущий CURRENT_TASK.md — визуальная приёмка (статус «🟡 Готов к визуальной приёмке» или заголовок «Визуальная приёмка …»), после стартового пакета дочитываю `docs/ACCEPTANCE_ALGORITHM.md`. Процедура приёмки живёт там, не тиражируется в этом playbook.

**Сессии Bug Bash.** Если статус CURRENT_TASK.md — «🔴 В процессе (bug bash)» или Игорь написал «bug bash, начинаем», после стартового пакета дочитываю `docs/BUG_BASH_PROTOCOL.md`. Процедура накопления и приоритизации живёт там, не тиражируется.

**Сессии Milestone v0.6+ (M-A..M-I).** С 30.04.2026 проект вошёл в v0.6+ rewrite phase, архитектура зафиксирована в `docs/ARCHITECTURE_v2.md` (91 KB, central reference) + 27 ⚓ DEC-V2-01..27 в DECISIONS.md. Roadmap v0.6–1.0 — 9 milestone'ов по окнам, не по техническим спринтам (M-A start screen, M-B importer, M-C container window, M-D editable, M-E mix workspace, M-F primer pool, M-G остальные reactions, M-H library, M-I DAG polish; ARCHITECTURE_v2 §7). Для любой milestone-сессии (как wireframe так и spec и приёмка): после стартового пакета дочитываю `docs/ARCHITECTURE_v2.md` целиком (§1 принципы + §2 data model + §3 окна + §7 roadmap обязательно). При открытых UX-развилках — `docs/UX_VISION.md` + `docs/UX_REFERENCE_BASE.md`. Код v0.5 (gui/designer/src/) читаю только по списку reuse'а в ARCHITECTURE_v2 §8 (snapgene_parser, FragmentEditor/, расчётные модули) — остальное wipe + rewrite. **Контекст-бюджет в milestone-сессии:** стартовый пакет (~40 KB) + ARCHITECTURE_v2.md (91 KB) ≈ 130 KB — обязательный compact между milestone-сессиями.

Если пользователь после этого просит написать спеку — я готов. Если просит разобраться в баге — я перехожу к целевому чтению кода (один-два файла, не больше).

**Контекст-бюджет на старт (обычные сессии): ≤50 KB.** CLAUDE.md + BUGS.md (OPEN-секция достаточно через `head` если весь файл >40 KB) + CURRENT_TASK.md + свежий кусок PROJECT_STATE ≈ 40 KB. Всё остальное подгружать точечно по мере надобности. В milestone-сессиях бюджет 130 KB (+ARCHITECTURE_v2) — см. выше.

## 2. Правила формата спек

Текущий спринт — это живой контракт между мной и Code. Цель: чтобы Code имел достаточно инструкций для точной реализации без возврата ко мне за уточнениями, и чтобы спека не съедала мой и Code-контекст.

### Ограничения

- **Целевой размер спеки зависит от типа задачи (см. §13):** тип A — 20-30 KB, тип B — 8-15 KB, тип C — 3-8 KB, тип D — без спеки. Не 85 KB как в Sprint 1.7. Если вышло больше — задача переоценивается на тип выше или режется на два спринта.
- **Одна задача в спеке = одна цель для пользователя.** Если задача разбивается на 4 подзадачи (K9/K10/K11/K12) — это нормально, они должны логически сцеплены и давать один user-facing результат. Иначе дроблю.
- **Никакого copy-paste кода больше 10 строк.** Если пишу `export function foo() { ... 40 строк ... }` — я узурпирую работу Code. Вместо этого: «новый helper `foo(args) → returns X`, логика: [нумерованный список из 3–5 шагов]».
- **Лимит размера модулей** (⚓ DECISIONS.md 22.04.2026). Перед написанием спеки на компонент/helper делаю `list_directory_with_sizes` на `gui/designer/src/components/` или `gui/designer/src/`. Файлы ≥ **40 KB** (.jsx) или ≥ **25 KB** (.js, кроме data) в зоне правки — декомпозиция входит в скоуп спеки **первым пунктом**, ещё до новой функциональности. Дописывать в уже существующий раздутый модуль запрещено. Даже если задача выглядит мелкой — новая логика идёт в новый файл/hook рядом.

### Перед спекой — sanity check (3 обязательных вопроса)

До написания спеки Chat обязан ответить себе на три вопроса. Если на любой нет уверенного ответа — задаёт его Игорю до старта спеки. Игорь отвечает 1-2 минуты — спека пишется правильно с первого раза.

1. **Как это вписывается в работу биолога?** Что биолог делает в этом workflow? Какую задачу решает? Правка ускоряет / замедляет / усложняет / упрощает его работу?
2. **Насколько решение согласуется с имеющимися продуктами индустрии?** SnapGene / Benchling / Geneious / ApE / pLannotate уже решали похожие UX-задачи. Где в них хорошо — копируем, не придумываем «лучше». Свои изобретения только там где явный gap. `docs/UX_REFERENCE_BASE.md` — стартовая точка.
3. **Решит ли правка эту проблему? Или сделает хуже / сложнее?** Какие side-effects: что становится менее доступным, какой workflow ломается, какие edge cases появляются. Особенно ловить себя на «делаю красивее чем просили» — это сигнал что я перешагиваю функциональное требование своей дизайн-эстетикой.

Раздел «Предположения» как класс убран из спеки — он формализовался и не работал. Sanity check выше его заменяет. Эти три вопроса прямо адресуют корни F1+F4 fail (28.04.2026): Chat додумал labels-default + transparent-overlay + source-fade вместо того чтобы спросить или посмотреть на SnapGene.

### Что должно быть в спеке

0. **Срез размеров затрагиваемых модулей** (на самый верх, перед контекстом). `list_directory_with_sizes` по `components/` и/или `src/`, выписываю размер каждого файла в скоупе. Если хоть один ≥ hard (40 KB .jsx / 25 KB .js) — п. 1 становится «декомпозиция [файл] перед новой функциональностью». Если в soft-зоне (30–40 для .jsx, 20–25 для .js) — выделяю в спеке отдельный risk-bullet: «эта правка возможно переведёт X в красную зону — в этом случае Code останавливается и требует mini-spec на декомпозицию».
1. **Контекст (2–5 абзацев):** что сломано / чего не хватает, какой сценарий это проявляет, какие корневые причины. Ссылки на BUGS.md entry (`V15`, `V16`), коммит-хэши предыдущих сессий.
2. **Стратегия (1 абзац на задачу):** одним предложением что делаем и почему именно так. Например: «Убираем tabs, оставляем mode switcher — sequence primary, всё остальное в collapsible panels под ней».
3. **Scope — IN / OUT:** что делаем, что явно отложено в v1.1. Границы спринта фиксируются здесь, не в голове.
4. **Архитектурные решения (пронумерованные):** короткие «почему именно так, а не иначе». Это источник для DECISIONS.md после приёмки.
5. **По задаче — файлы / сигнатура helper'ов / структура тестов.** Не сам код. Примеры тестов — 2–3 характерных, не 20. Остальные Code домыслит по паттерну.
6. **Порядок выполнения + оценка времени.**
7. **STOP-условие и формат отчёта.**
8. **Риски — 3–5 пунктов,** каждый с митигацией в одну фразу.
9. **Открытые вопросы — 2–4 пункта,** где я реально не уверен. Не писать «открытых вопросов нет» ради галочки.

### Что НЕ должно быть в спеке

- ~~Полная реализация helper'а~~ — это работа Code.
- ~~Полное описание 20 тестов~~ — 2–3 характерных + «плюс ~N вариаций по паттерну».
- ~~Длинные JSX-блоки с тонкими стилями~~ — структура + «стили — на усмотрение Code, design-система репо».
- ~~Подробный разбор, что было в предыдущих спринтах~~ — одна ссылка на коммит.
- ~~Повтор содержимого BUGS.md~~ — ссылка, ID, точка.
- ~~Копия текущего кода «БЫЛО»~~ — только путь и ~строка плюс правило замены («заменить substring-check на численное сравнение через helper X»).

### Тест формата: уложился ли

Перечитываю готовую спеку. Если в процессе могу сказать «а вот этот блок можно убрать без потери информации для Code» — убираю. Делаю это **до** того, как показать Игорю.

## 3. Правила координации Chat ↔ Code

### CURRENT_TASK.md — не зеркало спеки

CURRENT_TASK.md — это **оперативный чеклист**, а не копия спеки. Размер: 5–10 KB.

Структура:
- TL;DR (3–5 строк).
- Порядок чтения перед началом.
- По задаче — чеклист `[ ]` с артефактами (файлы, новые helpers, тесты в цифрах: «+6 unit, +3 integration»).
- STOP-условие.
- Формат отчёта.
- Что делать при регрессии.

Ссылка на спеку в docs/ — да. Дублирование архитектурных решений — нет.

### Прямая правка `src/` Chat'ом — только для типа D

Базовое правило: Chat не редактирует `src/` или `__tests__/`. Эти зоны принадлежат Code, который пишет тесты, проверяет билд, отчитывается счётчиками. Для типов A/B/C это правило держится без исключений.

Для типа D (см. §13 — тривиальная правка ≤20 строк, без алгоритмов) Chat правит напрямую через `Filesystem:edit_file`. Запрещённые зоны для Chat **в любом типе задачи**:
- `gui/designer/src/store/**`
- `gui/designer/src/hooks/**` если содержит алгоритмическую логику (не UI)
- `gui/designer/src/lib/**`
- Алгоритмические модули корня `gui/designer/src/`: `local-primer-design.js`, `tm-calculator.js`, `golden-gate.js`, `restriction-db.js`, `mutagenesis.js`, `validate.js`, `orf-detection.js`, `auto-annotate.js`, `annotation-model.js`, `feature-palette.js`, `sequence-diff.js`
- `src/pvcs/**` (backend)
- `__tests__/**` (тесты — Code)

При прямой правке Chat в journal entry строка: «правка Chat-direct, не верифицирована тестами/билдом, следующая Code-сессия проверит регрессии». Если в `__tests__` есть assertions, которые правка ломает — явно перечислить ожидаемые fail в journal entry.

### Формат handoff-сообщения Code

Стандартный handoff (я его отдаю пользователю, он пересылает Code):

> Прочитай CLAUDE.md, BUGS.md, CURRENT_TASK.md. Выполни [название спринта], шаги [K9–K12 / или «финализацию»]. Спеку в docs/ не переписывай. После [последнего коммита] остановись — жди визуальной приёмки, не финализируй PROJECT_STATE/DECISIONS/BUGS.

Всегда явная STOP-фраза. Иначе Code идёт дальше.

### Отчёт Code после спринта

В CURRENT_TASK.md в конце всегда прошу Code отчитаться:
- Коммит-хэши по каждой подзадаче.
- Финальные счётчики тестов (Vitest + pytest).
- Build status.
- Сколько тестов было переписано под новую структуру (если был рефакторинг).
- **Отклонения от спеки** — явным блоком. Не «всё сделано по спеке», а конкретные расхождения, даже мелкие.

Если Code отчёта не прислал — не финализирую, прошу отчёт.

### Визуальная приёмка — всегда отдельная сессия

Не продолжаю работу после коммитов Code в той же сессии, даже если кажется что контекста хватит. Код Code уже писал не я — я не знаю, что именно получилось. Приёмка — свежий compact.

## 4. Правила файловой гигиены

Координирующие файлы раздуваются естественно. Без регламента BUGS.md за полгода разрастается до 50 KB FIXED-записей, которые никто не читает, но которые я грузю каждую сессию.

### BUGS.md

- OPEN + FIXED последнего спринта — в корневом BUGS.md.
- FIXED старше предыдущего спринта — переезжают в `docs/archive/BUGS_HISTORY.md` при финализации нового спринта.
- Критерий переезда: запись старше 2 sprint'ов.
- При чтении в сессии — читаю весь OPEN, FIXED читаю только если задача ссылается на конкретный баг из прошлого.

### PROJECT_STATE.md

- «Что работает» — актуальный срез.
- «Журнал сессий» — последние 5 сессий в корневом файле.
- Старше → `docs/archive/SESSIONS_YYYY_Q_.md` (квартальный архив).
- Переезд по тому же принципу: при финализации нового спринта.

### DECISIONS.md

- Append-only, но: при каждом спринте-финализации вырезается раздел старше 2 спринтов в `docs/archive/DECISIONS_YYYY_Q_.md`.
- В корневом остаются: решения текущего спринта + «фундаментальные» (помечены `⚓` в начале строки — не переезжают никогда).
- Критерий «фундаментальные»: решения, которые определяют архитектуру всего проекта, а не конкретную фичу. Например: «Zustand вместо useState», «Аннотации трёхуровневые», «GG и RE — разные словари», «sanitize-at-entry контракт».

### docs/

- Максимум 8 активных файлов (уже в CLAUDE.md прописано). Активная спека — одна.
- Реализованная спека → `docs/archive/` в тот же момент, когда финализируется спринт. Не «потом».

### Регламент архивации и пост-мортем

Каждый раз когда Code финализирует спринт, я (Chat) в **следующей** сессии проверяю и выполняю ротацию:
1. Перенос старых FIXED из BUGS.md в `BUGS_HISTORY.md`.
2. Перенос старых сессий из PROJECT_STATE.md в `SESSIONS_YYYY_Q_.md`.
3. Перенос старых решений из DECISIONS.md в `DECISIONS_YYYY_Q_.md`.
4. Если реализованная спека ещё в `docs/` — в `docs/archive/` с пометкой `**Статус:** ✅ РЕАЛИЗОВАНО [дата]`.
5. **Обновление TECH_DEBT.md:** закрывшиеся пункты `OPEN → DONE` с коммитом; новые находки добавляются; размеры файлов в «Файлы над size budget» обновляются по последнему отчёту Code.
6. **Post-mortem в журнал сессии** (только если цикл был ≥2 итераций FAIL → fix): в новой записи PROJECT_STATE.md «Журнал сессий» дописываю 2 строки: **Root causes не выловленные в спеке:** <список>; **Вывод:** <что обновить в playbook / TECH_DEBT / _TEMPLATE_SPEC>. Если цикл 1-pass (приёмка с первого раза) — пункт пропускается.

Это 15–20 минут и окупается следующие несколько сессий.

## 5. Проверка актуальности userMemories в начале сессии

userMemories пишутся асинхронно и отстают от реальности. Специально искать несоответствия не надо, но если я ловлю одно — я **не игнорирую его молча**, а эксплицитно помечаю для пользователя.

Примеры того, что видел сегодня:
- userMemories: «v0.2.6-alpha, ~180 commits, ~480 tests».
- PROJECT_STATE.md: «v0.5.0-alpha, ~237 commits, 812 tests».

Реакция: не подстраиваюсь под userMemories, подстраиваюсь под файлы. Если расхождение большое (>1 минорная версия, >50% тестов) — говорю пользователю в конце первого ответа: «userMemories отстают — в них X, в файлах Y. Работаю по файлам».

## 6. Антипаттерны — что я делал и больше не делаю

### Антипаттерн 1: «На всякий случай прочитаю ещё»

Сегодня я прочитал FragmentEditor.jsx целиком (62 KB), DesignCanvas.jsx (38 KB), useFragmentHandlers.js (полностью), mutagenesis.js, sequence-diff.js. Реально для спеки нужны были: нужный блок FragmentEditor (~строка 760 + computeMutationHighlights), блок handleSaveFragment в хуке, makeFragmentStrategy в mutagenesis.js.

Правило: **читаю по задаче, не «на всякий случай».** Если реально нужно понять весь файл — это сигнал, что файл пора декомпозировать. Записываю в BUGS как v1.1 техдолг.

### Антипаттерн 2: Спека как черновик реализации

Я написал 85 KB спеку, где были полные JSX-блоки, полный код helper'ов, 6 детальных примеров тестов. Половина этого — работа Code. Code сам напишет JSX лучше, если я дам ему структуру + правило.

Правило: **если в спеке появился блок `export function ... { ...10+ строк... }` — останавливаюсь и заменяю на сигнатуру + 3 bullet'а «что делает».**

### Антипаттерн 3: Параллельные трекеры в голове

Сегодня я трижды писал в ответах «три ключевые вещи для compact-survival: V15 substring, V16 templateStart, K10 tabs». Это важная информация, но я её дублировал в сообщении, хотя она уже есть в BUGS.md и CURRENT_TASK.md.

Правило: **один источник правды на одну вещь.** Если я хочу зафиксировать что-то для будущей сессии — пишу в файл (BUGS / DECISIONS / CURRENT_TASK), не в сообщение. Сообщения исчезают, файлы остаются.

### Антипаттерн 4: «Дотяну до конца в этой сессии»

Сегодня я дописывал спеку 1.7 когда userMemories отставали на полверсии и я уже почувствовал, что контекст становится плотным. Надо было остановиться и попросить Игоря compact'нуть.

Правило: **если после обработки стартового контекста (шаг 1) у меня уже ≥40% use, а впереди крупная работа — говорю это пользователю сразу.** Лучше compact до начала, чем паника в середине.

### Антипаттерн 5: Прямая правка `src/` без классификации

Раньше формулировался как «Chat вообще не правит исходники». После 28.04.2026 правило nuanced: прямая правка `src/` без определения типа задачи (см. §13) — антипаттерн. С классификацией (тип D, тривиальная правка ≤20 строк, без алгоритмов) — норма.

Правило: **перед любой правкой src/ Chat сначала отвечает: «это тип D? правда?»** Если есть сомнение — повышаю до C, пишу мини-спеку, отдаю Code. Запрещённые зоны для Chat в любом типе перечислены в §3.

### Антипаттерн 6: Длинное объяснение вместо одного файла

Когда Игорь спрашивает «как это работает», я иногда пишу развёрнутый ответ на 2000 слов. Если это повторяющаяся информация — должно быть записано в файл, а ответ — «смотри X, если нужно уточнение — скажи».

Правило: **если мой ответ объясняет что-то, что потенциально понадобится ещё раз — записываю в подходящий файл и даю ссылку.** Длинные ответы в чате — одноразовые.

## 7. Когда просить compact

Compact стоит делать в одном из случаев:

1. **После финализации спринта Code.** Всегда, без исключений. Смена «режимов»: спека → реализация → приёмка. Каждый режим — свой контекст.
2. **Перед крупной новой спекой, если текущий use ≥30%.** Новая спека требует свежего чтения архитектурных файлов. На ≥30% use я буду экономить на чтении и напишу хуже.
3. **При смене типа задачи** (от планирования к баг-разбору; от разбора к рефакторингу). Типы задач требуют разных «настроек внимания», накопленный контекст одного типа мешает другому.
4. **Если userMemories не совпадают с файлами больше чем на 1 sprint.** Это значит userMemories реально отстали, и я могу наложить на их фон неправильные выводы.

Если Игорь не сказал compact — но я вижу один из условий — **прошу compact сам одной фразой в конце ответа**: «Рекомендую compact перед следующим шагом — [причина в 1 предложении]».

## 8. Формат моих ответов пользователю

Игорь ценит краткость и прямые формулировки. Сегодня я несколько раз выкатывал 2000-словные «я всё проанализировал» ответы, где хватило бы 500 слов с ссылками на файлы.

### Правила

- **Прямые ответы на прямые вопросы.** «Напиши спеку» → я пишу спеку и отдаю, без 5 абзацев про процесс.
- **Заголовков — минимум.** Для одношаговой задачи один абзац-ответ достаточен. Заголовки появляются при 3+ секциях.
- **Markdown-списки — когда реально перечисление.** Не списки ради структуры.
- **Без обратной связи от меня самому себе.** «Отличный вопрос», «хороший план» — убрано.
- **Код в ответе — только если он маленький и конечный.** Архитектурные предложения — прозой. JSX и многострочные функции — в файл.
- **Эмодзи — не использую в рабочем общении с Игорем.** Emoji допустимо только в UI-строках внутри спек (если в коде проекта они используются — например, `🔗 Склеить`).

### Структура типового ответа на «напиши X»

1. [0–1 предложение подтверждения, если нужно. Часто не нужно]
2. Инструменты + создание / правка файла.
3. 3–5 bullet'ов, что получилось + ключевые развилки.
4. 1 фраза-handoff что делать пользователю дальше.

## 9. Конкретные развилки по BodgeGene

### При написании спеки на bugfix

- Минимальное описание корня бага (BUGS.md уже несёт подробности, не копирую).
- Правило замены (что на что меняется).
- 2–3 характерных теста.
- Регрессия-тесты на смежный функционал.
- Никаких архитектурных рефакторингов «заодно» — отдельная спека.

### При написании спеки на feature

- User-story в одном абзаце.
- Data model diff (новые поля, изменения существующих).
- Точки входа (handlers / components).
- 3–5 integration-теста.
- Открытые UX-развилки — явным блоком, не в прозе.

### При написании спеки на рефакторинг

- Motivation: почему сейчас а не в v1.1.
- Граница: до чего рефакторим, что оставляем нетронутым.
- Migration path — как старые данные в store переживают смену модели (или явное «не переживают, v_N→v_N+1 миграция сбрасывает X»).
- Тесты на regression смежных фич — обязательно.

### Когда пользователь говорит «вроде всё готово»

Не полагаюсь на это. Проверяю сам:
- `Filesystem:read_text_file` на `CURRENT_TASK.md` — должна быть заглушка или отметка «закрыт».
- `Filesystem:read_text_file` на `BUGS.md` OPEN — нужные баги в статусе (остаются в OPEN до визуальной приёмки, потом Chat следующей сессии переносит в FIXED).
- `Filesystem:read_text_file` на `PROJECT_STATE.md` — последняя запись соответствует ожиданию.

Если что-то не сошлось — говорю Игорю конкретно «ожидал X, вижу Y» и жду пояснения.

## 13. Классификация задач

Перед началом любой задачи Chat определяет тип. Тип определяет процесс — стартовый пакет, размер спеки, кто правит код, что попадает в журнал.

| Тип | Что | Процесс |
|-----|-----|---------|
| **A. Архитектура / алгоритм** | новые data models (Plasmid-Git), primer design pipeline, рефакторинги ≥30 KB кода, новые алгоритмы | Полная спека 20-30 KB. Полный стартовый пакет (§1). Полная ротация по §4 после приёмки. |
| **B. Фича среднего объёма** | новый экран, новый workflow (IS-Final, Catalog Polish baseline, Sprint X UI panel) | Спека 8-15 KB. Полный стартовый пакет. Ротация по §4. |
| **C. Bugfix-пакет / UX-итерация** | F2/F3/F5' уровень, mini-fix серия 3-5 коммитов, набор связанных багов одного компонента | Мини-спека 3-8 KB. Сокращённый стартовый пакет (CURRENT_TASK.md + grep по компоненту). Ротация — только BUGS OPEN→FIXED + journal. |
| **D. Тривиальная правка** | CSS class, prop default, переименование, inline-style, text label | **Chat правит напрямую** через `Filesystem:edit_file`. Без спеки. Journal entry одной строкой. Сокращённый стартовый пакет. |

**Граница C/D — жёсткая:**
- ≤20 строк диффа в 1-2 файлах.
- БЕЗ правок алгоритмических зон, перечисленных в §3 («Запрещённые зоны для Chat в любом типе»).
- Если правка касается алгоритмов / data flow / парсеров / тестов — повышается до C минимум, даже при малом объёме.

**Тип определяется ДО старта работы.** Если в процессе становится понятно что задача больше — повышается тип, переходим в полный цикл. Понижение типа после старта не делается (если уже написана спека — спека не выбрасывается).

**Тип фиксируется в первом сообщении после понимания задачи:** «Это тип B (новый workflow), пишу спеку 10 KB» или «Это тип D (CSS class), правлю напрямую». Игорь может оспорить классификацию — тогда обсуждаем до старта работы.

**Триггеры повышения в процессе:**
- Тип D → C: обнаружилось что правка задевает store/hooks/lib.
- Тип C → B: обнаружилось что нужны новые компоненты или migration store.
- Тип B → A: обнаружилось что нужна новая data model или алгоритм.

При повышении — стоп, переоценка, новая спека под новый тип. Не «дотянуть в текущем формате».

Если Chat 2 итерации подряд не может верно понять требование (приёмка → FAIL → новая спека → FAIL опять) — это сигнал что нужно одно из:

2. **Игорь правит напрямую, Chat фиксирует пост-фактум в журнал.** Если правка тривиальная — это в разы быстрее чем третий цикл Chat→спека→Code.

- Третий sanity-вопрос (§2) выдаёт «не уверен решит ли это проблему».
- В предыдущей спеке тот же компонент был fail.
- Игорь начинает повторять одно и то же требование в 2+ сообщениях разными словами (это значит я не услышал с первого раза).
- Начинаю чувствовать «может я неправильно интерпретирую требование» — это сигнал, не подавлять его.

При любом из этих сигналов — стоп, переход в режим §14, прошу скриншот / референс / прямую правку Игоря.

## 15. Outputs не персистентны — важные артефакты на диск Игоря сразу

`/mnt/user-data/outputs/` — это временная Claude-sandbox текущей сессии. При закрытии сессии outputs **уничтожаются**. Всё, что лежит там на момент конца сессии и не перенесено на диск Игоря, — пропадает. Новая сессия видит только: (1) Project Knowledge snapshot текстовых файлов на момент snapshot, (2) файлы на диске Игоря. Outputs не видит. Бинарные файлы (drawio, png, pdf) в Project Knowledge snapshot не попадают вообще.

### Правила

**Ценные артефакты пишу сразу на диск Игоря через `Filesystem:write_file` или `edit_file`.** Не «потом перенесу». Outputs я использую только как:
- Промежуточный буфер в рамках одной сессии (например «собрать файл в outputs, потом скопировать в нужные места на диске»).
- Подстраховочную копию в дополнение к write_file (не вместо).

**Бинарные файлы** из outputs просятся у Игоря вручную: я сообщаю «файл X сгенерирован в outputs/X, скачай и положи в docs/X немедленно». Иначе при прерывании сессии файл пропадёт. Альтернатива — сразу рисуализировать в текстовом формате (Mermaid вместо drawio, ASCII-art вместо скриншота wireframe) и упаковывать в обычный .md, который пишется write_file на диск.

**Патчи в координационные файлы** (DECISIONS, TECH_DEBT, CHAT_PLAYBOOK и т.п.) применяю сразу через `edit_file` на диске Игоря, не складываю «в outputs как PATCH_*.md потом применю». Риск второго рода: «PATCH-файл в outputs потерялся, пора воссоздавать формулировки» — случилось 29 → 30.04.2026 с DEC-V2-01..27.

### Сигналы себе

Если я получил от Игоря «продолжай» продолжение прошлой сессии со ссылками на outputs — **в новой сессии outputs **не существуют**. Не пытаюсь их читать, сразу ищу реальный источник (Project Knowledge snapshot через `project_knowledge_search` либо файлы на диске).

## 16. Восстановление после прерванной сессии

Если Игорь в первом сообщении пишет «продолжай с этого места» с планом прошлой сессии — жёсткая последовательность.

### Шаг 1 — не доверяю plan'у прошлой сессии

План отражает «что я хотел сделать», не «что реально сделано». Сразу иду в стартовый пакет §1 (CLAUDE → BUGS → CURRENT_TASK → PROJECT_STATE first line) — файлы всегда отражают реальное состояние.

### Шаг 2 — разведка «что уже сделано, что нет»

Проверяю:
- `Filesystem:list_directory_with_sizes` на корне репо и docs/.
- Состояние файлов из plan'а прошлой сессии — есть / нет / изменён?
- `docs/archive/_pending_delete/` для понимания, что уже произошло с архивацией.

Разведка = 5–10 вызовов list_directory + read_text_file (head/tail). До этого ничего не пишу.

### Шаг 3 — восстановление из Project Knowledge snapshot

Project Knowledge snapshot индексирует все текстовые файлы в репо на момент выполнения. Имея имя потерянного файла:

```
project_knowledge_search query="имя_файла заголовок первая строка"
```

Даёт фрагменты. Для больших файлов (больше 30 KB) нужно 5–15 search'ей по секциям для полного восстановления — рискованно и дорого. Лучше: если файл был записан на диск прошлой сессией до прерывания — он должен быть на диске, виден через list_directory.

### Шаг 4 — чёткий расклад Игорю

Перед тем как двигаться — даю Игорю расклад:
- Что прошлая сессия **уже сделала** на диске (с именами файлов).
- Что осталось сделать.
- Что утрачено без возможности восстановления (binary, патчи без индексации в Project Knowledge).
- Какие вопросы к Игорю блокируют продолжение (например формулировки которые он помнит по смыслу).

До того как Игорь ответит — **пишу только безопасные операции** (move_file в archive, write_file новых файлов без конфликта). Рискованное (переформулировка решений, перепись CURRENT_TASK с нуля) — ждёт его подтверждения.
