# ARCHITECTURE_3LEVELS.md — три уровня навигации в BodgeGene

> **Дата:** 09.05.2026.
> **Статус:** утверждённое архитектурное решение (DEC-NAV-3LEVEL-01, кандидат в ⚓).
> **Зачем этот файл:** ответить на вопрос «где биолог проектирует, где смотрит историю, где правит одну плазмиду» — раз и навсегда, чтобы спеки M-C / M-E / M-G не пересобирали эту развилку каждый раз.

---

## Главная идея

Биолог задаёт три разных вопроса в три разные минуты работы:

1. **«Откуда взялся этот штамм?»** — глядя на проект через месяц.
2. **«Как соединить эти куски в одну плазмиду?»** — планируя сборку.
3. **«Что у меня внутри этой плазмиды?»** — ковыряя одну конкретную.

Если силой загнать все три в один интерфейс, какой-то из ответов получится плохо. Поэтому BodgeGene разводит их на три уровня — **макро**, **мезо**, **микро** — и явно описывает переходы между ними.

Один объект  «сборка» имеет **два представления для разных задач**: в DAG — как мульти-входной узел/ребро (откуда пришло, куда ушло), в парт-канвасе — как лента блоков (что с чем стыкуется). Это не два разных объекта, а один с двумя ракурсами. То же самое биолог уже видит в архитектуре Library + DAG («два режима одного компонента»).

## Открытие проекта = клик по заголовку

В BodgeGene **нет отдельной операции «открыть проект»**. Загрузка `.bodge` в библиотеку и его открытие — всё это одно и то же действие.

**Принцип:**
- Импорт `.bodge` (через drag-drop, file picker, AddModal) → проект появляется в Library Tree разделе `📦 *.bodge` и **сразу становится активным**. Биолог видит DAG в правой панели. Никакого «импортировал, нужно ещё открыть».
- Клик по заголовку любого проекта в Library Tree → этот проект становится активным (открывается в DAG справа). Прошлый активный автосохраняется в IndexedDB.
- Свободный режим («без проекта») — это зона `⎀ БЕЗ ПРОЕКТА` в Tree, биолог может работать в ней без выбора проекта вообще (импорт плазмид, разбор записей, без привязки к `.bodge`).

**Что исчезает из UX:**
- Кнопка «Открыть проект» как отдельная операция — **убирается**. Остаётся только «Импортировать .bodge» и «+ Создать проект» (пустой новый .bodge).
- «Импорт без открытия» как отдельный режим — **не нужен**. Импорт всегда открывает. Если биолог не хочет работать в импортированном — он кликает по другому заголовку в Tree.
- Отдельного экрана «Открыть» в StartScreen — не нужно. Биолог попадает или на свободный режим, или на последний активный проект (из PWA-state).

**Что изменяется в коде** (ориентир для M-X.7b/M-E):
- `librarySlice.openProject(id)` и `import.bodge` → оба зовут один внутренний `activateProject(id)`. Импорт — это `import + activate`. Клик по заголовку — только `activate`.
- `currentProjectId` остаётся как single source of truth, но меняется по клику на заголовок.
- Перед сменой активного проекта — флаш текущего в IndexedDB (это уже есть через PWA autosave).
- Multi-tab guard (`navigator.locks` в M-A.1) не ломается — он работает на уровне «одна вкладка на .bodge», а не «один проект открыт одновременно».

**Что это даёт биологу:**
- Абсолютно одна логика доступа ко всему — Tree слева. Кликнул — получил. Нет «файл → открыть → выбрать» в два-три шага.
- Совпадает с эпистемологией «.bodge = коробочка биолога» — биолог не «открывает коробочку» отдельным жестом, он «берёт её с полки» одним движением.
- «Проект» как сущность в UI сводится к `заголовок + DAG внутри`. Не «workspace», не «scope» — просто ячейка в Tree.

**Милстоун:** реализация в рамках R4 или отдельного мини-спринта (Tree группировка по `projectId` + click handler на заголовок). Совпадает с хвостом «Tree группировка по `projectId` — выкорчевать `entry.zone`» из очереди после Sidebar.

## Уровень 1 — DAG. Карта проекта

**Что отвечает:** «как из того, что было, получилось то, что есть».

**Сущности:** узлы = контейнеры (плазмиды, фрагменты), рёбра = операции (мутагенез, рестрикция, Gibson, Golden Gate, лигирование, KLD). Мульти-входовые узлы естественны: Gibson из четырёх фрагментов = четыре ребра, сходящихся в один узел.

**Семантика DAG — read-only.** Биолог **не рисует рёбра пальцем** и не двигает узлы для смысла. Структура графа появляется автоматически как **следствие** действий на других уровнях:
- Импорт плазмиды → новый узел.
- Подтверждение сборки в парт-канвасе → новое ребро + новый узел.
- Мутагенез в Container Window → новое ребро + новый узел.

Auto-layout (dagre LR). Биолог может перетащить узлы пальцем для эстетики — это локальная косметика, не правка проекта.

**Что биолог делает в DAG напрямую:**
- Drag-drop файла плазмиды (`.gb`, `.dna`, `.fasta`) → импорт, новый узел в зоне «без проекта» или текущего проекта.
- Кнопка «+ Сборка» на палитре → открывается **парт-канвас** (Уровень 2).
- Двойной клик на узел плазмиды → открывается **Container Window** (Уровень 3).
- Двойной клик на ребро сборки → открывается **парт-канвас с готовой сборкой** (можно пересмотреть / переделать).
- Контекстное меню на узле: переименовать, дублировать, удалить, экспортировать, добавить в Library.

**Базовая реализация уже есть:** `components/Dag/` (M-C.1 K4) — DagPalette + PreviewDrawer + DagCanvas + PlasmidNode + NeutralEdge. Сейчас держит только PlasmidNode. M-C/M-E расширят типами рёбер-операций.

## Уровень 2 — Парт-канвас. Редактор сборки

**Что отвечает:** «как соединить эти куски в одну плазмиду».

**Не отдельное окно.** Парт-канвас открывается **поверх DAG как модальный слой / fullscreen-overlay** с одним кликом «закрыть» (Esc) → возврат в DAG. Это не новый workspace, биолог не теряется в навигации. Принцип «пара кликов» (CHAT_PLAYBOOK §17 R2) соблюдён.

**Точки входа:**
- «+ Сборка» в DAG-палитре → пустой парт-канвас, биолог затаскивает контейнеры из палитры справа.
- Двойной клик по ребру сборки в DAG → парт-канвас с уже собранной лентой, можно пересмотреть метод, переставить блоки, поменять праймеры.

**Лента блоков.** Контейнеры выложены в ряд (для линейных сборок) или в кольцо (для круговых). Между соседними блоками автоматически появляется **узел-стык** (junction). Биолог двигает блоки — стыки пересчитываются.

**Логика стыковки автоматическая** (это то самое из v0.5, что биологу нравилось):
- Концы блоков имеют тип (sticky overhang `EcoRI`, blunt, custom overlap-region длиной N).
- По паре концов BodgeGene **сам предлагает метод стыковки**:
  - sticky end + комплементарный sticky → ligation,
  - blunt + blunt → KLD или blunt ligation,
  - custom overlap (Gibson tail) → Gibson или overlap PCR,
  - типизированные оверхенги BsaI/BsmBI → Golden Gate.
- Если у пары концов несколько валидных методов — биолог выбирает в junction-блоке (выпадайка с двумя-тремя вариантами).
- Если методы несовместимы — junction подсвечен красным с подсказкой «нужно сначала подровнять конец / добавить tail».

**Праймеры рождаются здесь.** При выборе Gibson биолог видит на стыке нужные пары праймеров, может прокинуть их в OligoManager (заказать), может пометить как «использовать существующий из библиотеки».

**Подтверждение сборки** (кнопка «Собрать» внизу):
- В DAG появляется новый узел = плазмида-результат + рёбра от каждого входного контейнера к новому узлу через метку метода (Gibson / Golden Gate / RE).
- Если биолог пересматривал существующую сборку и поменял план — DAG **обновляет** соответствующее ребро (или создаёт новую версию узла, если изменения сильные — это решение M-E дорабатывает).
- Парт-канвас закрывается, биолог в DAG.

**Что переиспользуется из v0.5 (через harvest):**
- `JunctionBlock.jsx` 29 KB + `JunctionDNA.jsx` 14 KB — 8 типов junction (overlap/Gibson, golden_gate, re_ligation, ligation, kld, sticky_end, blunt, preformed). **Алгоритм выбора метода по концам — забирается, UI переписывается.**
- `golden-gate.js`, `restriction-db.js`, `tm-calculator.js`, `local-primer-design.js` — алгоритмическое ядро остаётся как есть.
- `OligoManager.jsx` 13 KB — реестр праймеров со статусами заказа. Подключается к парт-канвасу через «использовать существующий праймер».

**Что НЕ переиспользуется:**
- `DesignCanvas` + `PartsPalette` + `PartsLibrary` + `PartBlock` + `AddFragmentModal` — старый drag-drop холст v0.5 на kill в Этапе 3. UI парт-канваса пишется заново в современном стиле.

**Milestone:** M-E (по roadmap `ARCHITECTURE_v2.md` §7 — «mix workspace»). Текущее имя в roadmap «mix workspace» уточнить до «assembly editor / парт-канвас» при апдейте `ARCHITECTURE_v2.md`.

## Уровень 3 — Container Window. Редактор контейнера

**Что отвечает:** «что у меня внутри этой плазмиды и как её изменить».

**Точка входа:** двойной клик по узлу плазмиды в DAG **либо** двойной клик по записи в Library Tree.

**Содержимое:**
- В центре — `SequenceView` (тот самый универсальный, который уже работает в Library Inspector / Importer / Annotator Preview).
- Боковая панель / footer — **harvest workflows** из v0.5 wizards: мутагенез, рестрикционное клонирование, Gibson «использовать как backbone», Golden Gate.
- Каждый workflow завершает работу созданием **нового узла в DAG** (мутант → новая плазмида) или **нового ребра в DAG** (рестрикция → два контейнера-фрагмента).

**Что переиспользуется из v0.5:**
- `PlasmidUseWizard.jsx` 39 KB — 10 режимов операций. Игорь: «частично переиспользуем».
- `MutagenesisWizard.jsx` 18 KB — site-directed mutagenesis 4 метода.
- `mutation-normalize.js`, `region-types.js`, `color-palette.js` — harvest из FragmentEditor (Этап 2).
- `PrimerPanel.jsx` 9 KB — отображение праймеров с категориями.
- `ProtocolTracker.jsx` 31 KB — лабораторный протокол (PCR / purification / assembly).

**Milestone:** M-C.2 (по roadmap). Базовая `ContainerWindowPlaceholder` в `Dag/` уже есть как заглушка drill-in. M-C.2 заменит на реальное.

## Точки входа — карта переходов

```
                     [файл .gb/.dna/.fasta drag-drop]
                                  ↓
                     ┌─────────── DAG ────────────┐
                     │ макро-карта проекта        │
                     │                            │
                     │   "+ Сборка"               │
                     │       ↓                    │
                     │   [Парт-канвас]  ←─ модаль │
                     │   мезо: соединить блоки    │
                     │   ↑ подтверждение → новое  │
                     │     ребро + узел в DAG     │
                     │                            │
                     │   [двойной клик на узел]   │
                     │       ↓                    │
                     │   [Container Window]       │
                     │   микро: правка плазмиды   │
                     │   ↑ операция → новое       │
                     │     ребро + узел в DAG     │
                     │                            │
                     │   [двойной клик на ребро]  │
                     │       ↓                    │
                     │   [Парт-канвас с готовой]  │
                     │   пересмотр существующей   │
                     └────────────────────────────┘
                                  ↑
                     [Library Tree запись]
                       (двойной клик → Container Window)
```

Все переходы — **один клик** или **двойной клик**. Возврат — Esc или close-кнопка → возврат в DAG. Биолог никогда не «теряется в шести окнах».

## Праймеры

Праймеры **не висят узлами в DAG** — это загрязнение макро-карты. Для биолога праймер — расходник, не этап проекта. Но они **визуально обозначаются** на DAG — биолог должен сразу видеть, где они нужны, без drill-in в парт-канвас.

**Где праймеры живут как данные:**
- `librarySlice` — primer entries как `LibraryEntry` с `kind: 'primer'`. Согласовано с `entry.kind` (DEC-LIB-K4-MULTIIMPORT-01).
- **Library tab «Праймеры»** — View, агрегация над всеми primer entries проекта (всех зон). Список со статусами заказа, Tm, длиной, использованиями.

**Где праймеры видны на DAG (визуальные хвосты):**

- На ребрах сборки (Gibson, Golden Gate, overlap PCR), где входящие фрагменты амплифицируются PCR'ом с праймерами, на входной стороне ребра (ближе к исходному фрагменту) **рисуется маленький боковой отросток — утыкающаяся сбоку олиго-стрелочка**.
  - Один отросток = одна пара праймеров (P1+P2 forward+reverse).
  - Иконография — две мелких стрелки «→ ←» в боковой плашке (визуальная метафора PCR-пары).
  - На макро-zoom — только иконка. На hover ребра / mid-zoom — всплывают имена пар (P1/P2). На close-zoom / drill-in в парт-канвас — полные детали.
- Клик по отростку → открывается этот праймер в Library tab «Праймеры» (или панель справа с деталями — по паттерну PreviewDrawer в DAG).
- Статус «не заказан / заказан / получен / плохой» из OligoManager выражается цветом отростка (серый / оранжевый / зелёный / красный). Биолог видит «эту сборку ещё нельзя делать — праймеры не получены» без открытия деталей.

**Где праймеры видны в парт-канвасе (полные детали):**
- В junction-блоке между двумя фрагментами — явно «Gibson, P1+P2» / «Golden Gate, BsaI tail = ATCG» с кликабельными именами.
- Биолог может «использовать существующий из библиотеки» — picker открывается, выбор из Library «Праймеры».
- При подтверждении сборки новые primer entries попадают в `librarySlice` и в OligoManager со статусом «не заказан».

**Итог:** праймеры — ресурс уровня проекта (не узлы графа), но **визуально явно обозначены** в DAG боковыми отростками-иконками на ребрах. Согласуется с архитектурой Игоря «Library праймеров = View, не Zone».

## Хранение в `.bodge`

**Отдельного файла DAG в `.bodge` нет.** DAG — это представление, выводящееся из того же набора данных, что и остальные уровни. Хранить его отдельно — значит иметь два источника правды и риск расхождения. Согласно архитектуре Игоря «commits-DAG is primary; commit = edge» — каждый commit и есть ребро DAG.

### Что лежит в zip

1. **`project.json`** — id, name, tags, currentProjectId, agents.
2. **`containers.json`** — все `MoleculeContainer` (плазмиды + фрагменты + промежуточные). Каждый контейнер хранится в одном из двух режимов:
   - **Полный** — `payload: { sequence: '...', annotations: [...] }`. Используется для листьев DAG (импортированные плазмиды, базовые backbone) и в первых версиях (пока baseSnapshot не появился).
   - **Diff** — `payload: { parentContainerId, ops: [...] }`. Используется для **версий плазмиды** (мутагенез, manual edit, copy-on-write по DEC-LIB-K7-VERSION-COW-01). Хранит ссылку на parent контейнер + массив ops из одноимённого commit’а. Sequence вычисляется при открытии как `parent.sequence` + apply ops.
   - Поля вне payload (общие для обоих режимов): `id`, `name`, `topology`, `version`, `origin`, `addedAt`.
   - **Обоснование:** без diff-storage 50 итераций мутагенеза одной 10 kb плазмиды дают пол МБ на одну ветку (50 × 10 KB × 2 раз на baseSnapshot+commits). С diff-storage — один полный baseSnapshot + 50 × ~200 байт операций. **Это решает проблему раздувания `.bodge` в активных проектах.**
   - **Согласовано с существующим в v0.7.1:** на уровне fragment уже есть `baseSnapshot` + `commits[]` с replay. На уровне `MoleculeContainer` тот же паттерн распространяется на сериализацию. Lazy migration: импортируемые до v0.9 `.bodge` без diff-режима остаются в полном режиме, новые версии создаются в diff.
3. **`entries.json`** — все `LibraryEntry` (контейнеры + праймеры через `kind: 'primer'`). Это «вид» над containers + primers с тегами и фолдер-путями.
4. **`commits.json`** — массив операций (рёбер DAG):
   - `id`, `createdAt`, `note?`
   - `inputs: containerId[]` — входящие контейнеры/фрагменты
   - `outputs: containerId[]` — созданные контейнеры
   - `method: 'gibson' | 'golden_gate' | 'restriction' | 'mutagenesis' | 'kld' | 'ligation' | 'overlap_pcr' | 'cloning'`
   - `params: {...}` — метод-специфичные параметры
   - `primers: primerId[]` — используемые праймеры (для PCR-операций, отсюда рисуются боковые отростки на рёбрах)
5. **`layout.json` (опционально)** — пользовательская косметика:
   - `nodes: { containerId: { x, y, collapsed? } }` — позиции узлов, перекрывают auto-layout.
   - `groups: [{ id, name, containerIds, color? }]` — пометки «эта группа — про экспрессию».
   - Если биолог ничего не двигал — файл не создаётся. Расхождение с реальным графом не страшно — не нашёл containerId в графе → игнорируется.

### Как DAG строится при открытии `.bodge`

1. Для каждого `MoleculeContainer` — узел графа.
2. Для каждого `commit` — рёбра от `inputs[]` к `outputs[]`. Если commit мульти-входный (Gibson из 4 фрагментов) — рисуется узел-операция в середине с 4 входящими рёбрами и 1 исходящим.
3. Auto-layout (dagre LR) считается заново каждый раз. Биолог не ждёт сохранения позиций.
4. Если есть `layout.json` — перезаписывает auto-позиции для совпавших containerId; рисует группы-овалы.

### «Конечная плазмида»

Это узел DAG, **который не является input ни в одном commit**. То есть в графе у него нет исходящих рёбер. **Вычисляется, не помечается флагом.** У проекта может быть несколько таких узлов (несколько конечных конструктов в одной коробочке) — это нормально.

Реверс-инженерия «как получить эту плазмиду» — обход графа от terminal-узла назад по `inputs`, до листьев (импортированные плазмиды, у которых нет commits-источников). Это и есть вся история.

### Что это даёт

- **Биолог открывает `.bodge` — видит DAG.** Ничего в fixed-state не хранится, невозможно «рассинхронизировать» граф с данными.
- **Одна и та же плазмида-backbone участвует в двух сборках** — два commits с одним и тем же input. Естественно для DAG (ветвление из одного узла).
- **Версии плазмиды** (DEC-LIB-K7-VERSION-COW-01) — новый container с `origin.parentEntryId` + тривиальный commit «version» с этим parent как input. В DAG это отдельное ребро «версия». Никакого специального механизма.

## Открытые вопросы (на M-E проектирование)

1. **Версионирование сборки.** Биолог открыл существующую сборку, поменял метод (Gibson → Golden Gate). DAG обновляет существующее ребро **или** создаёт новый узел-версию плазмиды? Лезвие: первое чище визуально, второе сохраняет историю принятых решений. Скорее второе с возможностью «удалить старую версию», но проектировать в M-E.

2. **Циркуляризация.** Лента в парт-канвасе линейная. Если сборка круговая — последний блок стыкуется с первым через дополнительный junction. UI: круговое размещение на холсте **или** линейное с явной меткой «circularize: end→start»? Биолог решит при первом use.

3. **Multi-step протоколы.** Реальный wet-lab часто двух-этапный: сначала PCR-амплифицировать фрагмент, потом Gibson. В парт-канвасе это **одна сборка с PCR-шагом** или **две связанные сборки в DAG**? Скорее второе (DAG это и показывает: два ребра последовательно), но требует ясного UI «это PCR, это Gibson, они связаны».

4. **Параллельное редактирование Container Window.** Биолог открыл плазмиду, начал мутагенез, вышел не сохранив. Состояние теряется или хранится как «черновик ребра» в DAG? Скорее черновик с явной плашкой «не подтверждено».

## Связь со спринтами kill

Эта архитектура **не блокируется** Этапами 2/3 kill, но и **не требует их завершения**. Логика junction'ов в `JunctionBlock`/`JunctionDNA` — изолирована от старого холста, harvest можно делать параллельно сносу. Реальная разработка парт-канваса (M-E) лучше идёт после M-C.2 (Container Window) — потому что Container Window определит API harvest workflows, который M-E будет переиспользовать.

**Порядок реализации:**
1. **Этапы 2 + 3 kill** — снос старого верстака. Junction-логика остаётся.
2. **R4 + Этап 4 kill** — добиваем impórter.
3. **M-C.2 Container Window** — двойной клик на узел DAG → SequenceView + harvest wizards. Здесь оживают Mutagenesis / Restriction / etc.
4. **M-E Парт-канвас** — двойной клик на ребро / «+ Сборка» в DAG → лента блоков с junction-логикой. Здесь оживают JunctionBlock harvest.
5. После M-E парт-канвас и Container Window закрывают цикл проектирования: биолог из DAG может и создать новую сборку, и заглянуть внутрь любого контейнера.
