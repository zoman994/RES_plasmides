# WALKTHROUGH — Overlap-PCR тестовый прогон (23.05.2026)

> Живой UX-прогон по v0.8.3-alpha. Игорь ведёт приложение по шагам, Chat
> диагностирует по коду. Цель прогона — overlap-PCR сборка двух фрагментов:
> F (linear, 456 bp) + кусок SttH плазмиды (район lacI, 1083 bp).
> Прошли путь целиком: создание проекта → импорт (файл + вставка текстом)
> → канвас → редактор сборки → авто-праймеры overlap-PCR → Realise as DAG
> → возврат на канвас (материализованный DAG).
>
> Этот файл — реестр находок «чтобы не забыть». Баги мигрируют в `BUGS.md`
> (V-номера присвоит миграция), UX/продуктовое — в бэклог, тип-C спека §E —
> ставится в очередь после визуальной приёмки V102.

---

## Итог прогона одной строкой

Машинерия overlap-PCR собрана **корректно** (геометрия сборки, overlap-хвосты,
тип op-группы, DAG из 2 PCR + junction + продукт по смыслу верен). Стадия
primer-design — **сознательный черновик** (фикс-binding 20 нт, Wallace-Tm) и она
**не помечена как черновик** в UX. Путь от проекта до DAG проходим, но содержит
разрывы между «слоями» (проект → канвас → редактор сборки), устаревший расчёт Tm
в одном модуле, раскол двух систем праймеров (op-группы vs assemblyDrafts) и
нечитаемую авто-раскладку DAG после realise.

## A. Баги (кандидаты в BUGS.md)

### WT-B-1 — `parseFasta`: заголовок и сиквенс в одной строке → пустая последовательность
**Severity: средний.** `parseFasta` (`file-import.js`): любая строка, начинающаяся
с `>`, целиком уходит в заголовок (`name = line.slice(1).trim().split(/\s+/)[0]`,
остаток отбрасывается). Если пользователь вставляет `>F1 ACGT...` одной строкой
через пробел — вся строка считается заголовком, `seqParts` пуст, `sequence=''`,
`parseFile` бросает «No sequence found in file».
**Фикс (двойной):** (1) `parseFasta` — если после имени в `>`-строке идёт
ACGT-подобный остаток, не отбрасывать его; ИЛИ минимум (2) `parseFile` — при
пустом `sequence` из `.fasta`-вставки прогнать текст как сырой ACGT
(`sanitizeSequence`). Сейчас синтетический файл вставки назван `pasted.fasta`,
поэтому фолбэка на raw нет, хотя модалка обещает «авто-определение plain ACGT».

### WT-B-2 — вставка текстом теряет common-features
**Severity: средний.** `enrichWithCommonFeatures` вызывается только в
`handleFileImport`. Путь вставки (`LibraryWorkspace.importFiles` → голый
`parseFile`) обогащение **пропускает**. Импорт файла обогащается, вставка — нет.
Подтверждено: F встал «456 bp · linear» без features.
**Фикс:** common-features детект гонять всегда (и файл, и вставка). Связано с §C.

### WT-B-3 — `primer-derive.js` считает Tm по Wallace (рассинхрон с SantaLucia)
**Severity: средний (биология).** Полная тип-C спека — §E. Кратко: авто-праймеры
overlap-сборки получают `tm` из локальной `tmEstimate` (`4·GC+2·AT`, Wallace),
тогда как весь остальной проект — SantaLucia NN (`tm-calculator.js`). Один и тот
же праймер показывает разный Tm в панели «Праймеры» и в редакторе праймера (K13).

### WT-B-4 — несогласованный перехват хоткеев
**Severity: низкий.** Ctrl+F на канвасе **не перехвачен** — срабатывает браузерный
поиск, строку поиска канваса пришлось открывать мышью. При этом Ctrl+R **в окне
выбора фрагмента перехвачен корректно** (создаёт праймер, перезагрузки нет).
Приложение рекламирует Ctrl+R как хоткей в подсказке панели праймеров, но
Ctrl+F не ловит. Нужен аудит хоткеев: одни перехвачены, другие нет,
предсказуемости для пользователя нет. Потери данных НЕ обнаружено.

### WT-B-5 — счётчик покрытия границ не обновляется
**Severity: низкий.** Вкладка «Границы» показывает «границы 0 / 1 покрыты» даже
после генерации 4 праймеров через «Auto-собрать». Индикатор покрытия не
пересчитывается при появлении праймеров стыка.

### WT-B-6 (нужна проверка кода) — счётчик «КОНТЕЙНЕРЫ · N» в редакторе сборки
**Severity: низкий, не подтверждён.** Счётчик «КОНТЕЙНЕРЫ · N» в правой панели
редактора сборки показывал последовательно 3 → 2 → 3; ни одно значение не сходится
чисто с наблюдаемым (сегментов в сборке 1→2, контейнеров на канвасе 2). Лейбл не
сообщает scope подсчёта. Требует чтения кода панели редактора сборки до вердикта —
**не диагностировано, гадать не стал.**

### WT-B-7 — диалог «Realise as DAG» игнорирует выбранный метод op-группы
**Severity: высокий.** При «Realise as DAG» диалог на каждую границу предлагает
метод через `suggestMethodForBoundary` (`assembly-realise-suggest.js`). Его
детектор праймеров `getBoundaryPrimerInfo` ищет праймеры только легаси-формы — в
`state.assemblyDraftPrimers[draftId]` со `source.kind === 'boundary'`. Праймеры,
созданные «Auto-собрать» через `deriveAutoPrimers` (`primer-derive.js`), имеют
другую форму — `origin.kind === 'auto-from-group'`, поля `source` у них нет.
Детектор их не видит → `hasPrimer:false` → дерево решений проваливается в дефолт
`gibson` (low). Диалог не читает `opGroup.kind` вообще, хотя op-группа уже имеет
тип Overlap PCR.
**Симптом:** в редакторе сборки op-группа = «Overlap PCR», а диалог «Реализовать»
по умолчанию предлагает Gibson — два места одного экрана противоречат. Подпись
«Рекомендуется: gibson (low) — по умолчанию (Gibson — самый общий)» — это
буквально текст fallback-ветки `suggestMethodForBoundary`. Нажатие «Реализовать»
без ручного переключения радио → реализация как Gibson, выбор Overlap-PCR молча
теряется. (Биологической катастрофы нет — Gibson и overlap-PCR оба работают на
25-нт overlap-хвостах; теряется протокол/интент дизайна, не молекула.)
**Корень:** тот же раскол двух систем, что у WT-B-3 — op-группы + `primer-derive.js`
(новое) vs assemblyDrafts + `assembly-primer-utils.js` (старое). Realise-путь
подключён к старой системе.
**Фикс:** диалог realise / `suggestMethodForBoundary` должны читать `opGroup.kind`
существующей группы как первоисточник — если группа есть, её метод и есть выбор,
эвристика не нужна. Либо `getBoundaryPrimerInfo` расширить на форму
`deriveAutoPrimers` (`origin.kind === 'auto-from-group'`).
**Не верифицировано:** честно ли `realiseAssembly` (`zone-pieces-to-dag.js`)
применяет ручной выбор радиокнопки — Chat этот модуль не читал, отдельный вопрос.

### WT-B-8 — нечитаемая авто-раскладка DAG после realise
**Severity: средний.** После «Realise as DAG» и возврата на канвас граф собран
**содержательно верно** (цепочка: `Сборка 1-frag-1` 1083 bp ──overlap──
`Сборка 1-frag-2` 456 bp → 2 ноды PCR `pcr_SttH плазмида` / `pcr_F` →
`Сборка 1-product` 1539 bp → ромб `overlap_pcr_product`), но раскладка нечитаема:
- **дубли входных нод** — `F` отрисован дважды двумя почти совпадающими
  накладывающимися карточками (контейнер-с-канваса и F-как-вход-DAG, видимо,
  разные ноды); вероятно то же с SttH;
- **наложение карточек** — карточки наезжают друг на друга (`Сборка 1-product`
  под `pcr_F`, две `F` перекрыты);
- **нечитаемые рёбра** — длинные кривые связи пересекают полполотна, идут через
  несвязанные ноды; и это всего 2 фрагмента — на 5–6 кусках будет каша;
- **ромб `overlap_pcr_product` «…настройте операцию»** разнесён с собственной
  нодой-продуктом `Сборка 1-product`.
**Корень не диагностирован** — не читал код раскладки DAG (`canvas-layout` /
`zone-pieces-to-dag` рендер). Гипотезы (дубли = контейнер vs DAG-вход; авто-layout
не отрабатывает на материализованных нодах) требуют проверки по коду.

## B. UX-находки (в бэклог)

### WT-UX-1 — стартовый экран не раскрывает возможности
Не показывает, что инструмент умеет; «Создать проект» продублирован (сайдбар +
баннер); онбординг-подсказка указывает на векторы, а не на пользовательские
фрагменты.

### WT-UX-2 — `ProjectInfoModal`: Save/Cancel на уже созданном проекте
Глаголы неверные (проект уже создан); форма метаданных блокирует первый контакт.
Лучше: создать + сразу внутрь проекта, переименование inline.

### WT-UX-3 — два дерева в одном виде
Проект + «свободный стол биолога» отрисованы двумя деревьями в одном виде; лейбл
«свободный стол» непонятен.

### WT-UX-4 — три неразличимых «Новый проект» в радиокнопках `AddModal`
Секция «Куда добавить» — три строки «Новый проект», отличаются только оранжевой
точкой 4px (текущий проект). Resolution записей нечитаемый.

### WT-UX-5 — правая панель пуста после импорта
Нет «показать импортированное», нет подсказки «добавь сюда первый фрагмент».

### WT-UX-6 — textarea вводит в заблуждение
Пробел после `>F` визуально выглядит как перенос строки (word-wrap textarea),
а парсер видит одну строку. Прямой источник WT-B-1 для пользователя.

### WT-UX-7 — `AddModal` не показывает и не даёт выбрать топологию
Топология назначается молча: plain ACGT всегда → linear (через `parseFasta`).
Верно для линейного фрагмента, но **молча неверно**, если вставить сырую
последовательность кольцевой молекулы. Нужен явный тумблер linear/circular
(дефолт linear для вставки) + показ выбранного.

### WT-UX-8 — `AddModal` без поля имени для headerless-вставки
Вставка ACGT без `>`-заголовка → контейнер с именем «imported». Нужно поле имени
либо подсказка «добавь `>name`».

### WT-UX-9 — заголовок `AddModal` «в библиотеку» при цели «проект»
Заголовок «+ Добавить в библиотеку», а цель по умолчанию — активный проект.
Заголовок не соответствует действию.

### WT-UX-10 — «Открыть проект» — неочевидный хук на канвас (§17)
Кнопка «Открыть проект» — единственный и крупный primary-баттон на экране, где
проект уже открыт. Глагол не соответствует действию (ведёт на сборочный канвас).
Нарушение §17. Переключение Дерево↔Канвас должно быть явными режимами/табами.

### WT-UX-11 — канвас V2 не гидрируется из проекта
`CanvasSkeleton` — изолированный workspace (свой `SkeletonProvider` useReducer,
снапшот `canvas-state-v1::projectId`). При первом открытии канваса проекта снапшота
нет → канвас пуст, хотя в проекте 2 контейнера. Контейнеры заносятся вручную через
строку поиска (секция «Из проекта» в выдаче есть). **Переходы между слоями не
наследуют операнды:** проект → поиск на канвасе → поиск в редакторе сборки = три
раза вручную добавляешь одни и те же контейнеры. Это из 8 известных дублей
(Library-вид vs canvas-вид).

### WT-UX-12 — на канвасе нет пути «контейнер → PCR»
Видны операнды и «+ Сборка»; standalone-операция убрана (AE-K9). Путь к ПЦР —
только через «+ Сборка» → редактор сборки. Неочевидно.

### WT-UX-13 — расхождение модели «контейнер на канвасе = сборка»
Игорь ожидал: контейнер на канвасе = уже сборка. Код: сборка = зона, создаётся
только явно через «+ Сборка» (`assembly-zone-create.js`). Контейнеры на канвасе —
просто операнды. **Нужна сверка:** либо модель сознательно изменилась
(унификация 18.05 «Только зона»), либо это регресс от того, что проектировалось.

### WT-UX-14 — «Tm» показывается для фрагмент-размерных выделений
Селектор «Выбор фрагмента» показывает «Tm» для любого выделения; код считает Tm
только для участков ≤150 п.о. Но 150 п.о. — всё ещё не праймер. Tm осмысленна
только для олигонуклеотидов праймерного размера (~18–50 нт). Биолог в overlap-PCR
может прочитать «Tm 77°» как «отжиг норм». Решение: показывать Tm только для
праймер-размерных выделений, либо подписывать «Tm участка».

### WT-UX-15 — лейбл «метод» в селекторе фрагмента вводит в заблуждение
«метод: undefined / cursor» — это способ ВЫДЕЛЕНИЯ (курсор/фича/RE-сайт), а
читается как способ ДОБЫЧИ (PCR/рестрикция). **Сама отложенность способа добычи —
модель ВЕРНАЯ** (праймер overlap зависит от соседнего куска, до второго фрагмента
способ неопределим). Проблема только в лейбле — переименовать.

### WT-UX-16 — вкладка «Границы» неинформативна
Почти пустая панель: строка «SttH плазмида → F» + стрелки. Не показывает ни
overlap, ни состояние стыка содержательно.

### WT-UX-17 — overlap-Tm не считается и не показывается
Код берёт overlap-хвост фикс. 25 нт (`OVERLAP_LEN`), но Tm перекрытия (отжиг
ампликонов друг на друга) не считается нигде — ни числа, ни проверки «>50°».
Для overlap-PCR это самостоятельный параметр стыка. (25-мер по NN почти всегда
>50° даже при низком GC — значение скорее ОК, отсутствует показ/контроль.)

### WT-UX-18 — авто-праймеры не помечены как черновик; binding фикс. 20 нт
`deriveAutoPrimers` берёт binding фиксированно 20 нт (`BINDING_LEN`), длина не
подгоняется под целевую Tm (~58–62°). AT-богатый конец F → праймер ~48°. Код САМ
помечает это как placeholder в докстринге (доводка — в редакторе праймера K13,
там полная NN-модель), но **в UX нигде не помечено** — биолог видит 4 готовых
праймера с Tm и может уйти в синтез. Нет ни флага «черновик», ни предупреждения
«48° вне рабочего диапазона». Для препаративной наработки разброс Tm терпим (не
блокер), но 48° стоит переписать руками.

## D. Что подтвердилось ВЕРНЫМ (зафиксировать, не трогать)

- **overlap-хвосты праймеров биологически корректны.** `primer-derive.js`:
  fwd-хвост = последние 25 нт предыдущего куска **дословно** (forward-праймер на
  верхней цепи), rev-хвост = `reverseComplement` первых 25 нт следующего куска
  (reverse-праймер на нижней цепи). Известный баг `overlapTail` (RC-инверсия
  overlap-конвенции) **НЕ выстрелил.** Проверено числом: junction-праймер
  `asm-fwd-2` хвост = `CATCGTATAACGTTACTGGTTTCAC` = конец SttH-сегмента дословно,
  без RC.
- **Тип op-группы = «Overlap PCR»** — корректный kind, как и нужно (создаётся
  «Auto-собрать» верно; проблема только в том, что realise-диалог его не читает —
  WT-B-7).
- **DAG собран содержательно верно.** После realise: 2 ноды PCR + junction
  (overlap) + продукт 1539 bp. Логика overlap-PCR в графе правильная (проблема —
  только в раскладке, WT-B-8).
- **Tm считается по binding-области, не по всему праймеру.** `makePrimer` ставит
  `tm` из `tmEstimate(binding)` (binding без хвоста). Проверено: `asm-fwd-2` 70° =
  Wallace на 20-мере binding. (Модель расчёта при этом неверная — см. WT-B-3 — но
  по правильной области.)
- **Топология вставки plain ACGT → linear** — корректно (через `parseFasta`).
- **Трансформация `AddModal`** (источник → inline-textarea, без нового окна) —
  хороший паттерн.
- **Графика селектора фрагмента** (выделение по фиче, диапазон start/end, RC) —
  отрабатывает корректно.

## E. Тип-C спека — Wallace → SantaLucia в `primer-derive.js`

> Решение Игоря (23.05.2026): «SantaLucia везде, Wallace убиваем как метод
> расчёта». Тип C (правка primer-design — алгоритмическая зона §3) → реализует
> Code. **В очередь ПОСЛЕ визуальной приёмки V102** (сейчас `CURRENT_TASK.md`
> занят V102). Эта секция самодостаточна — переносится в `CURRENT_TASK.md`
> при постановке в работу.

### Срез размеров
`primer-derive.js` — 6.14 KB. Под лимитом `.js` (hard 25 / soft 20). Декомпозиция
не нужна.

### Контекст / корень
В проекте сосуществуют две модели Tm:
- `tm-calculator.js` — SantaLucia 1998 NN (ΔH/ΔS nearest-neighbor + поправки
  соль/Mg²⁺ Owczarzy 2008). Канонический Tm. Экспорт `calcTm` = `calcTmNN`.
- `primer-derive.js` — локальная `tmEstimate` (`4·GC + 2·AT`, Wallace). `makePrimer`
  ставит `tm: tmEstimate(binding)`.

Авто-праймеры overlap-сборки («Auto-собрать») получают Tm по Wallace, мимо
`tm-calculator.js`. Тот же праймер в редакторе праймера (K13) показывается по NN —
**один праймер, два разных Tm в двух местах UI.** Это рассинхрон, не просто
«грубо».

Проверено Chat'ом, что NN уже используется в: `tm-calculator.js`,
`operation-pcr-bridge.js`, `assembly-primer-utils.js` (все импортят `calcTm`).
**НЕ прочитан** Chat'ом `local-primer-design.js` (v0.5 primer-core) — докстринг

### WT-B-6 — счётчик «Контейнеры · N» — ПОДТВЕРЖДЁН (баг, низкий; фикс = лейбл + дедуп, не пересчёт)

`AssemblySidebar` получает `containers={state.containers || []}` и показывает
`list.length` — число контейнеров в `state.containers` с непустым `sequence`
(плюс name-filter, если в поле что-то вписано). `state.containers` —
**глобальный пул контейнеров скелета**, не scoped ни на зону, ни на «ноды на
канвасе», ни на «сегменты этой сборки».

Пул РАСТЁТ:
- `AssemblyShellBody.onRangeConfirm` (entry-путь) на КАЖДУЮ вставку сегмента из
  библиотечного entry зовёт `addContainerFromEntry(entry)` → `+1` контейнер.
  Два сегмента — `+2`. Один и тот же entry дважды — всё равно `+2`
  (дедупа нет, материализуется свежая копия каждый раз).
- `realiseAssembly` добавляет `+3` (2 frag + 1 product для 2-сегментной сборки).
- Плюс drag-drop, `OP_EXECUTE` outputs.

→ Счётчик считает пул, пухнущий на каждой вставке сегмента и на realise. Это не
«контейнеры проекта» ни в каком смысле, который биолог отслеживает. «Ни одно
значение не сходится» — верно, оно и не должно. Точную тройку 3→2→3 по
walkthrough'у восстановить нельзя (per-step state не записан, гадать не стал —
§0.3 playbook'а), но механизм «пул растёт на каждый entry-insert + realise»
полностью объясняет нестыкующийся счётчик. Уменьшение возможно только через
`REMOVE_CONTAINER` либо набранный filter.

Сопутствующий настоящий баг (кормит и WT-B-6, и WT-B-8): `onRangeConfirm`
материализует НОВЫЙ контейнер на каждую вставку из entry без дедупа.

Фикс — не пересчёт, а продуктовое решение «что панель должна считать» (по функции
она — плоский drag-source список всех контейнеров). Дефолт-рекомендация: честный
лейбл / убрать счётчик из header'а + расследовать дедуп `addContainerFromEntry`
(смыкается с V52 и реестром 8 дублей). Severity низкий — счётчик косметический.

### WT-B-8 — раскладка DAG после realise — ДИАГНОСТИРОВАН (не баг layout-алгоритма — архитектурный: realise чисто аддитивен)

`handleAssemblyRealise` (`skeleton-state.js`): `containers:[...baseContainers,
...diffContainers]`, `operations:[...state.operations,...diffOperations]`.
Докстринг сам пишет «old entities are NOT auto-deleted». Realise **ничего не
удаляет**. После realise зона держит ОДНОВРЕМЕННО:
- свой piece-граф (исходные pieces сборки никуда не делись);
- op-группу «Overlap PCR» (создана «Auto-собрать», `zoneId=draftId`);
- T8 auto-reactions (финализатор `applyAutoReactions` по `piece.acquisitionMethod`);
- + новые realise-ноды: 2 PCR-опа + 2 frag-контейнера + 1 product-контейнер +
  2 junction.

T4.5 `applyZoneLayouts` лейн-пакует ВСЁ это в 3 дорожки одной зоны → каша
наложений. Ромб `overlap_pcr_product` «разнесён» с `Сборка 1-product`, потому
что ромб — **старая** сущность (op-группа либо T8 auto-reaction, realise её не
трогает), а `Сборка 1-product` — новый контейнер из realise-диффа.
`realiseAssembly` производит только `kind:'pcr'`-опы — никакого
`overlap_pcr_product`-опа в диффе нет.

«F отрисован дважды» — `realiseAssembly` для каждого sourced-сегмента кладёт
frag-контейнер с `sequence:seg.sequence` (срез без overlap-хвостов; хвосты в
`userPrimers`). PCR-оп при этом `inputs:[seg.source.containerId]` → указывает на
ИСХОДНЫЙ контейнер. Итог: исходный `F` (456 bp) + `Сборка 1-frag-2` (456 bp,
побайтово та же ДНК) — две почти идентичные карточки. Не глитч раскладки —
realise по построению материализует near-дубликат входа.

«Длинные кривые рёбра» — `handleAssemblyRealise` НАМЕРЕННО не затягивает
исходные контейнеры в зону (комментарий: grow-only T4-bounds раздуло бы зону).
Realise-опы лейн-пакованы внутри зоны, их `inputs` — исходные контейнеры —
лежат свободно вне зоны. Ребро op→source соединяет внутри-зонную ноду с
вне-зонной → длинная связь через полполотна, by construction.

Вывод: WT-B-8 — не «починить auto-layout». Realise = аддитивный дифф поверх
зоны, которая УЖЕ полностью представляет сборку (pieces + op-группа +
T8-реакции). Layout честно рисует вдвое больше нод, чем должно. Тот же раскол
двух систем, что у WT-B-3/B-7. Настоящий фикс — realise либо замещает
piece-граф зоны DAG'ом, либо realise-DAG живёт когерентно (и исходники
затягиваются/ссылаются чисто). Архитектурный разбор, не layout-патч.
`positionsLayout` сам примитивен (фикс-сетка `STEP_X=280`, `baseY=480`,
единственная коллизия-проверка — сдвиг блока на 200 вниз) — но это вторично:
даже идеальная сетка не спасёт, пока зона несёт два представления одной сборки.

Побочно (хвост WT-B-7): `RealiseModal.confirm` → `actions.realiseAssembly(draftId,
methods)`, `realiseAssembly` использует `perBoundaryMethods[i]` в
`junctionForMethod` → ручной выбор радиокнопки честно применяется. «Не
верифицировано» из WT-B-7 закрыто: realise уважает выбранный метод; баг WT-B-7
только в том, что *дефолт* радио (`suggestMethodForBoundary`) садится в gibson,
не читая `opGroup.kind`.
