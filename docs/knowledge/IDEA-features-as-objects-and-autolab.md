## 1. Исходная идея — фичи как объекты, «ООП против C», замена в 2 клика

**Игорь (verbatim):**
> «а еще можно расширить функционал фичей - не просто аннотация а так сказать "обьектно ореинтированное програмирование против C". когда работаем с нуклеотидами это C а вот можно тыунть на фичу и нажать заменить на... и там список промоторов которые есть в нашей базе (но тут вопрос откуда брать промоторы? можно из других контейнеров можно из свободного стола, можно из комон фичей (ввести раздле промоторы) в общем надо проработать чтобы не перегрузить. должно быть легко и прозрачно - в общем основаня идея - фичи как явная разметка элемента и базовый таг который обозначает ее функционал. и тынуть два клика для замены»

**Синтез дизайна:**
- Два уровня редактирования: **нуклеотиды = C** (низкоуровнево, база за базой) и **фичи = ООП** (объектный уровень).
- Фича = **объект** с **функциональным классом** = «базовый таг». Базовый таг ≈ существующее поле `type` на аннотации (`promoter / RBS / CDS / terminator / ori / marker / tag / signal / operator / linker / UTR`). Цвета уже есть (`featureColor`).
- Объектная операция: тык по фиче → **«Заменить на…»** → список совместимых деталей того же класса → 2 клика → span переставлен (splice + indel-aware сдвиг нижележащих фич).
- Это превращает аннотации из пассивных подписей в **детали-объекты**, взаимозаменяемые как Lego (модульное клонирование как прямое манипулирование, без визарда).

### Откуда брать детали — единый **Part Index** (главный вопрос Игоря)
Не три места, а **один типизированный пикер**, агрегирующий 3 источника:

| Источник | Что | Доверие | Статус в коде |
|---|---|---|---|
| 1. Common Features (курируемые) | каталог; добавить **разделы по классам** (Промоторы/Терминаторы/RBS/Маркеры/Таги) | verified | `CommonFeaturesPanel` + `promoteFeature` **уже есть**; common-features уже несут `type` + `sequence` + длину (в тестах есть `{name:'lacP', type:'promoter', sequence}`) |
| 2. Из контейнеров | любая аннотация класса X в любой записи библиотеки авто-доступна как деталь | «из pUC19» | derived-индекс из `libraryEntries[].annotations` |
| 3. Свободный стол (loose) | то же для неразложенных | derived |

**Принцип против перегруза:** каталог деталей **дерив, а не ручной** — инструмент индексирует детали, что уже существуют в твоих данных. Пикер: фильтр по классу + группировка по источнику (курируемые сверху) + поиск + метаданные (имя · длина · дельта `+40 bp` · источник). «Закрепить как деталь» поднимает находку в Common Features (`promoteFeature`).

**Ключевой вывод:** «откуда брать промоторы» по большей части **уже решено** — Common Features и есть типизированный каталог; не строим новый, переиспользуем существующий раздел.

### Механика замены
- Splice = `replace` через `applySequenceEditToEntry` (**уже** indel-aware: сдвигает нижележащие фичи на `len(новая)−len(старая)`).
- **Strand-aware**: фича на `−` → вставляем revcomp детали.
- Под-фичи детали (−10/−35 у промотора) переносятся со сдвигом.
- Провенанс: замена = 1 операция → 1 commit → кормит blame/семантический-diff/таймлайн.
- Undo: это sequence-edit → уже покрыт undo-движком.

## 2. Система классов деталей — «свой язык ООП» с жёсткими правилами

**Игорь (verbatim):**
> «и смотри тогда нам надо написать свой язык ООП который позволит задавать новые классы и делать базовые операции. т.е. пока что унас нет жестких правил, а без жестких правил мы обречены ошибаться, и менять плохотразмеченные фичи на плохо размеченные фичи.»

**Синтез дизайна:**
- **Развилка:** НЕ писать парсер/DSL (месяцы + баги). «Язык ООП» = **декларативный реестр классов + валидатор**. Даёт силу типов (классы, наследование, методы, проверка экземпляра) без языка как такового. Текстовый DSL — опциональный сахар потом.
- **Класс детали = запись-данные** (расширяемая через UI/JSON):
  ```
  promoter { rules:{strandMatters,minLen,mustNotContain,…severity} interface:{upstreamOf:[RBS,CDS], role} ops:[replace,disable,duplicate,reverse] extends: part }
  CDS      { rules:{ lenMod3:ERROR, startATG:WARN, noInternalStop:ERROR, strand:required } }
  tag      { rules:{ inFrameWithHost, noStop, lenMod3 } extends: part }
  ```
- Три эффекта:
  1. **Annotation-health линтер** — ловит плохую разметку («помечено CDS, но длина не ×3 и есть внутренний стоп → не CDS»). Прямой ответ на боль Игоря: система отказывается считать кривую фичу валидной деталью.
  2. **Type-checked swap** — пикер показывает только валидные детали класса; кандидат, не прошедший свои правила → предупреждение; на стыке проверяются рамка/цепь.
  3. **Грамматика сборки** — `interface` задаёт «что за чем» (promoter→RBS→CDS→terminator); питает линтер и батч.
- **Жёсткое vs мягкое (критично):** правила несут **severity** — `error` (однозначная биология: рамка, цепь, внутренний стоп) **блокирует**; `warn` (эвристика: сила промотора, наличие −10/−35) **сигналит, но пропускает**. Сохраняет «expert mode always ON»: блокируем только неоспоримое.
- Встраивание: **апгрейд существующего `type`** в тип с контрактом; **миграция через health-pass** (разовый прогон по библиотеке → список «починить разметку», кривое перестаёт молча быть деталью). Опирается на `annotation-contract`, `cds-validation`, `restriction-db`/`orf-detection`, `featureColor`, `CommonFeaturesPanel`.
- **Один реестр питает всё**: swap + линтер + ассерты + батч. Не три системы — одна онтология.

## 3. Режим «Автолаборатория» — массовая комбинаторная генерация

**Игорь (verbatim):**
> «Еще идея массовая генерация плазмид, когда ты прям батчем предлагаешь менять промоторы из твоей билиотеки и исразу генерируются 10-20 сборок с разными промотороами и полным протоколом. это отдельный режим замены, мы не будем его вписывать в текущийсборщик и ДАГ (это оставим для более ручного и дизайнерского подхода) то что я предлагаю - это скорее путь в сторону автоматизации и "автолаборатории.."»

**Синтез дизайна (отдельный режим, НЕ в DAG):**
- Поток: базовый конструкт → **переменный слот(ы)** (тык промотор → набор кандидатов из библиотеки; можно `promoter × RBS × CDS` = матрица) → **генерация N вариантов**.
- На каждый вариант: splice (type-checked) + **валидация** по правилам класса/грамматике (невалидные комбо отсеиваются) + **праймеры + полный протокол** + **worklist / plate-map**.
- Выход: набор вариантов (записи библиотеки / variant-set) + сводный протокол + пиклист.
- **Endpoint автоматизации (оригинальность «автолабы»):** экспорт батча в **робот** — Opentrons-протокол / Echo picklist / CSV-worklist. Дизайн→робот для маленькой лаборатории почти никто не делает (j5/DIVA — foundry, дорого/облако).
- **Провенанс по батчу**: каждый вариант = версия с происхождением → blame/diff/таймлайн работают по всему батчу (20 commit'ов с родословной, а не 20 безымянных файлов).
- **UX:** таблица/матрица (строки=варианты, колонки=слоты+метрики валидности/размера/Tm), выбор множеств + «Сгенерировать», зелёные/красные строки по валидности. Не канвас.

## 4. Как всё композится
```
Система классов (онтология, §2)
   ├─→ Annotation-health линтер   (ловит плохую разметку ДО swap)
   ├─→ Type-checked swap в 2 клика (§1)
   └─→ Batch / Автолаба (§3): только валидные комбо → протокол → робот
```
Тип-система = **единственный источник правды**, делающий безопасными и одиночную замену, и массовую генерацию. Порядок строго: **классы → swap → batch**. В обратном — автоматизация ошибок.

## 5. Фазы (чтобы не перегрузить)
1. **Реестр классов + валидатор + annotation-health линтер** (фундамент; виден сразу — подсветка кривых фич).
2. **Type-checked swap в 2 клика** (поверх common-features-как-деталей).
3. **Грамматика (`interface`) + Batch-режим** (комбинаторная матрица + протокол).
4. **Robot-export** (Opentrons/Echo) — «автолаба» endpoint.

## 6. Открытые решения
- Severity, не жёсткий отказ (`error` блокирует только однозначное; остальное `warn`).
- Реестр = данные (`part-classes.js`/JSON) + слайс; новые классы через UI; наследование (`extends`); без парсера.
- Миграция через health-pass (не молчаливая).
- Грамматику — фазой 2 (swap/линтер работают без неё; нужна батчу для осмысленных комбо).

## 7. Стратегически
Сдвиг категории: из **«редактор плазмид»** в **«типизированную среду проектирования + автолаборатория»**. Тип-система делает автоматизацию доверенной; batch + robot-export делают её *автоматизацией*. Ни один из 6 проанализированных конкурентов (SnapGene, Benchling, Geneious, free-tier, Plasmidsaurus, вендоры) не идёт этим путём для маленькой лаборатории.

## 8. Опора в коде (что переиспользуется)
`CommonFeaturesPanel` + `promoteFeature` (типизированный каталог деталей, уже есть) · annotation `type` + `annotation-contract` · `applySequenceEditToEntry` (indel-aware splice) · `cds-validation`/`orf-detection`/`restriction-db` (правила классов) · `featureColor` · Plasmid-Git (провенанс per-variant) · primer/Tm + protocol-export (батч-протоколы).
