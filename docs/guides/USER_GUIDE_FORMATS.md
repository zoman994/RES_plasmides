# BodgeGene — Форматы файлов: .bodge и .bodgebox

Гайд для пользователей. Версия 0.8.0, май 2026.

---

## Коротко

BodgeGene использует два своих расширения. Оба — открытые форматы поверх стандартного GenBank.

| Что | Расширение | Что внутри | Совместимость |
|---|---|---|---|
| Весь проект | `.bodge` | ZIP с N плазмидами + DAG-история сборок + праймеры + библиотека | Распаковывается как `.zip`, внутри обычные `.gb` файлы |
| Одна плазмида | `.bodgebox` | Один `.gb` файл с историей мутаций в COMMENT | Переименуется в `.gb` — открывается в SnapGene / ApE / Geneious / BioPython |

Главное: **никаких проприетарных форматов**. Если у коллеги нет BodgeGene — он откроет ваш файл в своём привычном инструменте. Потеряется только специфическая для нас информация (история сборок, граф проекта). Последовательность, аннотации, primers — на месте.

---

## Зачем два формата

Биолог работает на двух уровнях. Один — проект целиком: связанные между собой плазмиды, праймеры, реакции, история «откуда что взялось». Этот уровень живёт в `.bodge`. Второй — отдельная плазмида: вектор, мутант, конструкт, которым делятся с коллегой или отправляют в репозиторий. Этот уровень живёт в `.bodgebox`.

Аналогии из других программ:
- SnapGene: проект `.dna` — один файл на плазмиду; общего «проектного» формата у них нет.
- Benchling: проекты живут в облаке, файла как такового нет.
- ApE: только `.gb` / `.gbk`, проектная структура отсутствует.

Мы делаем `.bodge` ровно потому, что отдельные плазмиды на диске разлетаются: «где-то у меня был тот клон с GFP и His-tag, или это был mCherry?». Проектный файл собирает их с историей.

## .bodgebox — одна плазмида с историей

Это валидный GenBank-файл. LOCUS, FEATURES, ORIGIN — всё по стандарту NCBI. История мутаций и провенанс упакованы в structured COMMENT блок:

```
COMMENT     ##BodgeGene-Provenance-START##
            schema      :: https://bodgegene.dev/schema/v1
            format      :: base64-json
            payload     :: eyJjb250YWluZXJJZCI6...
            ##BodgeGene-Provenance-END##
```

В payload (base64-кодированный JSON) лежит:
- Отпечаток исходной плазмиды (хеш baseline-последовательности).
- История правок: что мутировалось, когда, кем, в каком порядке.
- Откуда взялась эта плазмида: из импорта, из библиотеки, из сборки, склонирована из чужого проекта.
- Опционально — праймеры, привязанные к плазмиде через PrimerUsage.

Custom GenBank qualifiers, которые BodgeGene добавляет к features:
- `/bodge_id=...` — стабильный ID для round-trip identity при повторном импорте.
- `/parent_feature=...` — для sub-features (signal peptide внутри CDS, RBS внутри promoter). GenBank плоский, иерархии features не имеет; этот qualifier восстанавливает её при импорте обратно в BodgeGene.
- `/note=sequence:ATCG...` на `primer_bind` — паттерн SnapGene'а, прямое крепление primer sequence к feature. BodgeGene его читает и может предложить добавить эти praimers в библиотеку.

Все custom qualifiers — non-breaking. SnapGene / ApE / Geneious их видят, но игнорируют как незнакомые. Феатура читается как обычная.

### Когда использовать .bodgebox

- Поделиться одной плазмидой с коллегой, у которого тоже BodgeGene → он откроет с полным provenance.
- Поделиться плазмидой с коллегой без BodgeGene → переименует в `.gb`, откроет в SnapGene или ApE с sequence + features. Provenance пропадёт незаметно для него.
- Загрузить плазмиду на GitHub / в supplementary к статье. Файл публичный, читаемый стандартными инструментами, но история сборки сохранена для тех, кто заглянет в наш редактор.
- Бэкап ключевой плазмиды отдельно от проекта.

## .bodge — весь проект

Это ZIP-архив. Если переименовать в `.zip` и распаковать — вы увидите:

```
project.bodge/
├── manifest.json              ← версии формата и схемы
├── project.json               ← название проекта, теги, agent
├── containers/
│   ├── pUC19.gb               ← обычный GenBank (с COMMENT-провенансом)
│   ├── pET28a-myGene.gb
│   └── ...
├── projectCommits/            ← рёбра DAG: какие реакции связали плазмиды
│   └── *.json
├── primers/primers.json       ← пул праймеров проекта + back-refs
├── library/library.json       ← ссылки в общую библиотеку
└── refs/refs.json
```

Внутри только два типа файлов: валидный GenBank (плазмиды) и plain JSON (DAG, метаданные, праймеры). Никаких бинарных полей, никаких proprietary кодировок. Всё читается обычным текстовым редактором.

### Что произойдёт у коллеги без BodgeGene

Если ему дать `.bodge` файл, он:

1. Переименует в `.zip` (или объяснить — расширение можно менять, ZIP остаётся ZIP).
2. Распакует.
3. В папке `containers/` увидит N валидных `.gb` — открывает каждый в SnapGene / ApE / Geneious.
4. JSON-ы в остальных папках читает текстовым редактором — там видна структура проекта в plain text.

Что он потеряет:
- DAG проекта как граф (список рёбер он увидит в `projectCommits/`, но без визуализации).
- Связи «какой primer использовался в какой реакции» (PrimerUsage back-refs он увидит в JSON, но без UI).
- Историю мутаций per-плазмида он увидит сразу — она в COMMENT внутри каждого `.gb`.

Что он получит:
- Все sequences, все features, все аннотации.
- Имена плазмид, теги, описания.
- Праймеры с Tm и метаданными (в JSON).

Это как раздать GitHub-проект архивом: исходники открываются, IDE-специфичные настройки теряются. Никакого lock-in.

### Когда использовать .bodge

- Бэкап всей работы.
- Передача проекта коллеге, у которого тоже BodgeGene.
- Коммит в Git-репозиторий лаборатории (в перспективе с RO-Crate metadata для FAIR-claims в статье).
- Synchronization через cloud-папку (Google Drive Desktop / Dropbox / OneDrive). Программа про cloud не знает — для неё это локальная папка, sync-провайдер делает свою работу.

## Что говорят сторонние программы

Я тестировал основные tools на round-trip — экспорт из BodgeGene, открытие в чужой программе, ре-импорт обратно с проверкой что всё на месте.

| Программа | Видит sequence + features | Сохраняет COMMENT | Round-trip провенанса |
|---|---|---|---|
| SnapGene Viewer / Pro | да | да, byte-for-byte | да |
| ApE | да | да, byte-for-byte | да |
| Geneious Prime | да | да, byte-for-byte | да |
| BioPython `SeqIO` | да | да (через `record.annotations['comment']`) | да |
| Benchling | да | под вопросом, **тестируется** | под вопросом |
| NCBI tools (Entrez) | да | да | unused |
| pLannotate / IGV | да read-only | unused | unused |

Benchling — единственный риск. Он может «pretty-print'нуть» COMMENT (переформатировать строки для удобочитаемости), и тогда BodgeGene при ре-импорте увидит файл как «отредактированный извне» и спросит, что с этим делать. Не катастрофа, но граница известна. Для остальных tools provenance проходит touchscreen без потерь.

## Что произойдёт если изменить .gb в SnapGene и вернуть в BodgeGene

Допустим, вы экспортировали плазмиду как `.bodgebox`, переименовали в `.gb`, открыли в SnapGene и поправили там одну буквенную замену. COMMENT остался прежним — SnapGene его не трогал. Вы импортируете файл обратно в BodgeGene.

Программа сравнит хеш sequence из COMMENT-payload с хешем текущей последовательности и увидит расхождение. Покажет toast:

> External edit detected. Last BodgeGene state: 8 May 2026, 14:23.
> Current sequence differs from provenance baseline.
> [Treat as new] [Restore baseline & lose external edits]

Это не бага, а фича. BodgeGene никогда не восстанавливает историю молча, если данные снаружи изменились. Решение всегда за вами:
- **Treat as new** — плазмида импортируется как свежая, провенанс старой истории сбрасывается. Полезно если вы действительно хотели изменить sequence.
- **Restore baseline** — программа берёт baseline из payload и проигрывает commits заново; ваше внешнее изменение пропадает. Полезно если правка в SnapGene была случайной.

Симметрично с тем, как мы восстанавливаем работу после сбоя браузера.

## Граничные случаи

**Файл `.bodgebox` весит 200 KB на маленькой плазмиде.** Это нормально, если у плазмиды длинная история мутаций. Каждый ContainerCommit лежит в COMMENT-payload, и при сотне правок payload разрастается. В v0.7+ появится опция «экспорт без истории» — для случая когда хочется просто поделиться рабочим вектором без слепка процесса.

**В Benchling COMMENT превратился в один длинный текст.** См. таблицу выше. Если коллега работает в Benchling и round-trip критичен — лучше делиться через `.bodge` ZIP или плоский `.gb` без provenance, чтобы не спотыкаться о Benchling-specific переформатирование.

**Custom qualifiers `/bodge_id` и `/parent_feature` пропали.** Какой-то tool в цепочке strip'ает unknown qualifiers (редко, но бывает у старых конвертеров). При ре-импорте BodgeGene попробует восстановить parent-child связи sub-features через coordinate inclusion: если sub-feature целиком вложена в parent по координатам и того же strand, программа их свяжет. Heuristic, но работает в большинстве реальных случаев.

**Файл с провенансом v2 в BodgeGene v1.** Schema versioning — открытый вопрос для v0.7+. Сейчас единственная schema `v1`, конфликта быть не может. Когда появится `v2`, мы определимся: ломать совместимость или поддерживать миграцию.

## TL;DR в одной строке

`.bodge` — весь проект, ZIP с GenBank внутри. `.bodgebox` — одна плазмида, обычный GenBank с провенансом в COMMENT. Оба формата читаются стандартными инструментами; полная информация — только в BodgeGene; внешнее редактирование детектится при возврате.
