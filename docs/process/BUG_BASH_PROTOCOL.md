# BUG_BASH_PROTOCOL.md — ритуал сплошного обзора функциональности

> Процедурный документ. Не спека и не техдолг — под лимит «8 активных файлов в `docs/`» не попадает.
> Парный документ к `ACCEPTANCE_ALGORITHM.md`: acceptance — протокол приёмки, bug bash — протокол накопления замечаний.
> Читать Chat'у в сессиях типа bug bash сразу после стартового пакета (`CLAUDE.md` / `BUGS.md` / `CURRENT_TASK.md` / `PROJECT_STATE.md` snapshot / `DECISIONS.md` sprint-level).

---

## Зачем это нужно

Игорь при обычной работе перескакивает с задачи на задачу — это нормальная человеческая реакция на многокомпонентный проект. В ходе спринт-сессий побочные раздражения (не критичные к текущей приёмке) легко теряются или записываются криво, в неправильное время. Chat в ответ на побочные замечания в середине acceptance тоже соскальзывает в их анализ, теряя фокус.

Решение — выделенное время, когда цель ровно одна: **систематически пройти по всем основным сценариям приложения и накопить замечания**. Ничего не чинить, ничего глубоко не обсуждать.

Делается не регулярно, а **по запросу** — когда Игорь чувствует «накопилось» или Chat видит в последних сессиях много UX-записей без системы.

---

## Формат сессии

**Подготовка Chat:** стартовый пакет (`CHAT_PLAYBOOK` → `CLAUDE` → `BUGS` → `CURRENT_TASK` → последняя запись `PROJECT_STATE`) + **этот файл**. Ничего больше. В `src/` не лезу вообще.

**Первое сообщение Игоря:** «Bug bash, начинаем». Chat:
1. Переписывает `CURRENT_TASK.md` в заготовку bug bash (чек-лист сценариев + счётчик V-записей + дата) — шаблон ниже.
2. Ждёт первый скрин / первое замечание.

**Ход Игоря:**
- Открывает приложение в браузере.
- Идёт по сценариям **подряд**, не прыгая (см. чек-лист ниже).
- На каждое «не нравится / странно / не работает» — одно сообщение Chat'у: короткое описание + скрин + привязка к сценарию («это в контексте мутагенеза»).
- **Не починяем ничего** даже если очевидно как. Записали → следующая точка.
- **Не переключаемся на другие типы задач.** Если вдруг «а добавь фичу» — стоп, это новая сессия после bug bash.

**Ход Chat:**
- На каждое замечание — **одна короткая черновая запись в BUGS.md** в новую секцию `### Bug bash DD.MM.YYYY — drafts (требуют приоритизации)` в конце OPEN-секции. Формат:
  ```
  - [ ] V-N DRAFT: {описание в словах Игоря, не парафраз}.
    Контекст: {сценарий из чек-листа}. Скрин: {если есть}. {дата}.
  ```
- Приоритет в драфте **не ставлю** — это делается в финальной фазе.
- Корневой анализ не делаю. Не критикую формулировку. Не отговариваю от записи («это же не баг»). Если формулировка совсем неясна — спрашиваю уточняющий вопрос строго по факту («где именно — в sequence view или в белок-панели?»), не больше.
- Подтверждаю одной строкой: «Записал V-N». Всё.

**В конце сессии (по инициативе Игоря «всё, хватит»):**
Chat в одном длинном сообщении:
1. Проходит по всем V-N DRAFT, **каждому** присваивает приоритет (CRIT/HIGH/MED/LOW) и категорию (UX / алгоритм / регрессия / feature-request).
2. **Группирует связанные** — если две-три записи про одно и то же (например, три про circular map разбивку меток) — объединяет в одну с подпунктами.
3. Переформулирует в финальный BUGS-формат с точным файлом/строкой где очевидно.
4. Обновляет `RELEASES.md` (без version bump — bug bash это документационный milestone): дополняет текущий версионный блок (или добавляет documentation milestone-секцию по аналогии с M-B Kickoff) записью «bug bash DD.MM.YYYY: N сырых → M финальных записей, распределение по приоритетам».
5. Возвращает `CURRENT_TASK.md` в заглушку «Нет активной задачи» или к предыдущему состоянию.
6. В сводном сообщении предлагает Игорю: (а) взять 1–3 записи в hotfix следующей сессией, (б) сгруппировать часть в новый спринт UX Polish, (в) оставить всё в OPEN и вернуться позже.

## Чек-лист сценариев (обновляется по мере роста продукта)

Минимальный обход, соответствует основным user-flow:

1. **Создание плазмиды.** Каталог SnapGene → выбрать → В библиотеку → на canvas.
2. **Визуализация плазмиды.** Circular map, sequence view, annotation bar, RE labels.
3. **Правка фрагмента.** FragmentEditor в mode=Правка: добавить/удалить nt, переименовать аннотации.
4. **Мутагенез in-place (KLD).** Одна мутация на standalone circular.
5. **Мутагенез in-place split.** 3+ замены далеко друг от друга, split-группа.
6. **Мутагенез через Wizard.** Open Wizard из PlasmidViewer → template → мутации → результат.
7. **Restriction cloning.** Wizard 3 шага, insert + backbone, ligation junction preview.
8. **Assembly на canvas.** 2+ фрагмента, Gibson/GG, расчёт праймеров, protocol view.
9. **Project Flow (DAG).** Создать multi-step из Construct → переключение на Flow view.
10. **Экспорт.** GenBank, протокол, заказ олигов.

Не обязательно проходить все за одну сессию — можно зафокусироваться на 2–3 сценариях. Но **внутри одного сценария** идём до конца, не бросаем на середине.

```markdown
## Когда закончим

Игорь пишет «всё, хватит». Chat:
1. Приоритизирует и группирует все V-N DRAFT.
2. Дополняет `RELEASES.md` (без version bump — documentation milestone) записью «bug bash DD.MM.YYYY: N сырых → M финальных».
3. Возвращает этот файл в прежнее состояние.
4. Предлагает план по дальнейшим действиям.
```

## Парное правило: обработка отвлечений в НЕ-bug-bash сессиях

Это дополняет bug bash — не заменяет. В обычной сессии (спека, приёмка, реализация, планирование) если Игорь бросает побочное «а ещё не нравится X»:

1. **Chat фиксирует одной строкой в `BUGS.md` OPEN** как `V-N DRAFT` с пометкой «упомянул в контексте {текущая задача}, DD.MM.YYYY».
2. **Chat подтверждает одной строкой:** «Записал V-N как draft, вернёмся при bug bash или когда соберём UX Polish спринт».
3. **Не разматывает подробное обсуждение.** Глубокий анализ побочного замечания в середине acceptance — это классический провал фокуса.
4. **Возвращает внимание к текущей задаче** одной фразой: «По блоку M — продолжаем, жду следующего скрина».

**Исключение (BLOCKER):** если побочное замечание блокирует текущую задачу (в acceptance всплыла регрессия ключевой фичи, в спеке обнаружилась принципиальная ошибка архитектуры) — STOP текущей задаче, явно констатирую «это блокер, записываю как {приоритет CRIT}, возвращаемся к {текущая задача} только после принятия решения по нему».
