# Workflow разработки BodgeGene

Этот файл дополняет `AGENTS.md`. Если правила противоречат друг другу, действует `AGENTS.md`.

## 1. Классифицировать запрос

- **Вопрос/ревью:** только чтение и доказательный ответ.
- **Диагностика:** воспроизвести и назвать корень; код не менять без запроса на исправление.
- **Bugfix:** один симптом, regression-test, минимальный фикс.
- **Feature:** user story, data-contract, UX-вход, integration-тесты и явные границы.
- **Refactor/cleanup:** доказать эквивалентность или отсутствие потребителей; не добавлять функции.
- **Визуальная приёмка:** browser smoke и проверка пользовательского сценария, без нового спринта.

## 2. Один рабочий документ

Только `CURRENT_TASK.md` хранит активный чеклист:

- цель и границы;
- допущения;
- K-шаги;
- acceptance gates;
- итоговые доказательства и отклонения.

Полная спецификация нужна только для новой сложной подсистемы или внешнего формата. Она живёт в `docs/specs/`, а `CURRENT_TASK.md` ссылается на неё, не копирует тело.

## 3. Перед изменением

1. Прочитать минимальный контекст из `AGENTS.md`.
2. Проверить текущий Git/status и незавершённые изменения пользователя.
3. Найти реальные consumers через imports, routes, registries, workers и runtime strings.
4. Загрузить доменный skill.
5. Зафиксировать baseline relevant tests и размер файлов в soft/hard зоне.

## 4. Реализация

Для поведения: RED → GREEN → related tests → full verification.

Для удаления dead code:

1. доказать отсутствие production-consumers;
2. проверить dynamic/lazy imports и fixtures;
3. удалить одну связанную группу;
4. запустить tests/build;
5. если тест падает — определить регрессию, а не переписывать тест под удаление.

Баг, найденный вне scope, записывается одной строкой в `BUGS.md`; улучшение — в `docs/BACKLOG.md`.

## 5. Handoff

Итоговый отчёт должен отвечать на пять вопросов:

1. Что изменилось?
2. Что это даёт биологу?
3. Какой риск устранён и какой остался?
4. Чем результат доказан?
5. Что сознательно не проверено?

Обязательные доказательства по применимости:

- RED→GREEN или обоснование удаления dead code;
- focused/related tests;
- полный test/build для завершённого пакета;
- browser smoke для пользовательского UI;
- `git diff --check`;
- size-budget;
- точный список отклонений от задачи.

Не называть браузерным доказательством harness-тест. Не скрывать флейки: указать файл, симптом и результат изолированного повтора.

## 6. Bug bash

Каждая находка проходит состояния:

`наблюдение → воспроизведено → причина подтверждена → BUGS.md → исправлено → regression-test`.

Не переносить предположение как подтверждённый баг. Биологически неоднозначное поведение останавливается до выбора конвенции.

## 7. Приёмка

Результат принят только когда проверен пользовательский сценарий, а не отдельный компонент:

- правильная сущность открывается;
- данные сохраняются и восстанавливаются;
- ошибки не маскируются пустым результатом;
- клавиатура, мышь и screen-reader получают одну семантику;
- нет console errors;
- нет скрытого downgrade биологической точности.

После приёмки актуализируются только текущие документы. Отчёты прошлых итераций не накапливаются.
