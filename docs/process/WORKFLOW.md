# Workflow разработки BodgeGene

Этот файл дополняет `AGENTS.md`. Если правила противоречат друг другу, действует
`AGENTS.md`.

## 1. Три AI-роли

### Ревизор

Ревизор — единственный центр решений внутри согласованных владельцем границ. Он:

1. проверяет предложение по живому коду, тестам, спецификациям и инвариантам;
2. принимает, отклоняет, паркует или возвращает на уточнение идеи Креативщика и
   пользователя;
3. переносит подтверждённый результат в один первичный канонический tracker;
4. пишет для Кодера один bounded-пакет в `CURRENT_TASK.md`;
5. проверяет frozen candidate, выдаёт не более одного correction pass;
6. запускает финальный gate и принимает либо отклоняет пакет.

Ревизор не пишет product code и не смягчает вывод ради согласия. Отклонение содержит
факты, риск и безопасную альтернативу. Владелец может вернуть предложение с новыми
данными или явно изменить контракт, но такое изменение фиксируется до реализации.

### Креативщик

Креативщик ищет проблемы и возможности, предлагает пользовательские сценарии и варианты
дизайна. Он читает код и референсы, но не меняет product code, `CURRENT_TASK.md`,
`BUGS.md`, `docs/BACKLOG.md` или `DECISIONS.md`. Результат — одна отдельная запись в
`Совместная работа ИИ/Идеи/`, а не готовое задание Кодеру.

### Кодер

Кодер реализует только пакет из `CURRENT_TASK.md`. Он не выбирает идеи из входящих, не
расширяет manifest и не меняет контракт. Для high-risk proof, seam split или независимой
альтернативы Ревизор может назначить второй экземпляр роли Кодер в отдельном worktree;
proof-writer и ответственный за интеграцию остаются назначениями одной роли Кодер.

### Воспроизводимый запуск

Запуск начинается из checkout, чей `HEAD` уже равен принятому base:

```powershell
git rev-parse HEAD
git status --short
git worktree list
claude --agent reviewer
claude --agent creative
claude --agent coder
claude --worktree <unique-name> --agent coder
claude --agent reviewer-readonly
```

Первые три Git-команды выполняются до любой правки. `HEAD` обязан точно совпасть с
base SHA, а dirty-state — с объявленным allowlist; иначе `STOP`. Единственный Кодер
работает в назначенном checkout. Второй экземпляр Кодера запускается отдельным
foreground-процессом в уникальном worktree. Независимые read-only линзы роли Ревизор
запускает владелец или внешний orchestrator; ведущий Ревизор не порождает writers.

## 2. Сквозная история

`Совместная работа ИИ/` — Git-tracked слой provenance между ролями:

- `Идеи/` — IDEA-предложения Креативщика или владельца;
- `Аудиты/` — AUD-доказательства Ревизора;
- `Референсы/` — REF-снимки внешних обзоров и исходных материалов;
- `Решения/` — отдельные DISP-решения ведущего Ревизора.

Это не второй backlog и не источник разрешения на реализацию.

### 2.1. Неизменяемый source

Каждый IDEA/AUD/REF имеет уникальный ID, автора/роль, дату с timezone, branch/base SHA и
при необходимости candidate manifest/digest. IDEA/AUD помечается `NON-CANONICAL INPUT`,
REF — `NON-CANONICAL REFERENCE`; факты, выводы и непроверенное разделяются.

В момент author handoff весь source-файл замораживается навсегда. Его SHA-256 фиксируется
во внешнем handoff, а не внутри самого файла. Ни автор, ни Ревизор не добавляет в source
disposition, backlink, status или позднее уточнение. Исправление/уточнение — новый
source-файл с новым ID и парой `supersedes source path + full SHA-256`; predecessor
остаётся byte-identical. Один участник создаёт один файл, несколько агентов не ведут
общий append-журнал. `PENDING` означает отсутствие decision-файла, а не поле source.

#### REF wrapper и payload

REF-source — immutable Markdown metadata-wrapper, а не внешний payload. Wrapper обязан
содержать REF ID, `NON-CANONICAL REFERENCE`, source URL/path, snapshot date,
applicability/staleness, payload mode и полный payload SHA-256. SHA-256 самого wrapper
фиксируется внешним handoff как отдельная идентичность; payload SHA нельзя выдавать за
wrapper SHA.

Допустимы только два payload mode:

- `SIDECAR`: неизменённый локальный payload хранится отдельным exact path. Если Кодер
  использует его содержимое, `CURRENT_TASK.md` пинит и wrapper path+full wrapper SHA-256,
  и payload path+full payload SHA-256; Кодер проверяет оба.
- `POINTER_ONLY`: wrapper хранит внешний URL/path и заявленный full payload SHA-256.
  Пока байты недоступны для проверки checksum, содержимое явно `UNVERIFIED`; его нельзя
  называть frozen copy или использовать как доказанный факт.

Большие/бинарные payload не коммитятся и остаются `POINTER_ONLY`. Hidden cache и третий
payload mode запрещены. Wrapper, локальный sidecar и predecessor после handoff
неизменяемы; поздняя проверка или уточнение оформляется новым successor REF-wrapper.

### 2.2. Отдельное решение и цепочка

Только ведущий Ревизор создаёт новый immutable файл
`Решения/DISP-<SOURCE-ID>-NNN...md`. Он содержит:

- decision ID, ведущего Ревизора/экземпляр, дату и timezone;
- decision class и disposition;
- source ID, exact path и full SHA-256;
- supersedes decision ID/path/full SHA-256 либо трижды `NONE`;
- reason и canonical target со stable locator либо `NONE`.

SHA-256 текущего DISP не записывается внутрь него: после handoff его пинит
`CURRENT_TASK.md` или другой внешний handoff. Первое решение получает NNN `001` и три
predecessor-поля `NONE`. Successor обязан сохранить тот же source pin, получить
`max(existing NNN for source)+1` и сослаться на непосредственного предшественника по ID,
path и full SHA-256. Collision имени требует STOP и повторного чтения цепочки. Два
наследника одного predecessor образуют fork: STOP и решение ведущего Ревизора; выбирать
ветвь по самой поздней дате запрещено. Source и predecessor никогда не меняются и не
получают backlink.

`INPUT_TRIAGE` допускает `ACCEPT FOR TRIAGE`, `CLARIFY`, `PARK`, `REJECT`. Решение
`ACCEPT FOR TRIAGE` создаётся только после переноса содержания ровно в один первичный
tracker: дефект — `BUGS.md`, улучшение/долг — `docs/BACKLOG.md`; DISP фиксирует stable
locator. `PARK` требует stable locator в `docs/BACKLOG.md`. `CLARIFY`, `PARK` и `REJECT`
никогда не авторизуют Кодера.

`PACKAGE_REVIEW` допускает `ACCEPT`, `CORRECTION`, `REJECT`, `STOP`. `CORRECTION` может
поддержать ровно один correction manifest; `ACCEPT` закрывает пакет, а `REJECT` и `STOP`
запрещают изменения отклонённого candidate. Перед successor решения, выбранного активным
`CURRENT_TASK.md`, Ревизор сначала переводит task в STOP и получает frozen handoff
Кодера. Продолжение требует нового task, явно пинящего выбранную ветвь.

### 2.3. Выбор входа для Кодера

IDEA/AUD считается выбранным только когда `CURRENT_TASK.md` содержит полную принятую
тройку: source path+full SHA-256, подходящий DISP path+full SHA-256 и canonical
target+stable locator. Кодер проверяет оба файла, совпадение source pin и то, что
class/disposition разрешают названное использование; mismatch означает STOP. Для REF
план всегда пинит wrapper path+full wrapper SHA-256. Если реально используется
`SIDECAR`, он дополнительно пинит payload path+full payload SHA-256; Кодер проверяет оба
и не следует непинованному sidecar/pointer. `POINTER_ONLY` с непроверенным checksum
остаётся `UNVERIFIED` context. REF не авторизует scope. Кодер не сканирует папку, не
ищет `latest` и не исполняет shared input самовольно. Единственный источник разрешения
на запись — `CURRENT_TASK.md`; DISP и REF лишь доказывают provenance.

Обзор Claude становится REF только через такой wrapper и остаётся контекстом, а не
нормативным источником: живой код и тесты → нормативная спецификация → канонические
текущие документы имеют более высокий приоритет. Независимые Ревизоры не читают чужие
выводы до собственного freeze.

## 3. Классифицировать запрос

- **Идея:** Креативщик или пользователь описывает проблему/возможность; Ревизор сначала
  проверяет ценность, факты, риски и дубли.
- **Вопрос/ревью:** только чтение и доказательный ответ; подтверждённая находка не остаётся
  только в чате.
- **Диагностика:** воспроизвести и назвать корень; код не менять без отдельного пакета.
- **Bugfix:** один симптом, regression-test, минимальный фикс.
- **Feature:** user story, data-contract, UX-вход, integration-тесты и явные границы.
- **Refactor/cleanup:** доказать эквивалентность или отсутствие потребителей; не добавлять
  функции.
- **Визуальная приёмка:** browser smoke и проверка пользовательского сценария, без нового
  спринта.

## 4. Один рабочий документ

Только `CURRENT_TASK.md` хранит активный чеклист:

- цель и границы;
- принятый base SHA и writer mode;
- точные manifests/worktrees и ответственного за интеграцию Кодера;
- content-pinned ссылки на выбранные записи из `Совместная работа ИИ/`;
- для REF — отдельный wrapper pin и, при использовании `SIDECAR`, payload pin;
- допущения, acceptance и gates.

Полная спецификация нужна только для новой сложной подсистемы или внешнего формата. Она
живёт в `docs/specs/`, а `CURRENT_TASK.md` ссылается на неё, не копирует тело.

## 5. До реализации

Ревизор:

1. читает `AGENTS.md` → `CURRENT_TASK.md` → `PROJECT_STATE.md` и только релевантный
   дополнительный контекст;
2. проверяет Git/status, worktrees и незавершённые изменения пользователя;
3. проверяет входящую идею/аудит против живого кода и удаляет дубли;
4. находит production consumers через imports, routes, registries, workers и runtime
   strings;
5. загружает доменные skills;
6. фиксирует base, IN/OUT, manifest, baseline relevant tests и размеры soft/hard-файлов;
7. только затем выдаёт Кодеру `CURRENT_TASK.md`.

Следующий пакет начинается от принятого checkpoint SHA, а не из памяти чата или сырой
записи общей папки.

## 6. Реализация Кодером

Для изменения поведения: RED → минимальная реализация → focused evidence → freeze.

Для удаления dead code:

1. доказать отсутствие production-consumers;
2. проверить dynamic/lazy imports и fixtures;
3. удалить одну связанную группу;
4. запустить названные tests/build;
5. если тест падает — определить регрессию, а не переписывать тест под удаление.

Баг, найденный вне scope, передаётся Ревизору: подтверждённый дефект идёт в `BUGS.md`,
улучшение — в `docs/BACKLOG.md`. Кодер не исправляет его «заодно» и не пишет trackers,
если они не входят в manifest.

## 7. Handoff и проверка

Кодер замораживает candidate и отвечает на пять вопросов:

1. Что изменилось?
2. Что это даёт биологу?
3. Какой риск устранён и какой остался?
4. Чем результат доказан?
5. Что сознательно не проверено?

Handoff также содержит base SHA, точный manifest, digest, preserved exclusions, размеры и
число собранных tests/files. Ревизор проверяет candidate read-only, консолидирует
независимые линзы и выбирает одно из решений: `ACCEPT`, `CORRECTION`, `REJECT` или `STOP`.

После `CORRECTION` разрешён один correction pass и только одна проверка названных
исправлений. Если причина пережила correction или появилась новая корневая причина,
Ревизор останавливает пакет и пишет новый план; второй test-only pass запрещён.

Обязательные доказательства по применимости:

- RED→GREEN или обоснование docs/dead-code исключения;
- focused/related tests;
- полный test/build для завершённого пакета;
- browser smoke для пользовательского UI;
- `git diff --check`;
- size-budget;
- точный список отклонений и непроверенного.

Не называть браузерным доказательством harness-тест. Не скрывать flake: указать файл,
симптом, inventory и разрешённый протокол локализации.

## 8. Bug bash

Каждая находка проходит состояния:

`наблюдение → воспроизведено → причина подтверждена → BUGS.md → исправлено → regression-test`.

Не переносить предположение как подтверждённый баг. Биологически неоднозначное поведение
останавливается до выбора конвенции.

## 9. Приёмка

Пакет принят только когда Ревизор проверил пользовательский сценарий, а не отдельный
компонент:

- правильная сущность открывается;
- данные сохраняются и восстанавливаются;
- ошибки не маскируются пустым результатом;
- клавиатура, мышь и screen-reader получают одну семантику;
- нет console errors;
- нет скрытого downgrade биологической точности.

После решения Ревизор синхронизирует только канонические текущие документы и создаёт
новый frozen DISP, который указывает на source и canonical target. Source и предыдущие
решения не меняются. Общая папка сохраняет provenance, но не копию текущего состояния
проекта.

## 10. Переход со старых названий

`Planner` теперь называется `Ревизор`; `Implementation coder` — `Кодер`;
`candidate-reviewer` — read-only назначение роли Ревизор; `proof-coder` — proof-only
назначение роли Кодер; `Integration owner` — ответственность назначенного Кодера, а не
отдельная роль. Старые frozen candidates сохраняют исходную терминологию как исторический
контракт до явного replan; новые пакеты используют только три роли.

`PROC-3R-FREEZE` от 07.09.2026 — одноразовое bootstrap-исключение, явно разрешённое
владельцем через `CURRENT_TASK.md` по content-pinned legacy AUD. Оно исправляет только
этот процесс, не разрешает product code и не создаёт reusable route. Все последующие
IDEA/AUD проходят обычный путь source → primary tracker → DISP → `CURRENT_TASK.md`.
