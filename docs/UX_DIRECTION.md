## Корень хаоса (аудит 19.06, evidence в коде)

1. **Два роутера окон сосуществуют.** Старый `canvas.activeFullscreen` (+`navStack`, `pushFullscreen`/
   `popFullscreen`) и новый `workspace.active` (плоский). Разные callsite'ы используют разные →
   навигация непредсказуема. `start`-экран вообще байпасит `AppShell`. → ист. «нет логики окон».
2. **Настройки в 5+ местах, разные localStorage-ключи.** Глобальный `SettingsModal` (Ctrl+,),
   per-view `SettingsPopover` (⚙ внутри вкладки Sequence), inline-контролы в Аннаторе, `displaySettings`/
   `theme`/`agent`/`annotator`/`ui-sequenceview` — каждый в своём ключе. Тема правится в 2 местах.
   Порог аннотаций дублируется (Аннатор ↔ сиквенс, синхр. кодом). `polymerase` / `primer prefix` —
   мёртвые no-op, след остался.
3. **Одно действие — разные триггеры.** «Скопировать»: SequenceView — Ctrl+C / правый клик; дерево
   библиотеки — никак (контекстного меню нет); align — правый клик. «Редактировать»: где двойной клик,
   где `E`, где кнопка. `allowInInput` у hotkeys непредсказуем.
4. **Невидимые аффордансы.** Разделители панелей без «хваталки»; ⚙ виден только в одной вкладке.

## Модель данных — корень логики окон

Главная претензия Игоря: «делаем интерфейс, не держа в голове структуру файлов и сборок». Поэтому
направление НАЧИНАЕТСЯ с модели данных (выверено по коду + уточнено Игорем 19.06):

```
ПРОЕКТ (.bodge) — верхний уровень (manifest exportType:'project'; стор currentProjectId)
 ├─ СБОРКИ[] (рецепты) — много на проект
 │    входные КОНТЕЙНЕРЫ + операции  →  новый КОНТЕЙНЕР (финальный продукт)
 ├─ КОНТЕЙНЕРЫ[] (project.containerIds) — пул ДНК проекта (плазмиды/фрагменты/продукты; и входы, и выходы сборок)
 ├─ FLOW (project.dag) — граф: сборки ↔ контейнеры ↔ продукты
 ├─ ПРАЙМЕРЫ (project.primerIds), ВЕРСИИ (project.projectCommitIds)
 └─ библиотека частей · notebook · вложения (sanger/pdf/img)
```

- **Контейнер** — «вещь» (ДНК-сущность). **Сборка** — «как её получить» (рецепт: входы + операции →
  продукт-контейнер). **Flow** — карта ВСЕГО проекта (как рецепты порождают контейнеры), не «ещё одно окно».
- Активный проект уже есть в сторе (`currentProjectId`, единая точка активации), **но интерфейс его не
  показывает** → «не понимаю, какой проект выбран». Это инвариант UI: активный `.bodge` виден всегда.
- ⚠️ Вью **Flow удалён 17.06** (`DagWorkspace` снесён как dead route); данные `project.dag` живы — вернуть
  как окно проекта (TD-DEAD-DAGWORKSPACE).

## Три принципа целевой модели

### A. Оболочка: инструменты «наравне» + контекст активного проекта

Не строго два уровня. Есть **кросс-проектные инструменты** (живут наравне, не принадлежат проекту, но
project-AWARE) и **окна-атрибуты активного проекта**.

Ментальная модель Игоря (скрин NocoDB 19.06): **Лаборатория = БД с таблицами** (плазмиды, праймеры,
реестр экспериментов…). Глобальные ресурсы лаборатории переиспользуются проектами; проект ссылается на них.

- **Инструменты (наравне, кросс-проектные)** — доступны всегда, проект не обязателен:
  - **Главная** — лендинг/дашборд.
  - **Библиотека** — глобальный лаб-ресурс: части/плазмиды + все проекты (`.bodge`) + свободные элементы.
    **Импорт `.gb`/`.dna` — действие ВНУТРИ Библиотеки** (не отдельное окно). Не атрибут одного проекта;
    здесь проект выбирается/создаётся.
  - **Праймеры (пул лаборатории)** — общая таблица всех праймеров лаборатории (PR-id · имя · 5′→3′ · длина ·
    GC% · Tm/отжиг), как реестр Игоря. Праймеры, используемые в активном проекте, **видны и явно отличимы**
    (бейдж/фильтр «в проекте {имя}») от остального пула. Параллель Библиотеке: глобальный ресурс + проектный срез.
  - **Выравнивание** — инструмент над ЛЮБЫМИ последовательностями (из проекта или произвольных файлов/
    Sanger); может писать результат в активный проект (исправленная версия), но проект не требует.
  - **Аннотатор — НЕ отдельный пункт назначения**, а действие: «Аннотировать» доступно из ЛЮБОГО
    sequence-viewer (Библиотека, Выравнивание, контейнер) — нырок в аннотатор на текущей последовательности
    (см. контракт §C).
- **Активный проект (`.bodge`) — виден ВСЕГДА** (полоса контекста: имя + файл + статус сохранения +
  «сменить проект»). Его собственные окна привязаны к нему:
  - **Обзор / Flow** — граф проекта (сборки ↔ контейнеры ↔ продукты); вернуть удалённый вью.
  - **Сборки** — список рецептов; открыть сборку → редактор сборки.
  - **Контейнеры** — пул ДНК проекта.
  - **Версии**.
  - (Праймеры проекта — это фильтр «в проекте» глобального пула «Праймеры», не отдельное окно.)
- Переключение проекта перецепляет проектные окна на него; инструменты (Библиотека/Выравнивание) остаются
  на месте, просто видят новый активный проект. Это #1 фикс «не понимаю, какой проект выбран».
- **Один роутер.** Канон — `workspace.active`; `canvas.activeFullscreen`/`navStack` → депрекейт.
  **`AppShell` оборачивает ВСЁ** (включая `startup` — как состояние, не байпас).
- **Хлебные крошки** (один компонент): инструмент → объект, либо `Проект → Окно → объект`. Назад — через
  рельс/крошки, не скрытый стек.

### B. Два чётких дома настроек

| Класс | Где | Что входит | Вход |
|---|---|---|---|
| **Глобальные** (app-wide) | один `SettingsModal` | тема, профиль (имя/email), дефолты импорта (`annotateOnImport`), порог синтеза, перенос строки, сброс БД, PWA | **Ctrl+,** + пункт в меню (один вход) |
| **Настройки вида** (view-local) | одинаковый **«Вид»-gear** в КАЖДОМ вьюере, на одном месте (правый верх тулбара вьюера), один поповер-паттерн | frames-mode, цвет нуклеотидов, видимые треки (annotations / AA / RE / primers / bottom-strand), RE-ориентация, predictions | клик по ⚙ «Вид» |

- **Тема — один источник.** Либо только в Settings, либо топбар-toggle, но **синхронно** с Settings
  (не два независимых состояния). По умолчанию: оставить быстрый toggle в топбаре, но он и Settings
  читают/пишут один `theme` (уже так — убрать визуальное ощущение «двух мест», см. фазу 1).
- **Порог аннотаций — ОДНО место.** Аннатор и сиквенс читают общий порог, не дублируют слайдер.
- **Удалить мёртвое.** `polymerase`, `primer prefix` — убрать остатки/комменты, чтобы не путали
  (уже no-op; чистка следов).

### C. Единый контракт взаимодействия (везде одинаково)

| Жест | Значение (инвариант по всем поверхностям) |
|---|---|
| **Левый клик** | выбрать объект / поставить каретку |
| **Двойной клик** | редактировать (фича / имя / фрагмент / зона) |
| **Правый клик** | контекстное меню действий этого объекта (копировать / удалить / переименовать / …) |
| **Drag** | переместить / выделить / изменить размер — по контексту, **с видимой хваталкой** |
| **Hotkey** | ускоритель того же действия; глобальные — через единый реестр `hotkeys.js` с предсказуемым `allowInInput` (правило: app-навигация и сохранение `allowInInput:true`; режимные одно-буквенные `false`) |

**Кросс-вьюерные действия (одинаковая аффордансная точка в КАЖДОМ sequence-viewer):** ⚙ «Вид» (настройки
вида) + **«Аннотировать»** (нырок в аннотатор на текущей последовательности — из Библиотеки, Выравнивания,
контейнера, откуда угодно). Аннотатор — действие над сиквенсом, не отдельный пункт рельса.

Пробелы к закрытию: **контекстного меню в дереве библиотеки нет** (правый клик) — добавить; разнобой
«двойной клик vs `E` vs кнопка» для редактирования фич — свести к двойному клику как первичному.

### D. Аффордансы

- Разделители панелей (`ResizeHandle`) — видимый grabber (точки/линия) + cursor + tooltip; одинаково везде.
- ⚙ «Вид» — видим в тулбаре вьюера всегда, не только в одной вкладке.

## План реализации (пофазно)

| Фаза | Содержание | Риск | Эффект |
|---|---|---|---|
| **0** | этот документ — направление + модель данных | — | согласовано |
| **1 — Проектный контекст** ✅ | всегда видимая полоса активного проекта (имя + `.bodge` + статус + «сменить проект»), читает `currentProjectId`; перенос проектного селектора из закоулков сюда | низкий (read-only оверлей) | **прямой фикс «какой проект выбран»** |
| **2 — Логика окон** 🟡 | хлебные крошки ✅ (DEC-UX-PHASE2-01); двухуровневый рельс ✅ (DEC-UX-PHASE2-02, Инструменты/Проект-группы + «Сборки»→канвас); ещё: унификация роутера (`workspace.active` канон, deprecate `activeFullscreen`) + **вернуть Flow** как окно проекта | выше (навигация) | «чёткая логика окон» |
| **3 — Настройки** 🟡 | ⚙ «Вид» всегда в шапке инспектора ✅ (DEC-UX-PHASE3-01); дедуп порога / мёртвые / тема — **уже сделано/намеренно** (аудит: A17 + DEC-PRED-03 + UX-006) | низкий (локально) | видимый «порядок» |
| **4 — Контракт кликов** 🟡 | контекстное меню в дереве (правый клик) ✅ (DEC-UX-PHASE4-01); ещё: правый клик в контейнерах · «двойной клик = редактировать» везде · аудит `allowInInput` | средний | предсказуемость |
| **5 — Аффордансы** | grabber на разделителях + видимость ⚙ + tooltips | низкий | discoverability |

Порядок переставлен (был 1=Настройки): теперь первой — **видимость активного проекта**, т.к. это
названный Игорем корень («не понимаю, какой проект выбран»), и она даёт спину для всей логики окон.

Каждая фаза: тесты первыми → код → `npm test` → `vite build` → браузер-верификация → обновить доки
(DECISIONS / BUGS / этот файл). Порядок 1→4 — от низкого риска и быстрого видимого эффекта к
структурному. Можно переставить по желанию Игоря.

## Что НЕ трогаем (scope guard)

- Биологию / движки (assembly, align, primer design, аннотации) — только UI/IA.
- Размер модулей сверх лимитов без декомпозиции-первым-пунктом (CLAUDE.md §7).
- `SequenceView` виртуализацию (PERF-9) и прочие перф-инварианты.
