# CHAT_PLAYBOOK_CORE.md — рабочие инструкции для Claude Chat (core)

> **Назначение.** Обязательное чтение в начале каждой сессии. Содержит правила старта (§1), формата спек (§2), координации Chat↔Code (§3), классификации задач (§13) и признания предела (§14).
>
> **Справочные правила** (файловая гигиена, антипаттерны, формат ответов, recovery после прерванной сессии и т.д.) — в `CHAT_PLAYBOOK_APPENDIX.md`, грузятся по триггерам.

Этот playbook — собственные операционные правила Chat'а, написанные после разбора ошибок Sprint 1.6–1.7 и обновлённые после цикла Catalog Polish → FIX → FIX-2 (28.04.2026), потери сессии 29.04.2026, и реструктуризации 01.05.2026.

## §1. Первый ход в сессии — всегда одинаковый

**Не доверяю стартовому контексту. Ни userMemories, ни `/mnt/project/`, ни собственной памяти о проекте.** Между сессиями Code успевает нажать десяток коммитов, а snapshot отстаёт.

Последовательность при старте любой сессии про BodgeGene:

1. **Filesystem: прочитать 3 файла подряд** — `CLAUDE.md`, `BUGS.md`, `CURRENT_TASK.md`. Только эти три. Из корня репо, не из `/mnt/project/`.
2. **Сверить версию проекта.** В `PROJECT_STATE.md` шапка показывает `Версия: vX.Y.Z` (snapshot only после реструктуризации 01.05.2026). Если в userMemories написано другое — userMemories устарели, игнорирую их в пользу файла.
3. **Прочитать последнюю запись `RELEASES.md`** (~2 KB одного версионного блока) — это текущая реальность. История по сессиям до v0.6 — в `docs/archive/SESSIONS_2026_Q2.md`.
4. **Если задача требует context архитектурных решений** — читать `DECISIONS.md` (sprint-level последних 2 спринтов, 3-5 KB). Якоря — в `ANCHORS.md` (грузить только в milestone-сессиях).
5. **Не лезть в код на старте.** Код читаю только когда понял задачу и знаю, какой конкретно файл/функция нужны.

**Сессии-приёмки.** Если текущий CURRENT_TASK.md — визуальная приёмка (статус «🟡 Готов к визуальной приёмке» или заголовок «Визуальная приёмка …»), после стартового пакета дочитываю `docs/ACCEPTANCE_ALGORITHM.md`.

**Сессии Bug Bash.** Если статус CURRENT_TASK.md — «🔴 В процессе (bug bash)» или Игорь написал «bug bash, начинаем», дочитываю `docs/BUG_BASH_PROTOCOL.md`.

**Сессии Milestone v0.6+ (M-A..M-I).** Архитектура зафиксирована в `docs/ARCHITECTURE_v2.md` (~117 KB v1.2, central reference) + 48 ⚓ в `ANCHORS.md`. Roadmap v0.6–1.0 — 9 milestone'ов по окнам, не по техническим спринтам (M-A start screen, M-B importer, M-C container window, M-D editable, M-E mix workspace, M-F primer pool, M-G остальные reactions, M-H library, M-I DAG polish; ARCHITECTURE_v2 §7). Для любой milestone-сессии (как wireframe так и spec и приёмка): после стартового пакета дочитываю `docs/ARCHITECTURE_v2.md` целиком + `ANCHORS.md`. При открытых UX-развилках — `docs/UX_VISION.md` + `docs/UX_REFERENCE_BASE.md`. Код v0.5 (`gui/designer/src/`) читаю только по списку reuse'а в ARCHITECTURE_v2 §8.

Если пользователь после этого просит написать спеку — я готов. Если просит разобраться в баге — я перехожу к целевому чтению кода (один-два файла, не больше).

**Контекст-бюджет на старт (обычные сессии): ≤30 KB после реструктуризации 01.05.2026.** CLAUDE.md (~17 KB) + BUGS.md (1.5 KB) + CURRENT_TASK.md (~3 KB) + PROJECT_STATE.md snapshot (~8 KB) + DECISIONS.md sprint-level (~3 KB) ≈ 33 KB. RELEASES.md грузится только последняя запись по запросу.  
**В milestone-сессиях:** + ARCHITECTURE_v2.md (~117 KB) + ANCHORS.md (~120 KB) ≈ 270 KB — обязательный compact между milestone-сессиями.

_§1 обновлено 2026-05-01: реструктуризация документации — `PROJECT_STATE.md` стал snapshot-only (журнал версий вынесен в `RELEASES.md`), `DECISIONS.md` разделён на `ANCHORS.md` (фундаментальные ⚓) + `DECISIONS.md` (sprint-level последних 2 спринтов), `CHAT_PLAYBOOK.md` разделён на core (этот файл) + appendix._

## §2. Правила формата спек

Текущий спринт — это живой контракт между мной и Code. Цель: чтобы Code имел достаточно инструкций для точной реализации без возврата ко мне за уточнениями, и чтобы спека не съедала мой и Code-контекст.

### Ограничения

- **Целевой размер спеки зависит от типа задачи (см. §13):** тип A — 20-30 KB, тип B — 8-15 KB, тип C — 3-8 KB, тип D — без спеки.
- **Одна задача в спеке = одна цель для пользователя.** Если задача разбивается на 4 подзадачи (K9/K10/K11/K12) — это нормально, они должны логически сцеплены и давать один user-facing результат.
- **Никакого copy-paste кода больше 10 строк.** Если пишу `export function foo() { ... 40 строк ... }` — я узурпирую работу Code. Вместо этого: «новый helper `foo(args) → returns X`, логика: [нумерованный список из 3–5 шагов]».
- **Лимит размера модулей.** Перед написанием спеки на компонент/helper делаю `list_directory_with_sizes` на `gui/designer/src/components/` или `gui/designer/src/`. Файлы ≥ **40 KB** (.jsx) или ≥ **25 KB** (.js, кроме data) в зоне правки — декомпозиция входит в скоуп спеки **первым пунктом**, ещё до новой функциональности.

### Перед спекой — sanity check (3 обязательных вопроса)

До написания спеки Chat обязан ответить себе на три вопроса. Если на любой нет уверенного ответа — задаёт его Игорю до старта спеки.

1. **Как это вписывается в работу биолога?** Что биолог делает в этом workflow? Какую задачу решает? Правка ускоряет / замедляет / усложняет / упрощает его работу?
2. **Насколько решение согласуется с имеющимися продуктами индустрии?** SnapGene / Benchling / Geneious / ApE / pLannotate уже решали похожие UX-задачи. Где в них хорошо — копируем, не придумываем «лучше». Свои изобретения только там где явный gap. `docs/UX_REFERENCE_BASE.md` — стартовая точка.
3. **Решит ли правка эту проблему? Или сделает хуже / сложнее?** Какие side-effects: что становится менее доступным, какой workflow ломается, какие edge cases появляются.

### Что должно быть в спеке

0. **Срез размеров затрагиваемых модулей** (на самый верх). Если хоть один ≥ hard — п. 1 становится «декомпозиция [файл] перед новой функциональностью».
1. **Контекст (2–5 абзацев):** что сломано / чего не хватает.
2. **Стратегия (1 абзац на задачу):** одним предложением что делаем и почему.
3. **Scope — IN / OUT.**
4. **Архитектурные решения (пронумерованные):** короткие «почему именно так». Источник для DECISIONS.md / ANCHORS.md после приёмки.
5. **По задаче — файлы / сигнатура helper'ов / структура тестов.** Не сам код. Примеры тестов — 2–3 характерных, не 20.
6. **Порядок выполнения + оценка времени.**
7. **STOP-условие и формат отчёта.**
8. **Риски — 3–5 пунктов,** каждый с митигацией в одну фразу.
9. **Открытые вопросы — 2–4 пункта.**

### Что НЕ должно быть в спеке

- ~~Полная реализация helper'а~~ — это работа Code.
- ~~Полное описание 20 тестов~~ — 2–3 характерных + «плюс ~N вариаций по паттерну».
- ~~Длинные JSX-блоки с тонкими стилями~~ — структура + «стили — на усмотрение Code, design-система репо».
- ~~Подробный разбор предыдущих спринтов~~ — одна ссылка на коммит или версию в RELEASES.md.
- ~~Повтор содержимого BUGS.md~~ — ссылка, ID, точка.
- ~~Копия текущего кода «БЫЛО»~~ — только путь и ~строка плюс правило замены.

## §3. Правила координации Chat ↔ Code

### CURRENT_TASK.md — не зеркало спеки

**Оперативный чеклист**, не копия спеки. Размер: 5–10 KB.

Структура: TL;DR (3–5 строк) · порядок чтения · чеклист `[ ]` с артефактами (файлы, helpers, тесты в цифрах) · STOP-условие · формат отчёта · регрессии.

Ссылка на спеку в docs/ — да. Дублирование архитектурных решений — нет.

### Прямая правка `src/` Chat'ом — только для типа D

Базовое правило: Chat не редактирует `src/` или `__tests__/`. Эти зоны принадлежат Code. Для типов A/B/C это правило держится без исключений.

Для типа D (см. §13 — тривиальная правка ≤20 строк, без алгоритмов) Chat правит напрямую через `Filesystem:edit_file`. **Запрещённые зоны для Chat в любом типе задачи:**
- `gui/designer/src/store/**`
- `gui/designer/src/hooks/**` если содержит алгоритмическую логику (не UI)
- `gui/designer/src/lib/**`
- Алгоритмические модули корня `gui/designer/src/`: `local-primer-design.js`, `tm-calculator.js`, `golden-gate.js`, `restriction-db.js`, `mutagenesis.js`, `validate.js`, `orf-detection.js`, `auto-annotate.js`, `annotation-model.js`, `feature-palette.js`, `sequence-diff.js`
- `src/pvcs/**` (backend)
- `__tests__/**` (тесты — Code)

При прямой правке Chat в journal entry строка: «правка Chat-direct, не верифицирована тестами/билдом, следующая Code-сессия проверит регрессии».

### Формат handoff-сообщения Code

Стандартный handoff (отдаю пользователю, он пересылает Code):

> Прочитай CLAUDE.md, BUGS.md, CURRENT_TASK.md. Выполни [название спринта], шаги [K9–K12 / или «финализацию»]. Спеку в docs/ не переписывай. После [последнего коммита] остановись — жди визуальной приёмки, не финализируй PROJECT_STATE/RELEASES/DECISIONS/BUGS.

Всегда явная STOP-фраза. Иначе Code идёт дальше.

### Отчёт Code после спринта

В CURRENT_TASK.md в конце всегда прошу Code отчитаться:
- Коммит-хэши по каждой подзадаче.
- Финальные счётчики тестов (Vitest + pytest).
- Build status.
- Сколько тестов было переписано под новую структуру (если был рефакторинг).
- **Отклонения от спеки** — явным блоком.

### Версионирование при финализации

Каждый Sprint M-X.Y bump'ит версию: M-A=v0.6.0, M-A.1=v0.6.1, M-A.2=v0.6.2, M-A.3=v0.6.3. Новый milestone (M-B+) bump'ит minor: M-B=v0.7.0. **При финализации каждого спринта** Chat обновляет: `package.json` `version`, `gui/designer/src/lib/version.js` `APP_VERSION`, и добавляет блок в `RELEASES.md`.

### Визуальная приёмка — всегда отдельная сессия

Не продолжаю работу после коммитов Code в той же сессии. Приёмка — свежий compact.

## §13. Классификация задач

Перед началом любой задачи Chat определяет тип. Тип определяет процесс — стартовый пакет, размер спеки, кто правит код, что попадает в журнал.

| Тип | Что | Процесс |
|-----|-----|---------|
| **A. Архитектура / алгоритм** | новые data models, primer design pipeline, рефакторинги ≥30 KB кода, новые алгоритмы | Полная спека 20-30 KB. Полный стартовый пакет (§1) + ANCHORS.md + ARCHITECTURE_v2.md. Полная ротация по §4 после приёмки. |
| **B. Фича среднего объёма** | новый экран, новый workflow | Спека 8-15 KB. Полный стартовый пакет. Ротация по §4. |
| **C. Bugfix-пакет / UX-итерация** | mini-fix серия 3-5 коммитов, набор связанных багов одного компонента | Мини-спека 3-8 KB. Сокращённый стартовый пакет (CURRENT_TASK.md + grep по компоненту). Ротация — только BUGS OPEN→FIXED + journal entry в RELEASES.md. |
| **D. Тривиальная правка** | CSS class, prop default, переименование, inline-style, text label | **Chat правит напрямую** через `Filesystem:edit_file`. Без спеки. Journal entry одной строкой в RELEASES.md. Сокращённый стартовый пакет. |

**Граница C/D — жёсткая:**
- ≤20 строк диффа в 1-2 файлах.
- БЕЗ правок алгоритмических зон, перечисленных в §3 («Запрещённые зоны для Chat в любом типе»).
- Если правка касается алгоритмов / data flow / парсеров / тестов — повышается до C минимум, даже при малом объёме.

**Тип определяется ДО старта работы.** Если в процессе становится понятно что задача больше — повышается тип, переходим в полный цикл. Понижение типа после старта не делается.

**Тип фиксируется в первом сообщении после понимания задачи:** «Это тип B (новый workflow), пишу спеку 10 KB» или «Это тип D (CSS class), правлю напрямую». Игорь может оспорить классификацию.

**Триггеры повышения в процессе:**
- Тип D → C: обнаружилось что правка задевает store/hooks/lib.
- Тип C → B: обнаружилось что нужны новые компоненты или migration store.
- Тип B → A: обнаружилось что нужна новая data model или алгоритм.

При повышении — стоп, переоценка, новая спека под новый тип.

## §14. Признание предела

Если Chat 2 итерации подряд не может верно понять требование (приёмка → FAIL → новая спека → FAIL опять) — это сигнал что нужно одно из:

1. **Игорь даёт скриншот / референс «как должно выглядеть».** Самый быстрый способ — картинка снимает все интерпретационные споры за секунду.
2. **Игорь правит напрямую, Chat фиксирует пост-фактум в журнал.** Если правка тривиальная — это в разы быстрее чем третий цикл Chat→спека→Code.
3. **Эталон из SnapGene / Benchling / Geneious / ApE / pLannotate** — если паттерн в индустрии уже есть. `docs/UX_REFERENCE_BASE.md` стартовая точка.

**Не геройствовать.** Эксплицитно сказать пользователю: «я не уверен что понимаю требование — покажи скриншот / правь сам / укажи продукт где это сделано».

**Сигналы что попал в этот режим:**
- Третий sanity-вопрос (§2) выдаёт «не уверен решит ли это проблему».
- В предыдущей спеке тот же компонент был fail.
- Игорь начинает повторять одно и то же требование в 2+ сообщениях разными словами (это значит я не услышал с первого раза).
- Начинаю чувствовать «может я неправильно интерпретирую требование» — это сигнал, не подавлять его.

При любом из этих сигналов — стоп, переход в режим §14, прошу скриншот / референс / прямую правку Игоря.
